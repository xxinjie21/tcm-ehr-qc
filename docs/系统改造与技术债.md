## 一、权限设计思想

### 1.1 三级权限模型

**设计**：
- **管理员**（`users.role='管理员'`）：全局权限，所有功能可用
- **所有者**（`organization_members.role='owner'`）：组织级最高权限，自助创建者自动为 owner
- **被授权成员**（`member` + 两个开关）：`can_write_qc_rules` / `can_write_dictionary`
- **普通成员**（`member`）：本组织内可用，无管理与增配权

**思想**：权限不是二元的（能/不能），而是**按数据范围分级**的。同一个功能，管理员看全部数据，所有者看本组织，成员只看自己——这是 RBAC 加数据范围的组合。

**踩过的坑**：
- ❌ **拦截器写死取 `orgId`，但路由变量叫 `{id}`** → 跨组校验自上线起从未执行过。也就是说，管理员 A 组的 owner 可以改 B 组的成员设置，因为后端根本没校验"你是不是这个组的 owner"。
- ✅ **修复**：`RequireOrgRole` 增加必填的 `pathVar`，拦截器按声明取变量，取不到即拒绝。

**教训**：权限校验是最后一道防线，**写了不代表生效了**。必须有测试覆盖"跨组访问"的场景——否则你以为有保护，其实没有。

### 1.2 词典写权限的三级设计

| 级别 | 权限 | 类比 Git |
|------|------|----------|
| 提案提交 | 登录即可 | 开 PR |
| 提案审核合并 | 组织所有者 | merge 权限 |
| 基础层导入 | 仅管理员 | 直接改主线 |

**思想**：词典是共享资产，改它要有流程。**"一个人改所有人的词库"和"协作者改自己组织的词库"是两回事**——前者风险大，要严格控制；后者风险小，可以放开。

## 二、多实例部署的坑

### 2.1 进程内状态 = 定时炸弹

**踩坑**：AI 异步任务状态存在进程内 `ConcurrentHashMap` → A 实例提交、B 实例轮询 → 404，前端显示"生成失败"。

**修复**：任务状态迁 Redis Hash，TTL 600s，进程内表作一级缓存。

**思想**：只要是多实例部署，任何"进程内状态"都是定时炸弹。登录态、任务状态、计数器、本地缓存——只要需要跨实例可见，就必须放共享存储。

**识别信号**：你在代码里看到 `static Map`、`ConcurrentHashMap`、`List` 作为成员变量存业务状态时，就要警惕——单实例能跑，多实例必炸。

### 2.2 本地缓存的一致性问题

**设计**：`VersionedCache` 是进程内缓存，存词典/规则的版本。

**取舍**：
- ✅ 优点：快，纳秒级，不占 Redis
- ❌ 缺点：多实例下各实例缓存不一致

**为什么可以接受**：单实例部署为主，且 TTL 短、有版本号失效机制。如果未来真的要多实例，这个缓存层就要重新设计。

**思想**：技术选型要看**部署形态**。单实例和多实例的架构是完全不同的——不要用多实例的复杂度来设计单实例的系统，但要清楚哪些地方是"单实例假设"，将来要拆。

## 三、事务与一致性

### 3.1 事务内失效缓存 = 脏读

**踩坑**：清洗数据时，事务还没提交就调了 `invalidateStats()` → 并发读在事务提交前 miss，按旧数据现算回填 → 提交后缓存持旧值最长 60s。

**修复**：`DistLock.afterCommit()` 在事务提交后才失效。

**思想**：Cache-Aside 的铁律是"先改库，后失效"，但更精确的说法是"先改库，**提交后**再失效"。事务内失效等于白失效——因为其他请求看到的还是提交前的数据。

### 3.2 长事务的取舍

**场景**：数据清洗方法带 `@Transactional`，事务横跨整轮清洗（可能几万条）。

**为什么保留现状**：
- 触发条件苛刻：需要"管理员 + 全库 + 并发清洗"三者叠加
- 实际是手动操作，不会并发
- 改动面大：要把事务降到逐页，循环体抽方法、改签名、注入事务模板、改测试

**思想**：不是所有"技术债"都值得还。**要算投入产出比**——改动成本是 10 人天，而这个 bug 一年都碰不到一次，那就先记着，等真的碰到了再改。

## 四、前端工程化

### 4.1 接口对齐的重要性

**踩坑**：NLP 任务列表返回 `NlpTasksVO{tasks, truncated, limit}`，QC 任务列表返回裸 `List<QcTaskVO>`——前端要写两套逻辑。

**修复**：统一改成 `QcTasksVO{tasks, truncated, limit}`，和 NLP 对齐。

**思想**：相似的接口要**口径一致**。前端调起来才不会困惑，后端维护起来也不容易出错。"截断标志"这种东西，有就是有，没有就是没有——不要有的接口有，有的接口没有。

### 4.2 任务生命周期的统一表达

**设计**：异步任务的进度条、失败清单、取消、重试、历史清单——NLP 和 QC 两套任务，前端组件要统一。

**思想**：任务是一个**抽象概念**，不管是解析任务还是质控任务，它的生命周期都是"排队 → 进行中 → 完成/失败"。好的设计是把这个抽象提出来，而不是每种任务各写一套 UI。

## 五、踩坑总结

| 坑 | 教训 |
|----|------|
| 权限拦截器写死变量名，跨组校验从未执行 | 权限代码必须有测试覆盖"反向用例"——不只测"能进"，还要测"不能进" |
| 异步任务状态存进程内，多实例 404 | 看到 `static Map` 存业务状态就警惕，多实例必炸 |
| 事务内失效缓存，导致脏读 | Cache-Aside 的"后失效"是"提交后失效"，不是"事务内失效" |
| 无界线程池，任务堆积跑不完 | 线程池要显式构造，队列容量和拒绝策略都要自己定 |
| 接口口径不统一，前端写两套 | 相似接口要对齐，返回结构、错误码、分页方式都要一致 |

## 六、值得学习的设计

| 设计 | 为什么好 |
|------|----------|
| `DistLock.afterCommit` | 把"事务提交后执行"这个常见需求封装成工具方法，避免每个调用点都自己写 try-catch |
| 版本号前缀缓存失效 | 不用 `KEYS` 命令，O(1) 失效，不阻塞 Redis |
| 空值哨兵 + 单飞锁 + TTL 抖动 | 缓存三防的标准实现，教科书级别的正确 |
| `PageSizeGuard.clamp` | 分页大小有上限，防止有人传 `size=100000` 拖垮系统 |
| 规则配置化 + 非法配置回退默认 | 配置是人的操作，人就会犯错——要有兜底 |

## 七、自研组件治理：轮子识别与替换实证

### 7.1 什么算轮子，什么算领域代码

**判据**：自研代码分两类——
- **轮子**：重复实现了已引入依赖或 Spring 生态已提供的通用能力，且自研版在正确性/并发/可维护性上更差 → 换。
- **领域代码**：框架没有等价语义（org 级判权、运行时参数审计、跨实例版本失效）→ 保留，不算轮子。

**踩坑**：审查时容易把"看起来像轮子"的东西一锅端。实际 `StatsCache` 的五项语义（版本前缀失效 / SETNX 单飞 / 空值哨兵 / TTL 抖动 / fail-open）`@Cacheable` 一个都表达不了；`ExcelRawStreamReader` 手写 SAX 是为绕开 POI `DataFormatter` 把 14 位时间戳转成 `2.02212E+13` 的 bug。换过去就是功能回退。

**思想**：**"框架没有等价语义"是保留自研的正当理由**。不要为了"少写代码"把领域逻辑塞进框架注解——换壳纯 churn，还丢语义。

### 7.2 替换前必须先跑最小验证

**教训**：12 项替换计划里，**6 项的前提与实测不符**——
- `RRateLimiter` 实测是 ZSET 滑动窗口等价，不是令牌桶（原计划担心的突发放行量差异不存在）；
- Caffeine 的 W-TinyLFU **不是严格 LRU**，换上去直接打破 `VersionedCacheTest` 两条已钉断言；
- RRateLimiter 保不住登录锁定口径（成功也计数 / 窗口续期 / 无剩余秒数）；
- POI 官方 handler 探针实测输出 `2.02212E+13`；
- Spring `DigestUtils` **只有 MD5 系列、无 SHA-256**，统一不了；
- `LlmClient` 外围本就是 RetryTemplate / RestClient / Encryptors，无事可做。

**修复**：每项落地前写**临时用例实测后删除**（保持全量测试数稳定在 556，便于跨批次对比基线）；`javap` 对项目实际版本验 API 签名，不信文档。

**教训**：**计划里写的"现成方案能覆盖"，必须跑一次最小验证才算数**。直觉方案（用 Spring 统一 hash、用 Caffeine 换 LRU、用 `@Cacheable` 换 StatsCache）全部在实测后被证伪。

### 7.3 缓存替换的具体坑

| 坑 | 教训 |
|----|------|
| Caffeine 不接受 null 值 | "该组织没有行"是有意缓存的稳定事实，直接存对象会退化成每次查库（批量质控 4 万条 = 4 万次查询）→ 用 `Optional` 包一层 |
| Caffeine 加 `maximumSize` | 原实现无上界、键空间 = 组织数，加上界会引入当前没有的逐出 → 零行为改动前提下不加上界 |
| `Set.copyOf` 迭代顺序未定义 | 它返回的 `SetN` 按 JVM 启动 SALT 打乱，会破坏"顺序稳定"契约（规则要素顺序、字典键顺序都依赖它）→ 必须用 `LinkedHashSet + unmodifiableSet` 保序 |
| 把可变 `@Data` 缓存为常量 | `QcRuleStore.normalize` 会把取到的子对象直接 set 进生效规则集 → 共享常量 = 全局污染，谁 `getElements().add(...)` 就污染所有调用方 → 抽方法每次返回新对象 |

**思想**：缓存库不是"换上就行"——它的**淘汰策略、null 语义、不可变视图契约**都和手写实现有细微差异，这些差异在测试里被钉住之前，都是行为变更。

## 八、代码审查与零行为改动纪律

### 8.1 只读审查的取证方法

**设计**：对 63 文件 / 8584 行的 common 包做只读审查——
- 否定性结论（"零引用"）一律用 `grep -rn` 计数证明，不靠读印象；
- 库 API 用 `javap -cp <实际 jar>` 对项目版本验证，不信 Spring 文档；
- 每条断言的 `文件:行号` 逐条回读原文件复核（第二/三轮复核专门做这件事）；
- 行数统计用 `[System.IO.File]::ReadAllLines().Count`（`Get-Content | Measure-Object -Line` 在 UTF-8 中文下会少算行）。

**思想**：审查报告的可信度 = 取证方式的可信度。**"我看了一下没人用"不算证据，`grep` 返回 0 才算**。

### 8.2 "零行为改动"裁定口径

**裁定原则**（用户授权"不影响现在能跑的系统"）：
- ✅ **做**：证明为零行为改动的项（注释订正 / 日志文案 / 等价实现收敛 / 堵 NPE 漏网）；
- ❌ **不做**：凡"可能改变可见行为 / 涉及并发与关停语义 / 需运行期确认 / 属净减防御"的，一律保留现状。

**具体被否决的"重构诱惑"**：
- `EntityNormalizer` 三处 `backfill*` 逐字同构——但抽象需 7~9 参数 + 3~4 函数式接口，属过度封装，三个原方法各 30 行反而直观；
- `SearchDTO` 全量归一成 `FiltersDTO`——前提不成立（两边字段互不包含），且 `FiltersDTO` 是 stats/导出契约的一部分，动它 = 动接口契约；
- `handleValidation` / `handleBind` 合并 `joinFieldErrors`——两者格式本就不同（"字段：消息"+去重 vs "字段 消息"不去重），合并必然改可见文案；
- `@RequireRole` 类级分支 / `@Target(TYPE)`——删掉后若有人在类上加注解，鉴权**静默失效**（安全漏洞），净减防御不能做；
- 版本号按 key 维度重写——写错的后果是"改了配置不生效"（静默、极难查），风险收益完全不成比例。

**教训**：**"看起来重复"不等于"应该合并"**。合并前先问：差异点是什么？合并后会不会改行为？会不会丢防御？三个问题有一个答不上来，就保留现状。

### 8.3 审查中确认正确的设计（补充）

| 设计 | 为什么好 |
|------|----------|
| `@RequireOrgRole.pathVar()` 不给默认值 | 漏写即编译不过，根治"变量名不一致导致校验静默失效"——比运行期拦截更狠 |
| `RecordFilter` fail-closed sentinel + 排序键白名单 + 次级键 `id` 保证分页全序 | 恶意排序字段被白名单挡掉，分页不重不漏 |
| `JwtUtil.parseAndVerify` 一遍过（验签+有效期+版本比对） | `revokeAll` 用 Lua 原子自增，`anchorVersion` 用 `EXPIRE` 不写值规避后写覆盖竞态 |
| `ExcelRawStreamReader` 手写 SAX + `disallow-doctype` | 防 XXE，且绕开 POI 日期格式化 bug |
| `EsConfig` 手工装配 ES 客户端 | Boot 4.1.1 实测无 ES 自动装配（`unzip -l` 验证），手工装配必要 |

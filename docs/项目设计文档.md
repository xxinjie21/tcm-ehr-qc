# 中医电子病历质控与标准化系统 - 项目设计文档

## 1. 项目名称、项目目标以及主要使用对象

### 项目名称
中医电子病历质控与标准化系统

### 项目目标
构建一套完整的中医电子病历数据处理系统，实现从原始非结构化病历到高质量标准化数据集的全流程自动化处理。

**具体目标：**
1. 实现非结构化病历文本自动转换为结构化实体字段，解决机器不可读问题；
2. 建立事前、事中、终末全链路质控体系，过滤错误、缺失、逻辑冲突数据；
3. 完成中医病历专属数据治理，统一术语、清洗脏数据；
4. 输出标准化数据集文件，满足病历规范化整理、数据统计、合规归档的基础信息化需求。

### 主要使用对象
1. **管理员**：负责病历导入、质控校验、术语词典配置；
2. **审核员**：负责人工复核异常病历、修正结构化错误。

## 2. 项目主要解决什么问题，明确系统准备做什么、不做什么

### 主要解决的问题
1. **数据输入杂乱**：病历文本口语化、术语不统一、字段缺失严重，机器无法解析；
2. **无结构化转换环节**：非结构化文本无法拆解为数据库可直接存储的标准化字段；
3. **无质量管控链路**：数据错漏、逻辑冲突、方药辨证不匹配等问题无双重校验；
4. **无标准化治理输出**：原始病历数据规范性差、质量参差不齐，无法直接用于统计分析。

### 系统准备做什么（功能边界）
**核心功能（必做）：**
- 用户登录与基础权限管理
- 病历批量导入与单条新增
- 原始病历查看（只读）
- 病历修改、删除、标签与归档管理
- NLP实体抽取（症状、舌脉、证候、病因、治法、方剂、中药）
- 术语标准化（疾病、证候、症状、中药、方剂）
- 质控检查（缺失字段、格式、查重）
- 结构化结果人工校正与异常复核
- 数据清洗、规整与标准数据集导出
- 终末质控评分与质控报告
- 词典管理（术语库维护）

**拓展功能：**
- 诊疗逻辑一致性检查
- 疾病频次统计
- 证候分布统计
- 方剂和中药频次统计

**系统不做什么（功能排除）：**
- 不实现病例智能检索
- 不实现处方智能推荐
- 不实现临床数据可视化分析
- 不实现患者自然语言自述输入
- 不实现候选方剂/中药推荐
- 不实现配伍禁忌与剂量审查
- 不实现知识库迭代、规则自动优化

## 3. 系统完整业务流程

### 数据流转总流程（闭环链路）
```
外部原始病历数据【输入】
    ↓
病历管理模块（入库存储）【输出原始病历库】
    ↓
智能结构化模块（NLP文本解析抽实体）【输出结构化临时数据】
    ↓
智能质控模块（三层校验筛错）【输出合规病历 + 异常病历】
    ↓                                    ↓
合格（≥90分）                  60≤评分<90 或逻辑冲突
    ↓                                    ↓
数据治理模块                 人工复核队列（7个工作日时限）
    ↓                                    ↓
清洗、归一、融合、去重         审核人员修正 → 重新评分校验
    ↓                              ↓           ↓
高质量标准数据               通过→治理   不通过→隔离归档
    ↓
标准化数据集持久化存储
    ↓
权限管控导出（CSV/JSON）
```

### 异常处理分支
- **评分<60分**：直接标记invalid，存入异常数据区，禁止导出
- **核心要素真缺失≥3项**：直接判定无效
- **证候-治法与证候-方剂同时冲突**：直接判定无效
- **文本无法解析**：直接判定无效
- **复核超时**：仍在待复核列表，前端高亮提醒，不自动关闭

### 详细业务流程
1. **数据输入阶段**：管理员上传病历Excel文件（.xlsx），单文件≤50MB，单次最多20个文件；系统自动校验格式、过滤空文件；
2. **结构化转换阶段**：NLP引擎从自由文本中一次性抽取全部中医实体（症状、舌象、脉象、证候、病因、治法、方剂、中药+剂量），保留原文溯源关系（sourceText）；
3. **质量控制阶段**：
   - **事前质控**（POST /api/qc/check）：检查核心要素缺失（症状、证候、舌象、脉象、中药），查重，格式校验
   - **事中质控**（POST /api/qc/check/logic）：校验诊疗逻辑一致性（证候-治法、证候-方剂、证候-中药匹配关系）
   - **终末质控**（POST /api/qc/score）：自动评分（满分100分），根据评分分级路由
4. **人工复核阶段**：评分60-89分或逻辑校验不通过的病历进入待复核列表，审核人员在对比界面修正后点击「复核通过」，系统自动重新评分；
5. **数据治理阶段**：对合格数据进行自动清洗（去重、格式规整、脏数据隔离）、术语归一（映射国标标准术语），产出标准化数据集；
6. **成果输出阶段**：支持UTF-8 CSV和JSON数组两种格式导出，满足本地存储和复用需求。

### 调用流程示例
```
用户点击[执行NLP抽取]
    ↓
前端 POST /api/nlp/extract → Java后端
    ↓
Java经 PythonNlpClient 转发 → Python服务（:8001）
（transformers 推理 → BIO 解码 → 规则兜底）
    ↓
Python服务 返回 9 类结构化实体（6 类模型 + 4 类规则）
    ↓
Java后端 → 术语归一(ES查询) → 评分计算(calculateScore)
    ↓
存入MySQL records.structured_data → 返回前端
```

### 模块关系说明
1. **前端**：Vue.js 3 + Element Plus构建SPA应用，通过HTTP请求调用Java后端API，菜单按角色动态渲染；
2. **Java后端**：Spring Boot提供RESTful接口，11个Controller共49个接口，负责所有业务逻辑（评分、术语归一、质控、数据治理、NLP抽取、AI 解读/助手/复核、LLM 配置等）；
3. **NLP抽取服务**：Python FastAPI 服务（`python-nlp/`），`transformers` 加载 `Monor/hwtcmner` + BIO 解码 + 规则兜底，对外由 `POST /api/nlp/extract`（Java 转发）暴露；
4. **模型推理**：独立服务（:8001），Java 经 `PythonNlpClient` HTTP 转发；服务/模型不可用时降级（空 9 类，`modelAvailable=false`；模型缺失但服务在 → 规则 4 类）；
5. **数据库**：MySQL存4张表（users、records、review_tasks、operation_log），structured_data和qc_results以JSON字段存在records表；
6. **文件存储**：JSON文件存术语库（data/dictionaries/*.json，支持备份回滚），日志文件存操作记录。

### 服务划分

| 服务 | 语言 | 端口 | 职责 | 接口数 |
|------|------|------|------|--------|
| Java后端 | Java/Spring Boot | 8080 | 业务逻辑、数据库、文件操作、评分算法、术语归一；转发 NLP 抽取 | 49个 |
| NLP抽取服务 | Python/FastAPI | 8001 | 模型推理（transformers + hwtcmner）、实体识别、规则兜底 | 1个（+ `/health`） |

## 9. 核心算法或核心处理逻辑

### 1. NLP实体抽取算法
**方案总结**：本项目NLP模块采用开源已微调中医 NER 模型 `Monor/hwtcmner`（RoBERTa），无需自行训练与微调；**Python FastAPI 服务**用 `transformers` 加载模型推理，正则做后处理，Java 侧经 `PythonNlpClient` 转发，结合自建术语库完成标准化，兼顾开发简易性与识别精度。

**实现什么功能**：从中医病历自由文本中一次性抽取9类实体（疾病、症状、舌象、脉象、证候、病因、治法、方剂、中药+剂量），输出结构化数据。

**具体怎么实现**：
```
原始文本 → 预处理 → transformers分词 → 模型推理 → BIO解码 → 规则兜底 → 术语归一 → 结构化数据
```

**第一步：预处理**
- 去除无关字符（特殊符号、多余空格）
- 统一编码格式（UTF-8），数据库字符集明确为utf8mb4（支持4字节字符，覆盖生僻字如"㿠"）
- 段落分割（按句号、分号切分）

**第二步：中文分词**
- 使用 `transformers` 加载模型自带 tokenizer（与训练侧同一套，中文按字切分，无 OOV 风险）
- 术语层面的词典匹配交由"第五步：术语归一"（ES 三级匹配）承担，分词阶段不做词典干预

**第三步：NER模型实体识别**
- 使用预训练 RoBERTa 中医NER模型（`Monor/hwtcmner`，13 标签 BIO）
- 输入分词后文本，模型输出BIO标签序列
- B-开头=实体开始，I-实体内部，O=非实体
- 示例输入："发热咳嗽舌红苔黄脉浮数"
- 示例输出：B-症状 I-症状 B-症状 I-症状 I-症状（模型只覆盖 6 类；舌象 / 脉象不在标签集内，由规则兜底补出）

**第四步：后处理规则**
- **剂量提取**：正则表达式 `[\u4e00-\u9fa5]+(\d+\.?\d*)(g|ml|mg|片|枚|条|张)` 从中药实体后提取剂量
- **多实体合并**：合并连续相同类型实体（"发热、咳嗽、头痛"→ 三个症状实体）
- **溯源保留**：记录每个实体在原文中的位置（sourceText字段）

**第五步：术语归一**（POST /api/governance/normalize）
- 将口语化表述映射国标术语（"嗓子疼" → "咽痛"）
- 五类术语库：疾病GB/T 16751.1、证候GB/T 15657-2021、症状GB/T 16751.1、中药中国药典2025、方剂中医方剂大辞典
- ES匹配策略：IK分词器 + 自定义词典（术语库全量标准词+别名收进IK词典，防止"恶寒"被切碎为"恶"+"寒"影响匹配质量）；匹配时取score≥阈值的top1结果，低于阈值或无结果返回原词、source置空
- 未命中时返回原词，source返回空字符串
- ES索引构建详细流程：1.系统启动时ApplicationRunner监听器触发，从data/dictionaries/*.json加载5类术语数据；2.分别创建五个ES索引（diseases/patterns/symptoms/herbs/formulas），配置IK分词器；3.生成IK自定义词典文件（config/ik/medical_terms.dic），格式：每行一个术语，包含标准词+所有别名；4.重启ES或调用IK热更新API加载词典；5.验证索引建立（"_cat/indices?v"检查分片和文档数）；6.首次归一测试：查询"恶寒"验证IK分词不被切碎、score阈值匹配生效

**完整接口调用链**：
```
POST /api/nlp/extract → Java 转发 Python 服务（transformers分词→模型推理→BIO解码）→ 规则兜底 → 自动调用normalize归一 → 返回完整structuredData
```

### 2. 质控评分算法（calculateScore）- Java实现
**实现什么功能**：对单条病历按自身缺陷项相对评分（相对评分），满分100分，按错误类型累计扣分，最低扣至0分，并根据评分进行三级分级路由。

**具体怎么实现**：

```
输入：structuredData + 质控检查结果
    ↓
初始化 score = 100, deductions = []
    ↓
┌─────────────────────────────────────────┐
│ 第一层：核心必填字段缺失检查（每项-15分）│
│ 脉象为空 → -15                          │
│ 舌象为空 → -15                          │
│ 证候为空 → -15                          │
│ 治法为空 → -15                          │
│ 方剂为空 → -15                          │
│ 中药为空 → -15                          │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│ 第二层：辨证逻辑冲突检查（每项-10分）    │
│ 证候-治法不匹配 → -10                   │
│ 证候-方剂不匹配 → -10                   │
│ 证候-中药不匹配 → -10                   │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│ 第三层：格式/重复检查（每项-5分）        │
│ 格式错误 → -5                           │
│ 数据重复 → -5                           │
│ 症状为空 → -5                           │
└─────────────────────────────────────────┘
    ↓
score = max(score, 0)
    ↓
┌─────────────────────────────────────────┐
│ 严重问题判定（直接invalid）：            │
│ - 核心要素真缺失 ≥ 3项                    │
│ - 证候-治法 与 证候-方剂 同时冲突        │
│ - 文本无法解析                          │
└─────────────────────────────────────────┘
    ↓
分级路由：
  score ≥ 90 且无逻辑错误 → grade="合格" → 进入数据治理
  60 ≤ score < 90 或 逻辑冲突 → grade="待复核" → 进入人工复核
  score < 60 或 严重问题 → grade="无效" → status=invalid，隔离归档
```

### 3. 诊疗逻辑一致性检查算法（checkLogic）- Java实现
**实现什么功能**：校验证候、治法、方剂、中药之间的中医诊疗逻辑是否自洽。

**具体怎么实现**：固定 3 条证候规则 + 2 条舌脉规则，写死在代码中，不支持自定义编辑。

**核心规则示例**：
```java
// 规则1：证候-治法-方剂匹配规则
Map<String, Map<String, Object>> rules = new HashMap<>();
rules.put("风寒感冒", Map.of("treatment", "辛温解表", "formula", List.of("麻黄汤", "桂枝汤")));
rules.put("风热感冒", Map.of("treatment", "辛凉解表", "formula", List.of("银翘散", "桑菊饮")));
rules.put("暑湿感冒", Map.of("treatment", "清暑祛湿", "formula", List.of("新加香薷饮")));

// 规则2：舌脉一致性规则
Map<String, List<String>> tonguePulseRules = new HashMap<>();
tonguePulseRules.put("舌红", List.of("脉沉迟"));  // 舌红不配脉沉迟
tonguePulseRules.put("舌淡", List.of("脉数"));    // 舌淡不配脉数
```

**执行流程**：
1. 遍历structuredData中的patternList
2. 对每个证候，检查treatmentList是否包含对应治法
3. 对每个证候，检查formulaList是否包含对应方剂
4. 检查tongueList与pulseList是否矛盾
5. 返回consistent布尔值和conflicts冲突列表

### 4. 术语标准化算法 - Java实现
**实现什么功能**：将口语化/非标准中医术语映射为国标标准术语。

**具体怎么实现**：
```
系统启动 → 从data/dictionaries/*.json读取术语库 → 全量重建 Elasticsearch 索引
    ↓
存放结构：Elasticsearch 索引（standard_term / aliases / source 字段）—— ES 负责召回候选
    ↓
输入术语 → ES 召回候选 → Java 侧三级匹配：
  1. 精确：与标准词或别名完全一致 → 直接返回标准术语
  2. 包含（双向）：输入含标准词/别名，或标准词/别名含输入 → 返回标准术语（多命中取最短标准词）
  3. 模糊：字符集 Dice 相似度 ≥ 0.8 → 返回标准术语
  4. 三级都不中 → 返回原词，source 为空
    ↓
导入 / 回滚术语库时重建 ES 索引

注：ES 是归一的唯一权威（2026-09-23 起不再有内存词典兜底）。ES 不可用时归一报
HTTP 503 + code=1010，而不是把词判成「未收录」。
```

**术语库版本管理**：
- 导入前自动备份旧文件到 `data/dictionaries/backup/`（时间戳命名）
- 支持按备份文件名一键回滚到指定版本
- 示例：`symptoms.json.bak_20260811_143000`

### 5. 数据清洗算法 - Java实现
**实现什么功能**：对质控合格数据做深度清洗、去重、规整，产出标准数据集。

**具体怎么实现**：
1. **去重**：基于病历原始文本哈希值去重
2. **字段修补**：轻度缺失字段（如非核心症状）自动标记
3. **格式规整**：统一日期格式（YYYY-MM-DD）、剂量单位（g/ml）
4. **脏数据隔离**：无法修复的数据标记invalid，不混入标准数据集
5. **术语归一**：调用术语标准化接口，统一全库术语

## 13. 当前仍未解决的问题

### 技术问题
1. **NLP模型效果**：开源中医NER模型（Monor/hwtcmner）在实际病历数据上的准确率和召回率需要测试验证，可能需要微调
2. **术语归一覆盖率**：口语化表述与标准术语的映射覆盖率可能不足，需要补充同义词
3. **质控规则完整性**：证候-治法-方剂-中药的匹配规则目前仅 3 条证候规则 + 2 条舌脉规则，覆盖面有限
4. **性能瓶颈**：NLP 模型推理在 CPU 上单条约数百毫秒（Python 服务推理），全库（≥3 万条）须批处理送推理、仍属离线批处理；非 NLP 环节基准为全量评分重算 ≤3 分钟、单页查询 ≤300ms、统计 ≤2 秒

### 业务问题
1. **数据获取**：真实中医电子病历数据需提前找老师获取，注意数据脱敏与保密
2. **术语库构建**：国标术语文件（Excel/CSV格式）需要获取原始文件，由LLM转换为JSON
3. **质控规则验证**：评分规则的合理性（扣分分值、分级阈值）需要中医专家确认
4. **复核流程细化**：人工复核的具体操作细节（如修正哪些字段、复核通过的判断标准）

### 是否引入中间件的思考

**Redis**：
- 当前方案：**已引入**（Docker Compose 中间件之一）。用途为全库写任务防重锁（`SETNX tcm:task:{type}` + EX 900s，见 `后续开发方案.md §8.7`）；导入任务状态仍用内存Map存储（重启丢失），术语库启动时加载到ES索引
- 未使用的能力：持久化导入任务状态、缓存术语库、存储用户会话（当前数据量下内存够用）
- 结论：**需要**（仅用于任务防重，不做缓存）

**RabbitMQ**：
- 当前方案：NLP 抽取为 **Python FastAPI 独立服务（:8001）**，Java 经 `PythonNlpClient` HTTP 转发，无消息队列
- 如果引入RabbitMQ：NLP任务可以异步处理，前端轮询结果，服务间解耦
- 课程设计结论：**不需要**（v1 明确不做异步改造）。NLP 抽取为本地服务调用，单条数百毫秒（localhost，无跨机网络）；全库（3 万条）解析属离线批处理，由前端放宽超时 + 勿重复提交兜底

**是否使用的判断标准**：
1. 数据量是否超过内存承载（3 万条全库操作 → 需要 Redis 做任务防重，不做缓存）
2. NLP处理是否需要排队等待（单条数百毫秒、全库为离线批处理 → v1 仍不做 MQ / 异步）
3. 老师是否有明确要求（如要求使用→必须加）

1. **数据格式**：实际病历数据的格式和字段是否与需求文档一致
2. **NLP方案选择**：使用开源NER模型还是ERNIE-UIE API，需要确认
3. **部署方式**：系统最终是本地部署还是需要云端部署
4. **评分标准**：质控评分的扣分规则和分级阈值是否需要调整
5. **中间件要求**：老师是否要求使用Redis/RabbitMQ等中间件（当前方案不使用）

## 14. AI可解释质控增强设计

> 定位：在既有 16 项必做功能基础上，新增"AI 辅助可解释质控"增强需求（对应《需求分析报告》第17条、功能设计文档附录C）。详细实施规划见《docs/后续开发方案.md》。

### 14.1 归一算法增强（normLevel）
在现有三级匹配（精确/包含/模糊）基础上，命中实体写入 `normLevel`（1/2/3）与 `normSource`，支撑溯源提示与三级命中分布统计；`CleanResultVO` 增加 `normByLevel {exact, contain, fuzzy}`。

### 14.2 AI质控评分（calculateScore）落地
实现文档第9节 9.2 节算法：`common/utils/QcScorer`（三层扣分 + 严重判定 + 分级路由）+ `common/utils/LogicChecker`（3条证候规则 + 2条舌脉规则）。新增 `POST /api/qc/score`（单条）与 `POST /api/qc/score/batch`（全库重算）接口；扣分明细与预检单写入 `records.qc_results`，使评分**可溯源、非黑盒**。

### 14.3 AI质控解读卡
详情页一键生成自然语言质控解读：数据源为行21字段 + structuredData + normLevel，**规则出结论**（完整性 / 缺项重点 / 归一命中 / 关键提示），再由 `POST /api/ai/interpret`（`LlmClient`）**LLM 叙述**生成报告与「主诉 / 诊断 / 辨证 / 方药」摘要；**LLM 不可用 → 降级模板叙述**、保留规则结论；含「AI辅助分析，最终以人工复核为准」声明。

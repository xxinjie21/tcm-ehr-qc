## 一、需求前提核查：四个批量功能都已经有进度条

「批量功能都要有进度条」这个前提**已经不成立** —— 逐处取证如下。

### 1.1 NLP 批量解析 / 归一（基准实现）

`frontend/src/components/NlpBatchPanel.vue`（566 行）：

- `:50` `<div v-if="activeTask" class="batch-progress">`；`:52` `<el-progress v-bind="progressBar" :stroke-width="10" />` —— 真实百分比。
- `:220` `progressBar` computed。
- `:66-70` 任务**运行中**只给一行计数（`已失败 N 条 · 任务结束后显示清单并支持重试`），终态改 `el-collapse` 折叠明细 —— 避免每 2 秒轮询重渲染长表。
- `:104` 起是「最近任务」清单（含「只看有失败的」筛选与截断提示）。
- 后端 `NlpBatchServiceImpl.list():643` 返回 `NlpTasksVO`（`:656` 构造），带 `truncated` 与 `limit`，**多取一条精确判截断**。

### 1.2 QC 批量重算

`frontend/src/views/Qc.vue`（984 行）：

- `:55-61` `<el-progress v-if="isActiveTask(recomputeProgress)" ... />`（注释标 `I7`：此前只有按钮文案，看不出推进快慢）。
- `:42` 起有取消重算入口；`:63-88` 终态失败清单；`:85` 附近「仅重试失败」。
- `:475` 起 `recomputeBar` computed；`:501` 起 `pollTask`（2s 轮询）。
- 上一轮已补 `resumeRunningTask()`（`onMounted` 调用）：从 `listQcBatch()` 找 `QUEUED` / `RUNNING` 并接管 —— **刷新或切页返回不会丢失在跑任务**。

⇒ QC 的**进度条本来就有**；缺的是清单与失败计数（见 T1 / T2）。

### 1.3 导入

`frontend/src/views/Records.vue`：`:117-125` 是**两态**进度条；`:567-587` 的 `importBar` computed 注释写明了为什么必须两态 —— `done` 只在整个文件的请求返回后才 +1，第一个文件还在传的整段时间里 `percentage` 恒为 0，而 `el-progress` 的填充宽度恒等于 `percentage%`，条子会看起来完全是死的；故一个文件都没完成时走不确定流动条，有文件完成后才切真实文件级百分比。

后端 `RecordServiceImpl.importRecords():109` 是**同步**方法；`taskId` 注释（`:118` 附近）明写「仅作本次请求的回执标识（P5.11：导入是同步的，不再维护内存进度表）」。勾选「导入后自动解析」时另提交后台 NLP 批任务并由 `ImportTaskVO.autoExtractTaskId` 回传 —— 那一段**已经**复用 NLP 的进度条。

### 1.4 清洗

`frontend/src/views/Governance.vue:82-91` 是不确定进度条，注释（`28.14`）写明「后端是同步接口、拿不到真实百分比，用不确定进度条只表达『在推进』；刻意不显示百分比数字，避免暗示一个并不存在的精确进度」。

后端 `GovernanceServiceImpl.clean():92` 同步返回 `CleanResultVO`。

### 1.5 小结

四条路径**都已有进度反馈**，只是形态分三档：真实百分比（NLP / QC）、两态（导入）、不确定流动条（清洗）。没有「哪个批量功能完全没有进度条」。

## 二、约束：异步禁用自研

- 全仓**没有** `@Async`、`ThreadPoolTaskExecutor`、`@EnableAsync`（grep 实测为空）。异步能力现由自研的 `java-backend/src/main/java/com/tcm/ehr/common/utils/AsyncTaskRegistry.java` 承担（提交拿任务号 + 轮询结果；请求上下文显式传播、结果按归属隔离、状态落 Redis 跨实例可见）。
- 新约束要求：**新增异步能力必须用框架机制，不许再造自研轮子**。
- 这条约束不影响 T1 / T2 —— 两者都只**读**已有的异步任务数据，不新增任何异步能力。
- 它直接决定 X1 的取舍（见第五章）。

## 三、T1：QC 批量重算补历史任务清单

### 3.1 缺口

QC 页只表达**当前/最近一次**任务。刷新或切页返回能接上在跑任务（`resumeRunningTask()`），但**已结束的任务详情不可回看**。NLP 侧有「最近任务」清单，两侧不一致。

### 3.2 后端改动（约 35–40 行，含**接口签名变更**）

- `QcBatchServiceImpl.list():457` 现在返回**裸 `List<QcTaskVO>`**、`LIMIT 50`、**无截断标志**。
- `QcTaskVO` 自带字段注释「失败清单；列表接口不带（省流量），详情接口带」。
- 参照 `NlpBatchServiceImpl.list():643` + `NlpTasksVO`：新增 `QcTasksVO{tasks, truncated, limit}`（新类约 15 行），`list()` 多取一条（`LIMIT 51`）精确判截断。
- **接口签名是编译期破坏性改动**，须一并改：`IQcBatchService.list()` 返回类型、`QcController.listScoreBatch():133-135`（`GET /api/qc/score/batch`）的返回类型。⇒ 实际改动比「约 10 行」大，估 **35–40 行**。

⚠️ **响应形状变更的波及面（动手前必须先看）**：`GET /qc/score/batch` 的响应数组改 `{tasks,...}` 后，`(res.data || []).find(...)` 这类写法会静默失效（对象上 `.find` 抛错、被 `catch` 吞）。共**两处**消费点，都要同步改成 `(res.data.tasks || [])`：

1. `frontend/src/views/Qc.vue:620-622` —— `resumeRunningTask()`（T1 自己所在的页面；改了它才能「刷新/切页返回接上在跑任务」）。
2. `frontend/src/views/StandardizationReport.vue:188` 导入、`:462` 调用、`:463` `find` —— 否则 `/standardization-report` 的 `adoptRunningTask()` 会静默退化成「提示稍后刷新」。

### 3.3 前端改动（约 120–130 行）

- ⚠️ **实施变更：未抽共用组件**。原计划把 `NlpBatchPanel.vue:104` 的「最近任务」表格抽成共用组件；但两处列集本就不同（NLP 是「提交时间 / 类型 / 状态 / 操作」，计数嵌在状态文案里；QC 需要「提交时间 / 状态 / 条数 / 成功 / 失败 / 操作」），而 §3.4 验收第 4 条要求 NLP 侧输出不变 —— 强行共用只能靠列配置 / slot 参数化，属为抽象而抽象。改为在 QC 页内实现同口径的本地清单块（`.recompute-tasks`），**NLP 面板一行未动**。
- QC 页接上该组件；点击某条任务调 `getQcBatch(id)` 回看其进度与失败明细。
- **同步改两处 list 消费方**（见 §3.2 ⚠️）：`Qc.vue:622` 与 `StandardizationReport.vue:463` 的 `(res.data || [])` → `(res.data.tasks || [])`。
- 进度条形态遵循项目既有统一口径：**`indeterminate` 必须配 `:percentage="100"`**，**`stripedFlow` 必须与 `striped` 同时给且不可与 `indeterminate` 同给**（`el-progress` 填充宽度恒等于 `percentage%`，给 0 时条子不可见）。

### 3.4 验收标准

1. QC 页能列出最近 N 条重算任务（提交时间、状态、总条数、成功、失败）。
2. 点击任一条可回看该任务的失败清单；列表不带失败明细，详情才带。
3. 超过上限时显示「已省略更早的任务」，且该提示在不足上限时**不出现**。
4. `/standardization-report` 的 `adoptRunningTask()` 行为不变（接管在跑任务仍成功）。
5. 后端测试基线不退化。

## 四、T2：QC 运行中显示失败计数

### 4.1 缺口

`Qc.vue:63` 的失败块条件是 `v-if="!isActiveTask(recomputeProgress) && recomputeProgress && recomputeProgress.failures.length` ⇒ **任务运行中**即便已失败若干条，页面上也看不到。NLP 侧的对应实现在 `NlpBatchPanel.vue:66-70`：运行中给一行计数，终态再展开明细。

### 4.2 改动（约 5 行）

### 4.3 验收标准

1. 运行中出现失败时立刻可见计数，无需等任务结束。
2. 无失败时该行不出现。
3. 终态失败清单仍折叠/按原样展示。

## 五、明确不做的事

| # | 项 | 不做的理由 |
|---|------|-----------|
| X1 | 把导入 / 清洗的不确定条升级为真实百分比 | 二者是同步方法（`RecordServiceImpl.importRecords():109` / `GovernanceServiceImpl.clean():92`），要真实百分比必须异步化。复用自研 `AsyncTaskRegistry` 违反硬约束；改用 Spring `@Async` 则等于给两个功能各造一套异步架构（任务状态、worker、取消、失败重试、断线重连）；**且成本主体不止 `@Async` 本身** —— NLP/QC 之所以「可回看 / 可取消 / 仅重试失败」，靠的是落库任务表（`nlp_task` / `qc_task` + `cancel_requested` + 轮询 + `failed_ids`），导入/清洗要同等能力就得再造一套同类落库基建。此外还要重新设计**导入的部分失败回滚语义**与 **`clean()` 的 `@Transactional` 边界**（该方法带 `@Transactional`、方法体内有两次 ES 往返，管理员全库时事务横跨整轮清洗，已登记于 `docs/未完成事项与验证缺口.md` §一）。成本远大于收益。 |
| X2 | QC 补 ETA | 锦上添花；且 QC 侧重算速度无可信采样数据，ETA 数字缺乏依据。 |

# 计划完整性与风险评审

> 评审日期：2026-09-19
> 评审对象：`docs/后续开发方案.md`（批A~批E 全部任务）+ 现有代码基线
> 评审问题：按现计划全部做完，能否得到一个完整、自洽、可交付的项目？
> 评审方式：计划文档 ↔ 需求分析报告 ↔ 功能设计文档 ↔ 项目设计文档 ↔ openapi ↔ database-init.sql ↔ 实际代码，五方交叉比对

---

## 0. 一句话结论

**不能。** 批A~批E 全做完，得到的是「完整项目里成员C 那条线」——数据治理 + 词典 + AI 增强。整条数据链路的入口（病历导入）和第二环（NLP 结构化解析）都不在批A~E 里，8 个菜单会有 3 个仍是 `Placeholder.vue`；同时计划内部存在 7 处必须裁决的矛盾，其中数据规模口径的冲突（100 条 vs 3 万条）会让批B·2.3 的验收标准无法达成。

## 1. 致命问题（做完也补不上）

### P0-1　批A~E 只覆盖了三分之一的需求

`需求分析报告.md` 的"必做功能"共 17 条，按 `后续开发方案.md §3` 分给三个成员，但只有成员C 的活被写成了任务：

| 成员 | 覆盖的必做项 | 方案里有什么 |
|------|-------------|-------------|
| 成员C | 10 / 11 / 12 / 14 / 15 / 16 / 17 | 批A~批E 全部详细任务（目的/改动点/流程/验收） |
| 成员A | 3 / 4 / 5 / 查询1 / 必做2 | 仅 `§3.1` 一张「现状」表，无任务分解、无改动点、无验收标准、无排期 |
| 成员B | 6 / 7 / 8 / 9 / 必做13 | 仅 `§3.2` 一张「现状」表，同样无分解 |

**直接后果**——批A~E 全部完成后，`frontend/src/router/index.js:15-17` 的三个路由仍指向占位页：

- `/records`（病历数据）→ `Placeholder.vue`：必做3/4/5/查询1 未实现
- `/nlp-extract`（结构化解析）→ `Placeholder.vue`：必做6/7/8/9 未实现
- `/review`（人工复核）→ 批D 会建 `Review.vue`，但 `§3.3` 自己写明"依赖成员A 的病历查询（按条件筛选待复核）"，属半阻塞
- `/audit-log`（日志审计）→ `AuditLog.vue:53` `USE_MOCK = true`，批A~E 没有任何任务去切真（属成员A 的 LogController）

即：8 个菜单里 3 个完全空壳 + 1 个半阻塞，而批E 6.2 的"全量回归 §6 场景 100% 通过"里根本没有这几页的回归场景——回归清单只覆盖治理/词典/质控/复核/看板。

> **裁决点**：要么把成员A/B 的任务也写成批（建议批F/批G，同样四段模板），要么在方案里明确声明"本方案仅成员C 线，完整交付另见 XX"，避免批E 收口时出现"计划已 100% 完成但项目不完整"的假象。

### P0-2　NLP 抽取零代码 + 默认关闭，会让质控评分把真实数据全判无效

- 整条链路的第 2 环没有任何实现；NLP 抽取定为 **Python FastAPI 服务（`python-nlp/`，当前仅 `.gitkeep`）+ Java `PythonNlpClient` 转发**，尚未开工。
- 批B·2.3 的评分规则：核心字段缺失各 -15（脉象/舌象/证候/治法/方剂/中药 6 项），核心缺失 ≥3 项 → 直接判 `invalid`。
- 断网/未接入时的"规则兜底"只能补舌象/脉象/病因/治法 4 类（方案 §1.2），疾病/症状/证候/方剂/中药 5 类拿不到。
- 现有 500 条能跑通，是因为 `structured_data` 是 `seed-database.py` 按词典预生成的（交付报告 §1.3），不是真抽取。

**结论**：真实病历一进来，6 项核心里至少有证候/方剂/中药 3 项为空 → 几乎全部命中"核心缺失 ≥3" → 全库判无效。批B·2.3 的验收标准"batch 后分级分布合理（非 85/12/3 随机）"在 NLP 未接入的前提下无法真实达成，只能拿 seed 数据自证。

> **裁决点**：NLP 接入必须前置为批B 的硬依赖（或明确"批B 验收用 seed 数据、真实数据验收延后"），否则整个质控线是纸面上的。

### P0-3　数据规模口径自相矛盾，且吞吐量算不过来

| 来源 | 口径 |
|------|------|
| `后续开发方案.md §1.3` | 真实病历 ≥3 万；SQL 优先；`seed-30k.py` 性能验证；batch 上限 3 万；3 万全量重算 ≤3min |
| `需求分析报告.md §4.1`（自称"唯一依据"，见 §1.3） | 单次批量处理上限 100 条；单条解析 ≤3 秒；批量 ≥30 条/分钟 |
| `项目设计文档.md` | 按 ≤100 条 / 并发 ≤10 设计 |

**吞吐量核算**：需求 §4.1 的 ≥30 条/分钟是含 NLP 解析的全链路速度。3 万条 ÷ 30 条/分钟 = 约 16.7 小时。方案 §1.3 说的"3 万全量重算 ≤3min"只统计了纯评分（不含 NLP），两者不是一回事，但方案把它们并列成同一套"3 万规模化"指标，会误导评审。

另外 `data/seed-30k.py` 在仓库中不存在（方案 §1.3 与 §5.1 都把它列为"新增"，但它是性能验证的前置条件，且造 3 万条含 `structured_data` 的数据本身是个独立工作量）。

> **裁决点**：明确二选一——① 承认项目是"≤100 条/单机/小批量"（改方案 §1.3 与 §7 的 3 万口径）；② 承认 3 万（则必须改需求 §4.1 与项目设计文档，且接受全链路跑一遍要十几个小时，batch 同步接口 + 无异步 + 无进度的设计需要重新评估）。批E 6.1 的文档同步清单里没有这一项，这是收口时最容易漏的。

### P0-4　数据链路的入口不在任何批里

链路第一环是"Excel 导入（去重、格式规整）"（README），对应必做3。实现它的是 `RecordController` 的 7 个接口，属成员A，不在批A~E。批A~E 的起点默认"已有 500 条 seed 数据"，等于从链路中间开始做。

## 7. 评审结论

| 维度 | 评价 |
|------|------|
| 文档质量 | **高**。四份设计文档 + openapi 层次清晰，方案的四段模板（目的/改动点/流程/验收）专业度超出一般课程设计 |
| 计划覆盖度 | **低**。仅覆盖 1/3 需求，缺 2 条完整业务线 |
| 计划自洽性 | **中**。7 处内部矛盾，其中数据规模口径为硬冲突 |
| 当前实现度 | **批A 之前**。方案 §5 的 20 个后端新增文件全未建 |
| 可交付性 | **弱**。无部署方案、无隔离区页面、入口链路缺失、NLP 空目录 |
| 风险 | **高**。P0-2（NLP 缺失导致全库判无效）与 P0-3（规模口径冲突）会在验收现场直接暴露 |

**核心判断**：这份方案是一份质量很高的单线开发计划，但被当成了整个项目的计划。真正需要补的不是更多细节，而是先回答"完整项目 = 谁的哪些活"，再谈批次。

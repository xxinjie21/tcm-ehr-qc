## 二、批次 A · 正确性缺陷

### A1 ✅ · `review_tasks` upsert 的 SQL 是语法错误（阻断）

- **位置**：`java-backend/src/main/java/com/tcm/ehr/mapper/ReviewTaskMapper.java:38`
- **证据**：`VALUES (REPLACE(UUID(), #{recordId}, …)` —— 列清单 9 列，值元组写成 `REPLACE(...)`，括号不平衡。
  MySQL 实测（`PREPARE`，只编译不执行）：原样 → `ERROR 1064`；把 `REPLACE(` 换成 `(` → 通过。
- **改法**：删掉 `REPLACE(` 三字，保留 `(UUID(), …)`。列清单 9 列与 9 个值一一对应，无需改动其它部分。
- **验收**：`PREPARE` 原样语句不再报错；单测新增/复用一条能覆盖 `upsertPending` 的 SQL 文本断言。
- **影响**：修复后「评分结果 = 待复核」的病历才能建出复核任务。

### A2 ✅ · 批解析 `limit` 触顶后不终止分页（`dd976ec` 引入的取数回归）

- **位置**：`java-backend/src/main/java/com/tcm/ehr/service/impl/NlpBatchServiceImpl.java:861-869`（`processPage`）+ `:765-771`（`runByFilter` 调用处）
- **证据**：`processPage` 在 `remain <= 0` 时 `return false`，而调用方把 `false` 理解为「未取消」⇒ `while(true)` 继续翻页，只在空页 / 不满一页时才 break。改造前是循环内 `if (processed[0] >= limit) return false;` 直接退出（`git show dd976ec` 确认该行被删）。
- **改法**：让 `processPage` 能区分「取消」与「已达上限」。改为返回三态 `enum PageOutcome { CONTINUE, CANCELED, LIMIT_REACHED }`；
  两个调用点同步改：`runByFilter:765`（`CANCELED` → `return true`；`LIMIT_REACHED` → `return false`）、`runByIds:827`（传 `Integer.MAX_VALUE`，`remain` 恒 > 0，只处理 `CANCELED`）。
- **验收**：集成测试 `NlpBatchIntegrationTest.filterTaskStopsPagingOnceTotalIsReached` —— 造 450 条（> `PAGE_SIZE=200`）、任务 `total=10`，断言 `recordMapper.selectList` **恰好 2 次**（第 1 页取 200 条并处理 10 条 → `CONTINUE`；第 2 页一进来即 `LIMIT_REACHED` → 收尾），且 `done=success=10`（**处理条数不得变化**）。反证：把 `remain<=0` 的分支改回 `CONTINUE`（等价旧行为）后该断言报 `Wanted 2 times but was 3 times`。
- **口径澄清（原计划此处写错，执行时更正）**：传进 `processPage` 的 `limit` **不是** DTO 的 `limit`，而是**任务行上的 `total`**（`runByFilter:738` `int limit = t.getTotal()`）。`NlpBatchDTO.limit` 的「空或 0 = 不限」在 `submit` 里已折算成 `total = count`（`NlpBatchServiceImpl:353`），所以 `limit=0` **不是**「一条都不处理」。
  真正触顶的场景是 `total < 匹配数`（如 DTO `limit=10`、匹配 450 条）；此时 `done/total/success` 与旧实现**完全一致**，**唯一可观测差异是取数次数**（旧实现会一直翻到匹配集末尾：40k 条 + limit=1000 时约 200 次 vs 6 次）。另：`PAGE_SIZE` 是 **200**，不是 1000。

### A5 ✅ · `submitIds` 缺事务，与注释不符

- **位置**：`java-backend/src/main/java/com/tcm/ehr/service/impl/NlpBatchServiceImpl.java:418`（方法）、`:453`（注释）、`:447`（任务 insert）、`:469`（明细批插）
- **证据**：方法无 `@Transactional`；唯一调用方 `RecordServiceImpl.java:109 importRecords` 也无事务（全文件仅 `:424`/`:460` 有）。注释却写「与任务插入同一事务」。
- **改法**：给 `submitIds` 加 `@Transactional(rollbackFor = Exception.class)`。`BatchInsert` 的类注释已声明「事务内 commit 是空操作」，故明细批插会正确并入本事务。
- **验收**：新增/复用断言——`TransactionAnnotationTest` 补一条对 `submitIds` 的断言（现有测试只断言了 `submit`）。
- **影响**：修复后明细插入失败会连任务行一起回滚，不再出现「任务在、items 空」⇒ 退化为全组织扫描。
- **范围已核实**：`:485-487` 确认本方法在插入之后**没有内存投递**（只 `log` + `toVO`），故事务只覆盖两次 DB 写，不会把队列投递卷进事务。

### A8 ✅ · 质控规则保存时不校验正则可编译（收窄范围）

- **位置**：`java-backend/src/main/java/com/tcm/ehr/common/config/QcRuleStore.java:199`（`normalize`）、`:227-229`（format 分支）、`java-backend/src/main/java/com/tcm/ehr/common/utils/QcScorer.java:190-191`
- **证据**：`normalize()` 过滤了非法**一致性**规则，但 format 规则只做 null 兜底，不校验 `expr` 能否编译；落库后由 `QcScorer:190 RegexCache.of(expr)` 逐条执行，非法正则走 `:191` 的 catch **静默放行**（规则静默失效）。
- **改法**：在 `updateFor`（**写路径**，`:123-127`）对 `normalize(next)` 的结果逐条校验：`type=regex` 的 `expr` 必须能 `Pattern.compile`，失败则抛 `IllegalArgumentException`（含规则 label 与原因）→ 全局处理器映射 **400**。
  **刻意不放在 `normalize()`**：`normalize()` 同时被读路径 `parseOrBaseline:109` 调用，放那里会给每次读都加一遍正则编译；而且存量非法规则会在读时被静默丢弃，用户看不到原因。
- **不做**：不引入正则超时 / 回溯上限 —— 「合法但灾难性回溯」的正则编译校验拦不住，要拦得引入 `RE2J` 之类的引擎，属新增依赖与算法替换（与「不允许退化」冲突）。写入者已是管理员 / owner 高信任档。
- **验收**：单测——保存含非法正则的 format 规则时，该条被丢弃且 `warnings()` 含对应文案；合法规则不受影响。

- **验收**：无行为变化（仍返回 0），仅新增日志。

### B2 ✅ · 基础层词典播种未走分布式锁

- **位置**：`java-backend/src/main/java/com/tcm/ehr/common/config/DataInitializationListener.java:109-123`
- **证据**：`seedBaseIfEmpty` 调 `termStore.replace(BASE_ORG, …)` 未加锁；同文件 `:152-163` 的 `reconcileLayer` 走了 `DistLock`。多实例同时启动可能双双播种，一个撞 `uk_org_type_term` 抛异常 ⇒ 该类型整轮被外层 try 跳过。
- **改法**：照搬同文件 `reconcileLayer:154-172` 的写法 —— 锁外先快速判空（`:110-112` 保留，避免每次启动都抢锁），抢到锁后在锁内**重新判空**再 `termStore.replace`；`ConcurrentOperationException` / `ServiceNotReadyException` 按「本次跳过」记 info/warn，不让启动失败。播种版本号用一个长度 1 的数组带出锁外再打日志。
- **验收**：单测——锁拿不到时该类型被跳过且不抛异常。

### B4 ✅ · 停机未等待任务内并行池

- **位置**：`java-backend/src/main/java/com/tcm/ehr/service/impl/NlpBatchServiceImpl.java:203-227`（`shutdown`）、`:886-891`（`recordPool.submit`）
- **证据**：`shutdown()` 只对 `workers` 做 `awaitTermination(5s)`，未等 `recordPool`；`recordPool` 置 STOP 后 `processPage` 的 `submit` 会抛未捕获的 `RejectedExecutionException` ⇒ 冒到 `runTask` 的 catch ⇒ 任务落 `FAILED`（设计意图是 `INTERRUPTED`）。
- **改法**：① `shutdown()` 对 `recordPool` 也 `awaitTermination`；② `processPage` 的提交包 `try/catch (RejectedExecutionException)`，视为「被中断」返回取消态，由 `endStatus` 落 `INTERRUPTED`。
- **验收**：单测——池已 shutdown 时 `processPage` 不抛异常且返回取消态。

### B6 ✅ · 配置保存的 check-then-act 并发撞主键

- **位置**：`java-backend/src/main/java/com/tcm/ehr/common/config/LlmConfigStore.java:126-137`、`java-backend/src/main/java/com/tcm/ehr/common/config/QcRuleStore.java:128-145`
- **改法**：`selectById` 为 null 时 `insert` 包 `try/catch (DuplicateKeyException)`，撞键则改为 `updateById` 重试一次。
- **验收**：单测——insert 抛 `DuplicateKeyException` 时走 update 分支且不向上抛。

### B8 ✅ · 批解析面板的轮询响应竞态

- **位置**：`frontend/src/components/NlpBatchPanel.vue:245-264`（`poll`）
- **证据**：`poll()` 开头取 `const id = activeTask.value?.id`，`await` 回来后**无条件** `activeTask.value = res.data`，不校验该 id 是否仍是当前任务。切换任务（`viewTask`）或某次请求超过 2s 时，旧响应会覆盖新任务 / 把进度显示回退。
- **改法**：回包前校验 `activeTask.value?.id === id`，不等则丢弃该响应（与 `composables/usePagedList.js` 的取号丢弃范式同构）。
- **验收**：无自动化测试；人工核对——连续点击两条任务，界面始终显示最后点的那条。

| 词典导入的解析期行数闸门（原 B3） | `DictionaryServiceImpl.java:459-533` → `:323` | 现在 `rows` 全量累积后才判 `entries.size() > MAX_ROWS`，高压缩 xlsx 理论上可先 OOM。**但任何「按行数前置拒绝」的改法都会引入误拒**：`entries` 是「现有词典 ∪ 新条目」去重后的结果，行数超限不等于结果超限（重导同一份大文件时行数可达 6 万而合并后仍 ≤ 5 万，今天能成功、加闸门后会失败）。**唯一零误拒的修法是「边解析边合并」**（把 merge 提前进解析循环，用 `merged.size()` 判），属结构性重构。当前 OOM 需构造高压缩比文件，且写入者已是管理员 / 被授权成员高信任档 ⇒ 不做，登记为已知风险。 |

## 六、已拍板项（决策记录）

### D1 · 成员管理接口与「管理员全通」的口径冲突 → **已定案：只有组长（owner），方向二**

- **定案**：用户 2026-10-12 先答「管理员和组长都能用」，复核市面口径后改判 —— **走方向二（只改文档、零代码）**，落点见 **§四 C10**。
- **改判依据**：
  1. **形态决定模型**。一套系统 = 一家公司的单一租户产品（钉钉 / 企业微信 / 飞书），「管理员」就是公司 IT 管理员，管全员是天然；而「一套系统 = 很多个自治单元」的多租户形态（GitHub Org、Atlassian / Jira），通行分层是「系统管理员 → 租户管理员 → 租户用户」—— 平台管理员管**组织生命周期**，组织内成员归 **Organization Owner**。本项目属后者。
  2. **代码是有意为之**，不是漏写：`OrgServiceImpl.java:694-696` javadoc 明写「管理员不在此放行：管理员的兜底入口是 reassign-owner」。
  3. **文档自身已判过**：`docs/角色与权限矩阵.md:81` 声明端点半表优先，`:64` 端点半表就是「所有者（本组织）×6」⇒ 按自身优先级，错的是功能矩阵 `:47/:48` 与规则 `:56`。
  4. **零行为变更**，天然满足「不允许退化」；改代码则会把管理员对 6 个端点由 403 变成放行。
- **弃选方向一（改代码）的理由**：仅有的收益是「管理员少走两步」，代价是把平台管理员与租户所有者的边界打穿，且需要连带改 `OrgRoleInterceptor` + `requireOwnOrg`（6 个调用点）+ openapi 标注 + 权限矩阵，改动面远大于收益。

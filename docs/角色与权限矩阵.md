角色定义：

| 角色 | 来源 | 说明 |
|---|---|---|
| 管理员 `admin` | `users.role='管理员'` | 全局，所有功能可用 |
| 所有者 `owner` | `organization_members.role='owner'` | 组织级最高权限；自助创建者自动为 owner |
| 被授权成员 `member + 授权` | `organization_members` 两个开关 | 两个开关**均已生效**：`can_write_qc_rules`（质控规则写）· `can_write_dictionary`（词典写，`DictionaryController.requireDictWrite()` 消费，见 2026-10-05 更新说明） |
| 普通成员 `member` | `organization_members.role='member'` | 本组织内可用，可提交词典提案，无管理与增配权 |
| 未加入组织 | 无 `organization_members` 记录 | 仅引导页；无人员池实体 |

> **第 20–22 行按 Git 工作流同构**：词典的写操作分三级 —— 提案提交/编辑自己 ≈ 开 PR（登录即可）；提案审核合并/归档回滚 ≈ merge 权限（所有者）；基线导入/重建索引 ≈ 直接改主线（仅管理员）。`can_write_dictionary` 授权位本意是「协作者写权限」（本组织词典可写、**基础层仍不可**）—— 该位**已由 `DictionaryController.requireDictWrite()` 消费**（2026-10-05 核实），故被授权成员在第 22b / 22c 行可用；第 22 行（基础层）仍**仅管理员**：这是「一个人改所有人的词库」与「协作者改自己组织词库」的分界。

判定规则：① 管理员不受组织限制，第 1–27 项全通；② 数据类读写取 `RequestUtils.currentOrgId()`，后台任务取任务快照 `org_id`（fail-closed）；③ 写权限校验顺序 `admin` → `owner` → `member && 对应开关` → 403；④ 授权位 = 两个布尔列，**均已消费**（`can_write_qc_rules` 质控规则写；`can_write_dictionary` 词典写，含组织层导入 `target=org`；基础层 `target=base` 始终仅管理员）；⑤ 未加入组织仅第 23、27 项可用。

> ✅ **第 25 / 26 项的服务端校验缺口已修（2026-10-05）**：`RequireOrgRole` 增加必填的 `pathVar`（路径里没有机构 id 时写哨兵 `NO_PATH_VAR`），拦截器按声明取变量、**取不到即拒绝**（不再「取不到就跳过」）；`OrgServiceImpl` 六个 owner 方法补 `requireOwnOrg` 兜底。原缺陷是拦截器写死取 `orgId`、而六个路由的变量都叫 `{id}`，跨组校验自上线起从未执行。（该缺陷原登记在已完结并删除的《数据流转问题与修复清单》A2 项，此处保留结论。）

### 1.3 六个必须一起修的交叉点

只修一半后面要改两遍，中间态更易出错。

1. **所有 DDL 收进同一个 migration**：原本散在六处，全部进 `data/migration-03-organizations.sql`，一次停服、一次正反向演练。
2. **配置类「DB 为准 + 版本号失效」三合一**：`LlmConfigStore` / `QcRuleStore` / 词典服务三个进程内单例，随「词典组织级、规则组织级、LLM 每用户」一次改，否则之后返工。
3. **批任务四个问题在同一对文件里**：`NlpBatchServiceImpl` / `QcBatchServiceImpl` 同时承载 `@PostConstruct` 无兜底、查表防重 check-then-act、NLP 提交无防重、取消位与记录 ID 集合内存态。
4. **复核任务一致性是同一根因**：`processOne` 无事务 · `upsertReviewTask` check-then-act · `review_tasks` 无唯一键，三者同链。
5. **权限口径四方冲突一次定完**：openapi 全局约定 `:9` · 端点标注 · 代码注解 · `开发指南与待办.md` 决策记录，必须同批对齐（批次 1）。三方一致性脚本只比端点标注，**照不出全局约定，改完须人工核对**。
6. **词典文件非原子写由批次 8 消灭**：`DictionaryFileServiceImpl:123/176` 的覆盖写随「入库」自然消失，不要单独修。

**目标** 把 LLM 每用户、词典组织级入库、质控规则组织级三个配置模块一次性改成「DB 为准 + 版本号失效」。

**设计要点**

**统一原则** 三个 store 一律「DB 为准 + 版本号失效」：本地缓存带 `version`，取用前比对 DB 版本戳，不一致即回源。缓存是加速，不是权威。三处「版本比对 + 回源」应抽**同一实现**（基类或工具）；缓存须**有界**（按 userId/orgId 上限或 LRU），避免长期运行内存无界增长。

- **LLM 每用户**：`LlmConfigStore`（全局单例 `:31-127`）/ `LlmClient`（单 `ChatClient`）→ 按 `currentUserId()` 解析 `user_llm_config`，有界缓存 + 每用户 `ChatClient`。无请求上下文或用户未配置 → 回退系统默认（`application.yml` 的 `llm.*` 基线）。密钥 AES-256-GCM：随机 12B IV，存 `Base64(IV ‖ ciphertext ‖ tag)`；密钥来源环境变量 `TCM_LLM_ENC_KEY`（32B Base64）→ `llm.crypto-key` → 皆缺则启动告警并按只读降级；解密仅服务端内部；`GET /api/llm/config` 返回掩码 `apiKeyMasked`；`PUT` 传空/掩码 = 保留原密钥，传新值 = 覆盖；仅作用 `currentUserId()`，管理员无权查他人密钥；提供重加密脚本。
- **词典组织级 + 入库**：现网 `data/dictionaries/*.json`（`DictionaryFileServiceImpl:43`）+ 全局 `currentVersion()`（`:277`）→ DB 表 + 基础层（`org_id = ''`，只读继承）+ 组织层叠加。`currentVersion(orgId)`；`EsTermNormalizer`/`EntityNormalizer` 的 `normalize`/`scan` 加 `orgId` 参数（请求线程取 `currentOrgId()`，批量取快照）；ES `term_{type}` 加 `org_id` 字段；写门槛 admin/owner/`can_write_dictionary`；导入/回滚按 `org_id` 作用域；导入格式仅 Excel/CSV/JSON。迁移：5 个 JSON → 基础层（`dictionary_versions` 写 `version`、`indexed_version` 留 NULL → 首次启动触发重建）；文件保留为模板下载。
  - **版本戳**：内容版本落 `dictionary_versions(org_id,type,version)`，启动按 `(type,org)` 逐条比对；`_meta.version` 降级为索引结构/mapping 版本（只有改 mapping 才递增）。
  - **重建方式**：按组织增量重建 —— `delete_by_query(term, type, org_id)` + `bulk`，不删整个索引；基础层变更（`org_id = ''`）才整索引重建。
- **质控规则组织级**：`QcRuleStore`（全局单例 `:28-208`）+ 可选 `data/qc-rules.json`（不存在）→ `get(orgId)/update(orgId,rules)/reset(orgId)`（带缓存）；请求取 `currentOrgId()`，批量取 `qc_task` 快照；写门槛 admin/owner/`can_write_qc_rules`；无记录回退 `QcRuleSet.defaults()`。

**一致性与对账**（DB 是唯一权威，ES 是可丢弃、可重放的派生索引，只走单向 `DB → ES`）。漂移判定落在 `dictionary_versions.version` / `indexed_version`：

| 步骤 | 动作 |
|---|---|
| 1 | 导入写 `dictionary_terms`（单事务），提交后算新内容 MD5 → 写 `version`（`indexed_version` 保持旧值） |
| 2 | 重建该 `(type, org_id)` 的 ES 词条（`delete_by_query` + `bulk`） |
| 3 | 成功 → 写 `indexed_version = version`、`indexed_at = now()`；失败 → 不动 `indexed_version`，返回 5xx，行上留「待重建」 |
| 4 | 启动对账：`DataInitializationListener` 扫 `WHERE indexed_version IS NULL OR indexed_version <> version` → 逐条重建 |
| 5 | 手动修复：`POST /api/dictionary/reindex`（仅管理员），重放全量或指定 `(type, org)` |

> **规模提示**：`dictionary_versions` 行数有限，但启动对账的 `WHERE indexed_version <> version` 走不到主键；建议为 `indexed_version` 建索引、或对启动重建**分批限速**，避免拖慢启动。

三条硬约束：① ES 挂了不许查 DB 兜底（仍 `TermIndexUnavailableException` → 503 + `code=1010`）；② 同 `(type, org_id)` 导入/重建必须串行（`SELECT … FOR UPDATE` 或应用级锁），跨组织不互斥；③ 不接受「只写日志不标记」，重建失败必须体现在 `indexed_version` 上。

### 批次 16 · 多实例（最后）

**目标** 让防重、取消、配置改动在多实例部署下真正生效。

**范围与边界** 做：Redisson 分布式锁、RabbitMQ 异步、调参、记录 ID 集合落库。不做：不改业务语义（正确性仍由 DB 唯一键 + 事务承担，锁只降冲突概率）。

**前置** 全部批次 **风险** 高（架构级变更）

**设计要点**

- **分布式锁 → Redisson `RLock`**：选它而非裸 `SETNX`（可重入 · 看门狗续期 · 按 key 精确互斥）。约束：① Redis 由「启动探活」变硬依赖 ⇒ 必须定降级策略，绝不允许「锁拿不到就放行」；② 锁粒度按业务 key（`dict:{type}:{org}`、`qc:batch:{org}`），不用全局单键；③ 锁不承担状态正确性。
- **异步 → RabbitMQ**：DB 是任务状态唯一权威，MQ 只做唤醒/分发，消息体只放 `taskId`；消费者幂等；队列有界 + DLQ，拒绝策略不能静默丢弃；不引入「MQ 状态 + DB 状态」双权威。
- **调参清单**：Hikari（现 20）· NLP 多进程 + 限流（`start-all.bat:34` 单进程）· 批任务并发度（现固定 2）· 导入异步化（`RecordServiceImpl:131,156-199` 仍同步）· 任务/日志列表 `LIMIT` · 记录 ID 集合落库（建 `nlp_task_items`）· `LlmClient.java:235` 重建锁**全局串行**（多实例下与 Redisson 锁一起定粒度）。

> `LlmClient:235` 的双重检查写法本身正确，本项只改**锁的粒度**，不是缺陷。

**工作项**

| 2 | 引入 RabbitMQ 做唤醒/分发，消息体只放 `taskId`，消费者幂等，队列有界 + DLQ | 工作项 1 锁粒度已定 |

### A.4 数据模型目标清单

- `organizations`：`id`、`code`(UNIQUE)、`name`、`purpose`、`owner_user_id`（冗余展示，权威以 `organization_members.role=owner`）、`status`（`active/stopped/archived`）、`create_time`。
- `organization_members`：`id`、`org_id`、`user_id`、`role`（owner/member）、`can_write_dictionary`、`can_write_qc_rules`、`is_primary`、`create_time`；保留 `UNIQUE(org_id,user_id)`、`INDEX(user_id,is_primary)`、外键。
- 现行 `research_groups` / `group_members` 已存在（`database-init.sql:28-54`）。现行 `research_groups.status` 默认值仍是 `'pending'`、注释仍是 `'pending/active/rejected/stopped'`（`:33`），必须改掉；四列 `applied_by`/`reviewed_by`/`reviewed_at`/`reject_reason`（`:34-37`）「取消审核」后无写入方，删。`database-init.sql` 是新库建表用，存量库靠 `migration-03`。
- `users.status` 只留 `active`/`disabled`。现状：`User` 三类常量，注册写 `pending`（`AuthServiceImpl:93`）、登录只拒 `disabled`（`:146`），全仓无 `pending → active` 路径，`STATUS_ACTIVE` 是死常量；存量已由 `migration-02` 把 `admin` / `auditor` 刷为 `active`，此后新注册账号仍停在 `pending`。
- `users.has_pending_group` 列保留（DROP 影响存量库与回滚），代码侧不再读写。
- 归属列：五表 `group_id` → `org_id`，索引名 `idx_*_group` → `idx_*_org`。注意 `operation_log` 没有 `idx_*_group`（`database-init.sql:127` 仍是 `idx_operator`，另有 `idx_log_time`/`idx_action`），它新建 `idx_group_time`/`idx_operator_time`。
- 配置模块五张新表完整 DDL 见 批次 4。

### B.3 最易漏

1. `Dashboard.vue` 的 `userStore.role` 数据分支（不是 UI 门禁），只改界面会漏。
2. openapi 是 BOM + LF（0 个 CR 字节），按 CRLF 写补丁会让整份文件 diff 炸开。
3. 改名时保持已实现的组维度行为：每请求解析（`is_primary=1` + `status='active'`）、fail-closed（`NO_GROUP_SENTINEL`）、`RecordFilter` 调用点与 Mapper 形参 —— 改的只是 `group`→`org` 字面名，语义不动。
4. 删 `tools/convert-standard-pdf.py` 时必须同批改 `DictionaryImportTest` 里 `contains("convert-standard-pdf.py")` 的断言；若存在登记该脚本用法的技能文档，一并同步。
5. 三方一致性脚本只比端点标注，照不出 openapi 全局约定 `:9`，每次改完须人工核对。
6. 批次 10 的 `str(Object)` 改名是**全计划唯一「改名即动行为」**：调用点必须逐处核对，不能 IDE 全局替换。
7. 批次 11「删 `font-weight: normal` 反写」必须与「改基础字重」同批，只删一边会让那 14 处突然变粗。
8. 批次 12 的 8 处 TDZ 调序是**改了就 `ReferenceError`** 的类型：调完必须逐页点一遍。
9. 批次 13 四处口径单源要**逐条做**，不要再当笼统项开工。
10. 批次 14 是**只测不改**的批：缺陷回填对应批次，不在本批顺手修。

### B.4 风险与缓解（全局）

| 风险 | 缓解 |
|---|---|
| 改名遗漏某条查询路径的组织过滤 → 越权 | 现有 `RecordIsolationTest` 已覆盖；改名时保持 `RecordFilter` 组维度不变 |
| 存量 `group_id` 语义改名 → 数据不可见 | `org_id` 迁移幂等；代码对空组织降级为「无数据」 |
| 管理员开关 `false` 后看不到任何数据 | A.5；需提前告知 |
| 自助建组织被滥用 | 批次 6 的防滥用（创建配额、名称校验） |
| 所有者离职 → 孤儿组织 | `leave`/移交前强制指定继任者；管理员改派接口见 B.1 #2 |
| 组织停用后成员数据 | 数据保留不删；停用只挡登录 |
| DB RENAME 涉及多表外键与存量归集 | 事务 + 正/反向脚本 + 先备份；与批次 5 同窗口发布 |
| ES 加 `org_id` 需全量重建 | 先迁移基础层再重建；组织差异可异步重算 |
| 组织级自助导入 → 跨组织重建窗口 | 按组织增量重建（只删写该 `(type, org_id)` 词条）⇒ 跨组织不再互相中断；基础层变更仍整索引重建（仅管理员，频率低）；UI 明示「重建中」并禁止并发导入 |
| 版本戳无处存 | 内容版本落 DB `dictionary_versions`，启动按 `(type, org)` 比对；`_meta.version` 降级为索引结构版本 |
| DB 与 ES 漂移 | 靠 `version` vs `indexed_version` 对账；重建失败不写 `indexed_version`；启动扫不一致项重建；`POST /api/dictionary/reindex` 手动重放；同 `(type, org)` 导入串行；ES 挂了不许查 DB 兜底 |
| 多实例落地时内存态静默失效 | §3.4 四条现在就要遵守；记录 ID 集合落库留最后，但须注释标明单实例前提 |
| 加密引入服务端密钥运维面 | 缺省降级不阻塞启动；提供重加密脚本 |
| openapi 按 CRLF 改 → 整份 diff 炸开 | 明确 BOM + LF，`python -X utf8` 读写 |
| 词典越权写入 → 污染其他组织归一结果 | 写门槛走 `admin` / `owner` / 授权位三档（`@RequireOrgRole` + 授权位），`DictionaryController` 的 `import` / `rollback` / `convert` 逐个核对注解 | 8 |
| 存量库执行 migration 不可逆 | 幂等脚本 + 正/反向覆盖 + `mysqldump` 备份 + 演练环境先跑（批次 4） |
| 密钥丢失 / 轮换 → 用户 LLM 配置不可解密 | 解密失败按「需重填」处理且不阻塞启动；提供重加密脚本（批次 8） |

| 每用户 LLM 的 `ChatClient` 缓存内存增长 | 有界缓存 + LRU（批次 8） |

**三个必须记住的技术口径**

1. **ES 负责召回，Java 负责判定**。`EsTermIndexServiceImpl.search` 只召回候选，三级判定（精确 / 包含 / Dice≥0.8）在 `EsTermNormalizer`。**ES 是归一的唯一权威**：未召回即未命中；ES 不可用抛 `TermIndexUnavailableException` → HTTP 503 + code=1010，**不静默降级**（否则会把"索引挂了"误报成"词典没这个词"）。
2. **判定地基 = 规则引擎**。评分 / 分级 / 归一都不依赖 LLM；LLM 只做叙述加工与建议，失败即降级。
3. **实体类型固定 9 类单一来源**（`EntityTypes`），其中 5 类有词典。质控评分核心要素 **6 项**：症状 / 疾病 / 证候 / 舌象 / 脉象 / 中药；治法、方剂不参与评分。

**配置注意**

- `spring.ai.model.*` 六项统一置 `none`：自动装配默认值是 `openai`，不关掉会在缺 api-key 时急切建 Bean 导致启动失败。模型由 `LlmClient` 按需自建。
- `application.yml` 路径类配置含绝对路径（`dictionary.dir`、`log.operation-file`），**换机需改**。
- 三个开关：`nlp.enabled`（默认 true，开前先起 :8001）· `llm.enabled`（默认 false，仅启动基线，运行时由「导入 LLM」覆盖）· `llm.convert-enabled`（默认 true，静态 `@Value`，改完要重启）。
- `llm.api-key` **不落盘**（`data/llm-config.json` 只存非密钥字段），每次重启需重填。

## 二、开发规范

### 协作铁律（最高优先级，优先于本文其余全部条款）

- **未经用户明确指示，不得修改任何代码、配置或文档。**
- 审查 / 扫描 / 分析 / 核实 / 出计划一律**只读**；发现问题**写进《待办》或报告，不擅自修复**。
- 只有用户明确说「改」「修」「执行」「做」等指令时，才动手；且**只改被点名的范围**，不顺手扩大。
- 一次只做用户当前要求的事；**做完停下等下一步指示**，不连续推进未获批准的批次。
- 需要判断时先**问**，不替用户做决定；不确定就停下来问。
- 例外：用户显式授权的当次任务（例如「把 X 写到规范里」）即为授权范围，照做即可。

### 后端

- **分层**：`common`（config / domain / exception / interceptors / utils）+ `controller` + `domain`（dto / po / vo）+ `mapper` + `service`。命名 `I*Service` 接口 + `*ServiceImpl` 实现；绑表服务 `extends ServiceImpl<Mapper,Po>`。
- **响应与异常**：统一 `Result{code,msg,data}`（文件流接口除外）；业务异常由 `GlobalExceptionHandler` 统一出口，**Controller 禁止 try-catch 兜错**。
- **范围查询**：数据域（角色行级权限）与用户筛选**统一走 `RecordFilter`**，**禁止在业务方法中手写 where**。执行顺序固化：**先数据域、后用户筛选，取交集**。
- **留痕**：清洗 / 导出 / 导入 / 回滚 / 复核等关键操作调 `OperationLogger`，写 `logs/operation.log` 并入库 `operation_log`（双写，不做强一致）。
- **业务规则单源**：复核时限、评分口径等由后端一处生成，前端只读展示、不重算。
- **LLM 提示词归档**：统一固化在 `LlmClient`，不散落到各接口。
- **术语**（违反即问题）：
  - **禁止出现「治理」字眼**；状态词统一「**待清洗／已清洗**」。
  - 英文标识**不改**：`GovernanceController` / `IGovernanceService` / `governed` 等保留。
- **可读性**：优先靠合理命名与代码结构自解释；多阶段方法体写 `// 1. // 2.` 步骤注释，关键决策处写「为什么」。

### 前端

- **主题**：中式变量 `--ink/--paper/--line/--ochre/--danger`（见 `theme.css`），不加渐变 / emoji / 骨架滚动动画。
- **组件复用**：`PanelCard` / `StatCard` / `BarList` / `TermInput` / `RangeFilter` / `StructuredDataCard` —— 优先复用不新建。
- **请求**：统一走 `utils/request`（响应拦截 + blob 下载 `utils/download`）；接口封装于 `api/*.js`。
- **UI 风格**：**相同视觉层级的字体大小一致**；颜色 / 间距 / 圆角用全局变量，禁大量硬编码。
- **预览桩**：仅用于审核预览，**不上运行页**；数据结构须与 openapi VO 完全对齐，仅填假值、不增删字段。
- **禁魔法值**：固定常量抽离管理；兜底状态（加载中 / 空数据 / 异常）展示方案全局统一。

### 契约纪律

- 新增 / 变更接口：**先更新 openapi.yaml，再实现代码**。
- **角色标注（强制）**：每个接口 `description` 首部必须带 `【权限：…】`，四档取值：`仅管理员` / `登录即可` / `管理员 / 审核员` / `公开`。
- 错误码查 openapi 附录 B；前置校验统一 `IllegalArgumentException` → HTTP 400。

### git 工作流

- 每线独立 commit、可独立回滚；格式 `feat|fix|docs|refactor|chore(scope): 描述`。
- 分支模型：`main` + `XXJ` / `YC` / `ZRC`；**MR → 评审 + 验收 → merge**，main 保持随时可演示。
- 推送需 Steam++（github.com:443 直连会被 reset）。
- 合 main 前执行 `grep -rn "graph-preview|静态假数据" src/`，禁止预览桩数据文件合入。

| 层 | 资产 | 用途 |
|---|---|---|
| 后端 | `GlobalExceptionHandler` / `Result` | 统一异常与响应 |

| 后端 | `EsTermNormalizer` / `EntityTypes` | 三级归一 / 实体类型单一来源 |

### 并发防护约定

- **前提**：单机单实例部署，无分布式一致性问题；并发只需防"同一人连点 / 重复提交"。
- **任务防重**：全库写操作（质控重算 / 数据清洗）用 Redis `SETNX tcm:task:{type} NX EX 900s`；前端按钮 disabled + loading 先拦一道，后端锁兜底。
- **数据层兜底**：`review_tasks` 幂等 upsert（SQL 语义）保证重复执行不重复建任务 —— **不依赖锁保证状态正确**。
- **词典文件**：导入 / 回滚 / 备份方法加 `synchronized`，避免并发覆盖词典 JSON 与 ES 索引重建冲突。
- **已知局限**：`tcm:task:batch` 是**全局单键**，任意管理员的批量重算会让其他人排队；TTL 900s 固定，大批量可能超时导致并发双跑。见待办。

### 角色鉴权约定

| 角色 | 菜单 | 接口权限 |
|---|---|---|
| 管理员 | 8 项全量 | 全部 |
| 审核员 | 首页看板 + 人工复核 | 病历读取（数据域限 `grade='待复核'`）、复核 |

- 机制：`@RequireRole` + `RoleInterceptor`（未过 → 403）；前端路由 `meta.roles` + 守卫，菜单按登录角色**动态渲染**。
- 数据域：审核员 = `grade='待复核'`，管理员 = 全库；`/api/ai/*` 与病历读取同域过滤。
- **新增接口默认**：写操作「仅管理员」，只读「登录即可」，复核专接口「双角色」。

## 四、架构取舍与已定方案

**已定案（不再讨论）**

| 项 | 结论 |
|---|---|
| 隔离归档区形态 | 以 `records.grade='无效'` + `status='invalid'` 落地，**不单独建表或页面**；导出仅取 `grade='合格'`，隔离数据天然排除 |
| 质控图谱需求口径 | 属"质控结论的可解释性呈现"，不涉及临床诊疗决策，**不做临床数据可视化**；力导向关系图已弃，只留表格 |
| 归一唯一权威 | **ES**，无内存兜底（2026-09-23 起） |
| 批量任务上限 | 「全部（默认）/ 指定前 N 条」；超限拒绝提交（400） |
| 批量操作日志 | 各类操作各记 **1 条汇总**（现状，非缺陷） |
| 方剂词典 | **保留**（源数据无方剂列，但 `formulas.json` 仍被归一 / 结构化 / 复核消费） |
| 术语词典页 UI | **不改**（用户决定保持与其它页一致） |
| 部署 | 演示走 vite dev（3000），**不采用 nginx 线上部署** |

**明确不做的**

- 批量重算**不做异步任务**（同步执行 + 上限 3 万）。
- 图谱**不预计算 / 不缓存**（≤3 万 → SQL GROUP BY + LIMIT）。
- 事务**不引入行锁 / 乐观锁 / 分布式锁**（单机单用户，幂等由 SQL 兜底）。

**性能特征**：Python CPU 推理单条约数百毫秒（须批量送推理）→ 3 万条**按小时计（2~4 小时）**，属离线批处理。

## 五、审查 Playbook

> 用途：把下面两段提示词分别交给 AI（或自动化代理）做新一轮审查。**默认只读。**

### 5.1 代码审查（技术视角）

**角色**：资深全栈代码审查者（Java 后端 + Vue 前端 + Python + 数据/搜索）。目标：**找出真实缺陷与风险，而不是夸奖**。结论必须有代码位置与证据。

**如何审查（必须实际动手）**

1. **编译/构建**：后端 `mvn -o compile`（`JAVA_HOME=F:\jdk24`）；前端 `npm run build`。记录失败与警告。
2. **静态阅读**：Controller → Service/Impl → Mapper/PO → Util/Config；前端 api → store → view/component。
3. **契约核对**：`openapi.yaml` 的路径/方法/参数/权限标注与各 Controller 逐一对照。
4. **数据流核对**：`NLP 抽取 → 术语归一 → 结构化落库 → 质控评分 → 报表/导出` 全链路一致性。
5. **运行期检查**（可行则做）：启后端到临时端口打关键接口。**不得改数据库 / 配置 / 提交**。

**审查维度**（逐项给结论，"未发现问题"也要说明检查范围）

1. **正确性**：边界、空值、并发、分页上限、事务边界、幂等、外键（`review_tasks`→`records`）、异常吞掉。
2. **安全**：`@RequireRole` 是否覆盖每个敏感接口；越权 / 数据域；密钥是否落盘或泄漏到日志；SQL 注入 / ORM 拼接；文件上传校验。
3. **一致性**：openapi ↔ Controller ↔ 前端 三方签名一致；文档中接口数 / 字段与代码一致；错误码统一。
4. **数据与搜索**：ES / 词典归一是否单一权威（**不得偷偷降级**）；`structured_data`、`qc_results` 解析是否容错。
5. **并发 / 资源**：任务队列、线程池生命周期、取消 / 中断语义、Redis 锁是否释放、连接 / 超时设置。
6. **性能**：N+1、全表扫描、大 JSON、聚合上限是否截断、分页是否强制上限。
7. **前端质量**：未 import 的 Vue API（会整站白屏）、响应拦截错误处理、状态与轮询清理、`v-for` key、内存泄漏。
8. **配置与运维**：`application.yml` 残留无效项、默认值是否安全、路径是否可移植。
9. **可维护性**：重复代码、死代码、硬编码、魔法数、**命名与注释是否与实现一致**。
10. **测试与可验证性**：关键逻辑（评分 / 归一 / 鉴权）是否可验证；给出最小验证命令。

**本仓库已知约定（违反即问题）**

- `openapi.yaml` 是唯一契约；接口增删须同步。
- DB 结构改动只进 `database-init.sql`。
- 术语归一以 **ES 为唯一权威**，无内存兜底。
- 质控规则**可配置**（`data/qc-rules.json`）；实体类型有**固定 9 类单一来源**。
- 评分核心要素 6 项；治法 / 方剂不参与评分。
- 批量解析为后端异步任务（`nlp_task`）。
- 禁止「治理」字眼；状态词「待清洗／已清洗」。
- 范围查询三模块口径一致；相同视觉层级字号一致。

**输出格式**

1. **问题清单**（按级别排序）——每条含：级别（`阻断`/`高`/`中`/`低`）、位置 `文件:行号`、**证据原文**、影响、修复建议（**仅建议，不擅自改**）。
2. **契约一致性核对表**：openapi ↔ Controller ↔ 前端 逐接口对照。
3. **文档与代码一致性**：接口数 / 字段 / 开关默认值。
4. **回归风险与验证清单**：改动后必须重测的点 + 最小命令。
5. **未检查 / 存疑项**：说明原因。

### 5.2 用户视角审查（业务视角）

**角色**：**没有技术背景的医院质控科业务用户**，第一次使用本系统。找出"看不懂、找不到、吓一跳、对不上、点了没反应、数据不一致"的地方。

**检查方式（必须实际动手）**

- 用**浏览器自动化**逐页真实操作：登录、查询、点按钮、填表、上传、切换标签页。
- **每页打开先看浏览器控制台**：记录报错 / 白屏 / 请求 4xx-5xx。
- 关键操作**多角色各做一遍**（管理员、审核员），并**换页往返、刷新**验证状态是否丢失。
- 记录 **HTTP 请求**，确认接口返回与页面显示一致。

**检查维度**

1. **功能正确**：按钮 / 入口是否如其名；"批量删除"是否按所选范围删、"重算"后分级是否变化。
2. **数据一致性**：看板、质控分级、导出、日志之间数字是否对得上；同一事实跨页是否矛盾。
3. **三模块数据流**：解析输出 → 归一 → 质控评分，口径是否一致（词典里没有的词能否归一、一致性规则期望值是否只能从词典选）。
4. **文案与可理解性**：是否有技术术语泄漏（字段名 `symptoms`、正则、`patternList`）；空态 / 错误态是否说清"为什么空、下一步做什么"。
5. **交互与布局**：无谓滚动 / 弹窗套弹窗；页面大小一致；表格 / 卡片错位。
6. **边界与异常**：空数据、超大数（3 万条）、必填缺失、重复导入、**关掉 NLP / ES 再试**。
7. **权限**：审核员看不到 / 进不去的入口是否正确；越权是否被拦并有清晰提示。
8. **评分可解释性**：单份病历的"为什么是这个分、差多少到合格"是否说得清。
9. **归一与标准化**：命中展示（原文 → 标准词）、未命中处理、词典导入 / 回滚可读性。
10. **性能与反馈**：长操作是否有进度 / loading / 防重复。

**重点场景**（至少覆盖）：登录登出 · 首页看板 · 病历数据（含导入、勾选删除、按范围删除）· 结构化解析（单条 / 批量 / 取消 / 上限）· 质控校验（标准卡片 / 重算 / 扣分明细）· 人工复核（含逾期）· 清洗与导出 · 术语词典（5 类 / 导入 / PDF 转换 / 回滚）· 日志审计（筛选 / 导出 / 清理）· AI 助手与 LLM 配置弹窗。

**输出格式**：问题清单（级别 `致命`/`高`/`中`/`低` + 复现步骤 + 期望 vs 实际 + 业务影响）· 数据一致性核对表 · 做得好的地方 · 系统性问题与改进建议 · 未验证 / 存疑项。

### 5.3 共同约束

- **默认只读**：不改代码 / 配置 / 数据库，不提交、不推送、不重启用户服务（除非明确授权）。
- 每条结论必须**可复现**并附证据；不确定标"存疑"。
- 聚焦真实缺陷，**不罗列无关紧要的样式偏好**。
- 用中文输出。

## 二、P0（阻断 / 严重性能问题）

### P0-1 · AI-28 / R14 异步任务状态在进程内，多实例轮询 404

- **问题简述**：`AiAsyncTasks` 登记表为进程内 `ConcurrentHashMap`（`MAX_TASKS=2000`、`RESULT_TTL_SECONDS=600`）。A 实例提交、B 实例轮询 → 404，前端显示「生成失败」。多实例部署下 AI 功能整体不可用。
- **根因**：任务状态无共享存储；登记表与结果只在本 JVM 内。
- **修复方案**：任务状态迁 Redis（`task:ai:{taskId}` Hash，TTL 600s），保留进程内表作一级缓存。接口形态（`AiController.java:48` `/api/ai/async/{kind}`、`:93` `/{taskId}`）不变。
- **验证标准**：起两个实例，A 提交 → B 轮询返回任务状态而非 404；单实例行为与改造前一致。
- **来源**：AI-28、Redis 3.7.2 R14。**（来源报告列为第二批 P2，此处按严重度上提。）**

### P0-2 · R3-③ `StatsCache` 使用 `KEYS` 阻塞命令

- **问题简述**：`StatsCache.java:72` `redis.keys(KEY_PREFIX+scope+":*")` 为 O(N) 全库扫描 + Redis 单线程阻塞，期间所有其它请求（令牌校验、分布式锁）排队。生产禁用级。
- **根因**：失效用「通配删除」而非版本号；key 空间由 `md5(filters)` 决定、无白名单。
- **修复方案**：key 改版本号前缀 `cache:stats:{scope}:v{n}:all:{md5}`，失效改为 `INCR` 版本号（旧 key 自然过期）。**不保留任何 `KEYS` / `SCAN` 删除路径。**
- **验证标准**：`grep -rn "\.keys(" java-backend/src` 零命中；失效后旧 key 不再被读；补一次 10 万键量级的对比计时。
- **来源**：Redis R3-③ / 3.4 硬规则 1。

### P0-3 · A1 / T2 标准化报告同一条 JSON 解析 7 次

- **问题简述**：`StandardizationReportServiceImpl.report()`（`:67`）后七处统计方法各自解析——`byMonth:109`、`coverage:90`、`unmatched:95`、`normalizableRate:161`、`datasetShape:116`、`scoreDistribution:101`、`qcCoverage:163`。同一条 1.13 KB JSON 反序列化 7 次（其中 5 次是同一份 `structured_data`），4 万条 ≈ **28 万次 Jackson 解析**，实际只需约 8 万次。
- **根因**：无请求内中间结构，各统计器独立遍历、独立解析。
- **修复方案**：`report()` 入口**一次遍历、一次解析**，抽扁平中间结构（每条只需 `visitTime / score / grade / manuallyEdited / symptoms{content,sourceText,normLevel} / qc.score`）向下传。**不引入** `Map<recordId, Map<String,Object>>` 请求内解析缓存——那只是把同一份解析结果换个容器多存一遍。
- **验证标准**：解析次数由 7n 降到 n（mapper/打点计数）；4 万条真实数据上报告接口改造前后各计时一次，用实测值替换「省 4–10 s」估算。
- **来源**：Redis A1、算法 T2（同条，交叉引用不重复登记）。

### P0-4 · C1 报告页全表全行加载，无列投影

- **问题简述**：`StandardizationReportServiceImpl.java:358` `recordsInDomain` 走 `selectList`，拉回 `records` 全部列（21 TEXT + 2 JSON + 标量），4 万条约 **45 MB 常驻堆**。
- **根因**：未做列投影。对照：`RecordServiceImpl.searchRecords`（`:476`）与 `StatsServiceImpl.recordsFor`（`:191`）**都已做列投影**。
- **修复方案**：按实际消费投影 `id / visit_time / score / update_time / chief_complaint / self_report / structured_data / qc_results`（8 列）。`present_illness` 等大 TEXT 不需要；**本报告不消费 `pattern` / `department`**，故不投影。**改列必须同步维护 `RecordColumnNameGuardTest` 列名守卫**（该文件已加入守卫的 `RECORD_WRAPPER_FILES`；列名须内联书写、不传数组变量，否则守卫扫不到引号 token）。
- **验证标准**：堆占用 45 MB → 约 12 MB；列名守卫测试通过；报告各项数值与改造前逐项一致。
- **来源**：Redis C1。

### P0-5 · W1 数据清洗在事务内失效缓存

- **问题简述**：`GovernanceServiceImpl.java:87` `@Transactional` 内 `:216` 调 `invalidateStats()`；清洗逐页 UPDATE（未提交）即清缓存 → 并发读 miss 按旧数据现算回填 → 事务提交后缓存持旧值最长 60s。
- **根因**：失效时机在事务提交前，违反 Cache-Aside 规则②「失效必须在事务提交之后」。
- **修复方案**：`:216` 改 `DistLock.afterCommit(StatsCacheInvalidator::invalidateStats)`。无活动事务时立即执行，单测直调路径不受影响。
- **验证标准**：清洗中并发轮询看板，提交后缓存不再持旧值；单测直调路径行为不变。
- **来源**：Redis W1 / 3.5.1。（**事务回滚不是问题**，缺陷纯粹来自「清缓存发生在提交前」。）

### P0-6 · W2 删除病历在事务内失效缓存

- **问题简述**：`RecordServiceImpl.deleteRecords`（`:421` `@Transactional`、`:428` `invalidateStats()`）与 `deleteByFilter`（`:452` `@Transactional(timeout=60)`、`:460` `invalidateStats()`）。并发读窗口内按「删除前旧数据」回填 → 提交后统计着**已删病历**最长 60s。
- **根因**：同 W1。
- **修复方案**：两处改 `DistLock.afterCommit(...)`。
- **验证标准**：删除后立即查看板，数字即时变化。
- **来源**：Redis W2。（其余 6 处调用——`importRecords:213`、`createRecord`、`updateRecord:411`、`ReviewServiceImpl.review`、`QcBatchServiceImpl:433`、`NlpBatchServiceImpl:570`——均不在活动事务内，**不动**。）

### P0-7 · T13 清洗链路逐条调词典元数据 → 4 万条 16 万次 SQL

- **问题简述**：`GovernanceServiceImpl.java:294-295` `stamp` 内逐条调 `effectiveDictVersion` / `effectiveTermCount`，底层（`DictionaryTermStoreImpl.java:349/382`）各查基础层 + 本组织两次库。`CleanDTO` 无上限（空 = 全量），4 万条 → 约 **16 万次 DB 查询**。
- **根因**：元数据未按批记忆化。**关键对照（非推测，项目已修过一次）**：`NlpBatchServiceImpl.java:839-846` javadoc 记录同一问题（3.5 万条口径「十几万次 SQL」）已用 `DictMeta`（`:848`）修掉，`GovernanceServiceImpl` 未修。
- **修复方案**：把 `DictMeta` 提升为可复用组件，`clean()` 进主循环前取一次，循环内复用；`orgId` 一批内恒定，语义不变。
- **验证标准**：4 万条清洗 SQL 条数由 16 万降到个位数（mapper 计数）；清洗结果逐条与改造前一致。
- **来源**：算法 T13。

### P0-8 · T1 导出 CSV 循环内对整实体做 bean→Map 转换

- **问题简述**：`GovernanceServiceImpl.java:630-641`（`:631` 循环体 `objectMapper.convertValue(r, Map.class)`）在 `for (String col)`（`:630`）内，每行做列数次整实体反射转换。4 万行 → 数十万次反射 + 等量临时 Map，比「每行转一次」慢 20 倍以上。
- **根因**：转换位置在列循环内。
- **修复方案**：`convertValue` 提到循环外**每行一次**；更彻底用 `RecordUtil.column(r, col)`（`QcScorer.java:225` 就在用）绕开反射。
- **验证标准**：导出 4 万行耗时与临时对象数下降；CSV 内容与改造前逐字节一致。
- **来源**：算法 T1。

### P0-9 · T16 清洗路径同一 JSON 解析 2 次 + 序列化回环

- **问题简述**：`GovernanceServiceImpl.java:144`（`isValidJson`）与 `:293`（`stamp` 序列化 → 内部解析 → 再序列化）→ 4 万条 ≈ 20 万次 Jackson 往返，与 T13 叠加是清洗性能两个主因。
- **根因**：校验与解析分离；`stamp` 入参被序列化后又解析。
- **修复方案**：`isValidJson` 与解析合并为一次；`stamp` 加「入参已是 Map」重载去掉回环。⚠️ `stamp` 被多处复用（`RecordServiceImpl` / `NlpBatchServiceImpl`），加重载**不改既有签名**。
- **验证标准**：单条清洗 Jackson 往返由 5 次降到 2 次（打点）；清洗结果逐条一致。
- **来源**：算法 T16。**与 P0-7 同链路，一并改、一次验收。**

## 三、P1（重要优化）

### P1-1 · AI-1 LLM 配置解析每请求查 2 次库

- **问题简述**：`LlmClient.java:259`（`getFor`）/`:264`（`versionFor`）→ `LlmConfigStore.java:73-79`/`:128-133`（`:77`/`:132` 各一次 `selectById`）。`:77` 的查询在 `perUser.get(...)`（`:78`）**之前无条件执行**——缓存只省 `merge()`，没省 DB 往返。放大点：`LlmClient.java:126` 降级分支再调一次 `getFor`；技术拒答分支 `isAvailable()`（`:107` → `resolve()` 又 2 次）。
- **根因**：缓存命中判断在 DB 查询之后。
- **修复方案**：`LlmConfigStore` 增加「一次查询同时返回配置与版本」的方法；缓存命中判断提前到 DB 查询之前。
- **验证标准**：改造前后各发 100 次 AI 请求，`user_llm_config` mapper 调用计数下降（每次省 1~3 次）。
- **来源**：AI-1。

### P1-2 · AI-2 `AiAsyncTasks` 线程池队列无界

- **问题简述**：`AiAsyncTasks.java:69` `newFixedThreadPool(4,...)` 内部 `LinkedBlockingQueue` 无界，`submit` 永不拒绝；`MAX_TASKS` 只约束登记表。LLM 单次 20s 超时、池 4 线程时，并发提交 100 个任务有 96 个堆在队列；前端 150s 放弃后后端仍跑完。
- **根因**：未用有界队列 + 拒绝策略。
- **修复方案**：显式 `ThreadPoolExecutor` + 有界队列 + 拒绝策略（拒绝时回 503「AI 繁忙」）。`prune()`（`:148`）在 n≤2000 下可接受，不动。
- **验证标准**：并发压测复现堆积；超限提交返回 503 而非静默排队。
- **来源**：AI-2。

### P1-3 · AI-8 / C3 offset 深翻页退化

- **问题简述**：批解析 `NlpBatchServiceImpl.java:687` `selectPage(new Page<>(pageNo, PAGE_SIZE, false))`（`PAGE_SIZE=200`，`:72`）→ 4 万条 200 页，末页 `LIMIT 39800,200` 需扫过前 39800 行。清洗 `GovernanceServiceImpl.java:96`（`pagedRecords`）/`:221`（`CLEAN_PAGE_SIZE=1000`）/`:232`（定义）同形态，累计扫描量约为实际行数的 **20 倍**。
- **根因**：offset 分页。对照：`QcServiceImpl.deductionStats` 已用 keyset（实测 4.9s → 216ms，22×）。
- **修复方案**：两侧都复用 `RecordKeyset.anchorAfter(wrapper, cursorVt, cursorId)` 锚 `(visit_time DESC, id ASC)`；需回归两个 `NlpBatch` 测试。
- **验证标准**：扫描行数由约 80 万降到 4 万（约 10–20×）；分页结果集与改造前一致。
- **来源**：AI-8、Redis C3（同源，C3 覆盖清洗侧、AI-8 覆盖批解析侧）。

### P1-4 · AI-9 逐条 `UPDATE records`，无批处理

- **问题简述**：`NlpBatchServiceImpl.java:834` `processOne` 逐条调 `updateStructuredData`；`runTask` 未标 `@Transactional`，每条各自 autocommit → 4 万条 = 4 万次提交。
- **根因**：无批处理与事务边界。
- **修复方案**：`rewriteBatchedStatements=true` + 每 500 条一次批量更新（MyBatis-Plus `updateBatchById`），取消逐条 autocommit。
- **验证标准**：4 万条批解析总耗时与 SQL 条数下降（开启 `rewriteBatchedStatements` 前后各跑一次）；解析结果一致。
- **来源**：AI-9。

### P1-5 · AI-12 Python `extract` 同步 def，推理无并发上限

- **问题简述**：`python-nlp/main.py:293-294`（`@app.post("/api/nlp/extract")` + `def extract`）非 `async def` → FastAPI 投进 anyio 线程池（默认上限 40）；torch 推理 CPU 密集，多实例或直压 8001 时 40 线程同时跑 → GIL 争用、内存翻倍。
- **根因**：未限并发、未限 torch 线程数。
- **修复方案**：`threading.Semaphore` 限并发；`torch.set_num_threads(...)` 避免 oversubscribe。
- **验证标准**：直压 8001 端口，Python 进程 RSS 峰值受控、P95 不劣化。
- **来源**：AI-12。

### P1-6 · AI-16 `runAiAsync` 固定 1s 轮询

- **问题简述**：`frontend/src/api/ai.js:32`（`POLL_INTERVAL_MS=1000`）、`:35`（`POLL_TIMEOUT_MS=150000`）、`:45`（`runAiAsync`）。一次 30s 生成即 30 次轮询；首次 poll 后必睡 1000ms，**LLM 默认关闭时后端毫秒级返回、前端却至少多等约 1s**。
- **根因**：固定间隔轮询。
- **修复方案**：退避轮询 **100ms → 200ms → 500ms → 1s 封顶**。**不引入 SSE / 长轮询**——前端已统一走轮询，新增推送通道要同时改 `AiAsyncTasks` 与两处批量面板，收益不抵改动面。
- **验证标准**：慢任务请求数降 3–5×；快任务端到端延迟回到毫秒级（浏览器 Network 计数 + 时间戳差）。
- **来源**：AI-16。

### P1-7 · AI-18 `NlpController.extract` 同步阻塞

- **问题简述**：`NlpController.java:71`（`nlpClient.extract`）、`:89`（`entityNormalizer.normalize`）同步完成「转发 Python（`nlp.timeout=30000ms`）+ ES 归一」才返回，Tomcat 请求线程被占住；前端 `api/nlp.js:5` 超时放宽到 60s。对照：`AiController` 已「提交拿任务号 + 轮询」（`:48`），NLP 单条未跟进——同一项目两套口径。
- **根因**：单条抽取未异步化。
- **修复方案**：复用 `AiAsyncTasks` 把单条抽取改异步提交 + 轮询。
- **验证标准**：改造前后各 50 并发单条抽取，Tomcat 请求线程占用时长下降。
- **来源**：AI-18。

### P1-8 · AI-19 复核详情把 AI 生成 await 在页面 loading 之内

- **问题简述**：`components/ReviewDetailPanel.vue:2`（`v-loading` 覆盖整个面板，文案「正在读取复核详情…」）、`:392`（`detailLoading=true`）、`:413`（`await runAiAsync('review',...)`）、`:427`（finally 置 false）。LLM 慢时复核员等最长 150s 才能看到扣分明细。
- **根因**：AI 建议与详情加载耦合。
- **修复方案**：AI 建议与详情加载解耦，AI 结果异步补入（独立小 loading）。

### P1-12 · R3-①② 统计缓存 TTL 无抖动 + key 空间失控

- **验证标准**：TTL 分布不再同秒过期；构造随机 filter 不再产生无界 key；失效瞬间只一次现算。

### P1-13 · W3 Cache-Aside 旧值写回竞态

### P1-15 · S1 术语建议召回全量线性扫描词典【科研级】

- **问题简述**：`AiServiceImpl.java:737`（`recallCandidates`）、`:748`（`overlap`）、`:759`（`commonChars`），调用点 `:706`。对每个待补词全量扫描该类型全部词条，复杂度 **O(T×D×A×L²)**。当前规模单条约 2000–3000 次 `commonChars`，T=500 达百万级（秒级）；导入国标全量后（D≈3 万）单条约 4.5 万次 → T=500 时 2250 万次（十秒到分钟级）。
- **根因**：无索引，线性扫描。`commonChars` 用 `StringBuilder.indexOf + deleteCharAt`，各 O(L)。
- **修复方案**：**倒排索引 + 字符 n-gram**（中文 IR 标准做法）。因 `RECALL_MIN_OVERLAP=2`（`AiServiceImpl:675`），「与 w 共享 ≥ 2 个不同字符」是入选的**充要条件** → 可在**完全不改变结果集**的前提下把扫描量从 D 降到候选数。倒排表挂 `DictionaryTermStoreImpl` 既有 `VersionedCache`（`org|type|version`，`:79` 区）同一版本号，不新增失效通道。
- **精度说明**：过滤阶段**零精度损失**（充要条件保证结果集相同）；`overlap` 打分函数**不动**，BM25 不在本期范围（换 BM25 会改变排序结果）。
- **验证标准**：`recallCandidates` 输入规模 T 与单次耗时埋点；结果集与改造前逐条一致；国标全量后收益从约 30× 增到约 400×。
- **来源**：算法 S1（合并 A3 / AI-7 同一根因的「预计算 overlap」修复）。

### P1-16 · S3 模糊 Dice 逐对计算 + 每次重建字符集【科研级】

- **问题简述**：`EsTermNormalizer.java:243-268`（三级判定模糊级）、`:277-285`（`dice`，`:282`/`:284` 每次 `new HashSet<>()` 两个）。单实体约 75 次 `dice`、150 个临时 Set；4 万病历 × 每病历约 30 实体 ≈ 120 万实体 → **约 1.8 亿次 Set 分配**，「单点不痛、批量痛」。
- **根因**：Dice 每次重建字符集并做 O(L) 求交。
- **修复方案**：**字符集位图**。`Dice = 2×popcount(a&b) / (popcount(a)+popcount(b))`，`Long.bitCount` 单指令；`input` 位图建一次，候选位图随词条预计算并挂词典版本（`VersionedCache` 有版本机制）。
- **精度说明**：位图结果与现实现**逐位相同**（Dice 定义不变）→ 零精度损失，**直接替换 `dice` 内部实现、不改调用点**。
- **验证标准**：单次 Dice 由「O(L) 建集 + O(L) 求交」降到 O(1)（预计算后），临时对象归零、GC 压力下降；归一结果与改造前逐条一致。
- **来源**：算法 S3（合并 AI-22 实现层同源）。

### P1-17 · T3 清洗链路逐实体调 ES，未复用批量预热

- **问题简述**：`GovernanceServiceImpl.java:79`（`normalize` 单实体）；对照 `EntityNormalizer.prefetchRecall`（`:336`，`_msearch` 一次往返）。`RECALL_CACHE`（4096）会吸收重复，但每个新原文仍一次往返，原文种类多时往返可达数十万次。

### P1-18 · T14 `QcRuleStore.getFor()` 每次 `selectById`

### 4.4 新增 Redis 场景（R5–R12）

> 逐点落地。**R8 / R9 必须先有失效通道再开缓存。**

| 编号 | 场景 | Key 设计 | 落地口径 |

# 中医电子病历质控与标准化系统 \- 详细功能设计文档

## 接口通用约定（统一 Result 返回包装规范）

所有接口（文件流下载类除外）统一返回 Result 包装：

```JSON
{"code": 200, "msg": "string", "data": any}
```

\- code: 状态码，200 = 成功；非 200 = 业务 / 系统异常。通用状态码：200成功；400请求参数非法；401未登录；403权限不足；404资源不存在；500服务异常。

\- msg: 提示信息，成功 / 失败描述文案。

\- data: 业务真实返回数据，无数据时返回 null。

\- 实体识别无结果统一返回空数组\[\]，禁止返回null。

\- 分页查询统一参数：page（页码从1开始）、pageSize（每页条数）。

示例（成功）:

```JSON
{
  "code": 200,
  "msg": "登录成功",
  "data": {
    "token": "abc",
    "role": "管理员"
  }
}
```

示例（失败）:

```JSON
{
  "code": 401,
  "msg": "用户名或密码错误",
  "data": null
}
```

\- 登录态传递：所有非登录接口需在请求头 Header 中携带 `Authorization: Bearer <token>`；token 缺失或过期时返回 code=401。

\- **权限约定**：接口分四档，各接口在 `openapi.yaml` 的 `description` 首部以 `【权限：…】` 标注，以该文件为唯一基准：
  - **公开**：用户登录、用户注册；
  - **仅管理员**：管理类操作（病历导入 / 新增 / 修改 / 删除、数据清洗、数据集导出、词典导入 / 回滚、质控评分与重算、日志审计、清洗状态统计）；
  - **登录即可**：只读查询与业务计算（NLP 抽取、术语查询 / 归一、统计看板、原始病历查看、多条件查询、质控检查）；
  - **管理员 / 审核员**：复核相关接口（待复核任务列表、提交复核）。

  审核员另受数据域（行级权限）约束：仅可读取 `grade='待复核'` 的病历，管理员为全库；执行顺序固定为「先数据域、后用户筛选」取交集，用户筛选条件不得绕过数据域。权限不足统一返回 403。

文件流下载类接口（日志导出、标准数据集导出）不套 Result 包装，直接返回文件流。

# 一、 必做功能设计

### 1\. 用户登录

**功能描述**: 系统的入口，负责验证用户身份并授予相应权限。角色固定内置（管理员、审核员），登录后按角色返回菜单列表，无需独立权限配置界面（对应需求4\.5安全性、2\.1用户角色）。

**输入数据流**:

用户输入的用户名（username）。

用户输入的密码（password）。

**输出数据流**:

登录成功或失败的状态标识。

登录成功后，返回用户角色信息（如：管理员、审核员）及按角色分配的菜单列表，前端据此渲染页面。

用于后续接口鉴权的会话令牌（Token）。

**接口设计**:

路径: POST /api/auth/login  // 作用：用户账号密码登录鉴权，下发登录令牌与角色信息

请求体:

```JSON
{
  "username": "string",
  "password": "string"
}
```

响应体:

```JSON
{
  "code": 200,
  "msg": "登录成功",
  "data": {
    "token": "string",
    "role": "string",
    "menus": ["首页看板", "病历数据", "结构化解析", "质控校验", "人工复核", "清洗与导出", "术语词典", "日志审计"]
  }
}
```

失败示例:

```JSON
{
  "code": 401,
  "msg": "用户名或密码错误",
  "data": null
}
```

### 2\. 基础权限与操作日志管理

**功能描述**: 
系统权限采用固定角色方案：仅建 users 表（含 role 字段），登录成功后由后端按 role 返回对应菜单列表，前端按菜单渲染页面，实现功能访问隔离；无需权限配置界面。

关键操作（导入、修改、删除、导出等）在代码中追加写入日志文件 logs/operation.log（格式：时间 | 操作人 | 操作内容），持久化存储、重启不丢失，并提供导出接口（对应需求4\.5安全性）。

**输入数据流**:

用户登录时的账号、密码（角色存于 users 表 role 字段）。

**输出数据流**:

登录后按角色返回的菜单列表（随登录接口返回，见必做1）。

关键操作（导入、修改、删除、导出等）追加写入 logs/operation.log（格式：时间 | 操作人 | 操作内容），持久化存储、重启不丢失。

**接口设计**:

路径: GET /api/logs/export  // 作用：读取 logs/operation.log 日志文件，作为文件流返回前端下载

响应: 文件流下载（文本格式），不套 Result 包装。

### 3\. 病历批量导入与单条新增

**功能描述**: 支持管理员批量上传病历Excel文件，也支持单条新增病历，作为系统数据处理的源头；解析上传文件并校验文件格式、字段完整性，过滤空文件、格式错误文件。

**输入数据流**:

用户上传的病历Excel文件（.xlsx格式），包含21个字段：
- 基本信息：登记号、门诊号、性别、年龄、就诊次数
- 诊断信息：西医诊断、中医诊断
- 四诊信息：主诉、自诉、现病史、望诊、脉诊、舌诊、查体
- 辨证信息：辨证结论
- 治疗信息：草药、随访、治疗效果
- 就诊信息：开单科室、医生工号、接诊时间

约束：单文件最大50MB，单次最多上传20个文件。

单条新增：填写21个字段信息。

**输出数据流**:

一个唯一的导入任务ID，用于追踪处理进度。

导入结果的摘要信息，包括总文件数、成功数、失败数及失败原因列表。

成功入库的病历建立唯一ID，包含完整的21个字段。

**接口设计**:

路径: POST /api/records/import  // 作用：批量上传病历文件，校验并创建导入任务，批量入库病历

请求体: multipart/form‑data \(包含文件列表\)

      "failed": 2,

请求参数: 无（taskId 为路径参数）

说明：任务状态暂存于服务内存（内存 Map<taskId, String>），导入开始时置为「处理中」，成功/失败后置为「已完成」；接口返回当前状态供前端展示进度。

### 6-9\. NLP实体抽取（症状/舌脉/证候病因治法/方剂中药）

**功能描述**: 
利用NLP技术从非结构化病历文本中自动识别并抽取中医四诊实体，统一接口 POST /api/nlp/extract 一次返回完整结构化数据，覆盖：

① 症状实体提取——识别症状实体，每个实体包含内容（content）与原文片段（sourceText）；
② 舌象、脉象提取——提取舌象描述和脉象描述，支持多条结果；
③ 证候、病因与治法提取——提取中医证候、病因（如外感风寒、饮食积滞）与治法（如辛温解表、疏肝理气），支持多条结果；
④ 方剂和中药提取——识别方剂名称（支持多方剂）与中药列表（含每味中药的名称和剂量）。

（对应需求3\.2核心处理逻辑2）

**输入数据流**:

原始病历的自由文本内容。

**输出数据流**:

症状实体列表，每个实体包含内容（content）与原文片段（sourceText）。

舌象描述和脉象描述，支持多条结果，保留原文片段（sourceText）。

中医证候实体。

病因实体与治法实体，支持多条结果，保留原文片段（sourceText）。

方剂名称列表，支持多方剂。

中药列表，包含每味中药的名称和剂量，保留原文片段（sourceText）。

**接口设计**:

路径: POST /api/nlp/extract  // 作用：NLP实体抽取统一入口，一次返回完整结构化数据（见附录A）

### 10\. 症状、证候、中药与方剂术语标准化

**功能描述**: 
依托系统内置中医标准术语库，将提取出的口语化、非标准表述映射为标准医学术语，统一同义词、别名、口语化表述。术语库在系统启动时从 data/dictionaries/*.json 加载到ES索引（IK分词器+自定义词典+score阈值匹配），术语库导入完成后自动重载（对应需求3.4术语归一）。

**输入数据流**:

从病历中提取的口语化症状词，例如"嗓子疼"。

**输出数据流**:

对应的标准医学术语，例如"咽痛"，及术语来源标准。

未命中标准术语时，standardTerm 返回原词、source 返回空字符串（不报错，交由 NLP 流程原样保留）。

未命中时的边界处理：术语库未收录的术语（如食材类"粳米"、传统单位"3片"）返回原词，source置空；未命中不影响评分判定（不视为缺失/错误），仅用于统计分析；管理员可在"术语词典管理"中补充缺失术语，重建ES索引后重新归一。

内置标准术语库（四类）：症状（《中医临床诊疗术语》GB/T 16751）、证候（《中医病证分类与代码》GB/T 15657‑2021）、中药（《中国药典》2025版）、方剂（《中医方剂大辞典》）。

**接口设计**:

路径: POST /api/governance/normalize  // 作用：将口语化/非标准中医术语归一国标标准术语

请求体:

```JSON
{
  "type": "symptom",
  "term": "嗓子疼"
}
```

type 取值：disease（疾病）、pattern（证候）、symptom（症状）、herb（中药）、formula（方剂）。

响应体:

```JSON
{
  "code": 200,
  "msg": "success",
  "data": {
    "standardTerm": "咽痛",
    "source": "《中医临床诊疗术语》"
  }
}
```

### 11-12\. 质控检查（缺失/格式/查重）

**功能描述**: 
作为事前质控的一环，对结构化病历统一执行三类检查（对应需求3\.3事前质控）：

① 缺失字段检查——校验核心必填要素（症状、证候、舌象、脉象、中药）是否缺失，全面标记字段缺失类异常；
② 重复和格式检查——查重病历并验证字段格式是否符合规范。

统一接口 POST /api/qc/check 一次返回全部结果。

**输入数据流**:

经过NLP提取后的结构化病历数据【structuredData，见附录A】。

**输出数据流**:

缺失的核心必填字段列表，如脉象、证候、方剂等。

是否为重复病历的布尔值。

格式错误的详细信息列表；子项字段：\{"field":"字段名","msg":"错误描述"\}。

**接口设计**:

路径: POST /api/qc/check  // 作用：事前质控统一入口，一次返回缺失字段、格式错误、查重结果

请求体:

```JSON
{
  "structuredData": {}
}
```

响应体:

```JSON
{
  "code": 200,
  "msg": "success",
  "data": {
    "missingFields": ["pulse", "pattern"],
    "formatErrors": [{"field": "pulse", "msg": "字段为空"}],
    "isDuplicate": false
  }
}
```

### 13\. 结构化结果人工校正与异常复核

**功能描述**: 
为审核人员提供统一的人工修正工作台，病历状态二元化（待复核 / 已完成），校正与提交复核合并为同一接口 POST /api/records/\{recordId\}/review。

触发与流转：评分<60分标记为无效数据（status=invalid）；60分≤评分<90分或逻辑校验不通过（logicErrors 非空）的病历自动进入待复核列表；审核人员修改数据后点击「复核通过」，系统自动重新执行评分与逻辑校验：通过则置为已完成，仍有错误则保持待复核（复核时限7个工作日）。

超时处理：任务超过复核截止时间（deadlineTime）后仍保留在待复核列表中，前端对其进行高亮或特殊标记提醒；系统不自动关闭或转交任务，由审核人员人工处理。

（对应需求3\.2核心处理逻辑4、3\.3人工复核回流）

**输入数据流**:

系统自动提取的原始结构化数据。

人工修正后的结构化数据【structuredData，见附录A】。

自动进入待复核的病历列表（60≤score<90 或 logicErrors 非空）。

审核人员的复核操作及修正内容。

**输出数据流**:

校正后的最终结构化数据，自动覆盖原结构化记录并更新结构化临时数据表。

病历状态更新（待复核 → 已完成），返回复核截止时间用于前端展示7个工作日时限。

复核后自动重新执行评分与逻辑校验的结果。

### 15\. 终末质控评分与质控报告

**功能描述**: 
对单条病历自动评分，评分规则直接写死在代码 calculateScore 函数中（**相对评分**：以病历自身缺陷项为基础扣分，满分100分，最低扣至0分）：

- 核心要素（症状、疾病、证候、舌象、脉象、中药）缺失每项扣 6~12 分（原始列有=漏抽 -6；两处皆无=真缺失 -12）；
- 辨证逻辑冲突（证候‑治法、证候‑方剂、证候‑中药规则校验不通过，见拓展1）每项扣10分；
- 格式错误、重复数据每项扣5分。

扣分明细以 deductions 数组返回。

评分分级：评分≥90分且无逻辑错误判定合格，进入数据集（必做14）；60分≤评分<90分或逻辑校验不通过自动进入待复核（必做13）；评分<60分标记为无效数据（病历 status=invalid，存入异常数据区，禁止导出）。

额外严重问题判定规则：核心必填字段缺失≥3 项、证候‑治法与证候‑方剂规则同时逻辑冲突、文本无法解析，视为严重问题，直接判定为无效数据，设置 status=invalid 存入异常数据区、禁止导出。

质控报告为页面展示评分与扣分原因文字，不生成独立报告文件或模块（对应需求3\.3终末质控）。

**输入数据流**:

结构化病历数据【structuredData见附录A】及其质控检查结果（缺失、重复、格式、逻辑冲突）。

**输出数据流**:

病历相对质量评分（满分100，按自身缺陷项扣分）。

评分分级路由：评分≥90分且无逻辑错误→判定合格，进入数据清洗模块（必做14）；60分≤评分<90分或逻辑校验不通过→自动进入待复核（必做13），复核通过后重新评分校验，合格则进入清洗，仍有错则保持待复核；评分<60分→标记为无效数据（病历 status=invalid，存入异常数据区，禁止导出）。

质控报告：页面展示评分、扣分明细与扣分原因文字，不生成独立报告文件或模块。

**接口设计**:

路径: POST /api/qc/score  // 作用：终末质控，自动对病历打分、扣分并完成质量分级

后端处理流程: 接收 structuredData → 内部调用事前质控逻辑（缺失、格式、查重，见必做11-12）→ 内部调用事中质控逻辑（诊疗一致性，见拓展1）→ 汇总所有问题执行评分计算 → 返回评分、分级与扣分明细。

请求体:

```JSON
{
  "structuredData": {},
  "qcResults": {}
}
```

响应体:

```JSON
{
  "code": 200,
  "msg": "success",
  "data": {
    "score": 82,
    "grade": "待复核",
    "deductions": [{"type": "missing_field", "points": 15}]
  }
}
```

### 16\. 词典管理（术语库维护）

**功能描述**: 
采用「文件即数据库 + LLM 即 ETL + 备份文件即版本历史」方案维护系统内置标准中医术语库：

术语库存储于项目 data/dictionaries/ 目录下的五个 JSON 文件（diseases.json、patterns.json、symptoms.json、herbs.json、formulas.json）。

管理员上传国标 Excel/CSV 术语文件，由 LLM 自动转换为标准 JSON 并写入对应文件。

写入前自动将旧文件备份至 data/dictionaries/backup/（文件名加时间戳，如 symptoms.json.bak_20260811_143000，构成版本历史），支持一键回滚到任意备份版本。


实现智能化、可追溯、可回滚的术语库构建，无需繁琐的增删改查后台（对应需求3\.4术语归一、2\.1管理员职责、1\.4数据范围）。

**输入数据流**:

管理员上传的国标术语文件（Excel/CSV 格式），五类：疾病（《中医临床诊疗术语 疾病》GB/T 16751.1）、证候（《中医病证分类与代码》GB/T 15657‑2021）、症状（《中医临床诊疗术语 症状》GB/T 16751.1）、中药（《中国药典》2025版）、方剂（《中医方剂大辞典》）。

演示数据建议使用国标子集（如一两百条），避免一次全量转换超时或出错。

**输出数据流**:

LLM 转换并写入的 JSON 术语库文件（data/dictionaries/*.json），写入前自动备份旧文件至 data/dictionaries/backup/（时间戳命名，构成版本历史）；导入后自动重新加载内存术语库。

术语库导入的成功/失败结果及异常明细。

更新后的术语库供必做10术语标准化及拓展1诊疗逻辑校验调用。

**接口设计**:

路径: POST /api/dictionary/import  // 作用：上传国标术语文件，由 LLM 转换为标准 JSON 并写入术语库文件（LLM 驱动导入）

请求体: multipart/form‑data \(Excel/CSV术语文件，字段含 type 指定术语类型\)

后端处理流程:
1. 读取文件内容，调用 LLM 按指令转换（Prompt 示例：提取「标准术语」与「别名」两列，输出 [{"standardTerm": "标准名", "aliases": ["别名1", "别名2"]}] JSON 数组，仅返回 JSON）；
2. 解析并校验 LLM 返回（剥离多余文字，跳过非法条目）；
3. 按 standardTerm 去重合并别名；
4. 将旧文件备份至 data/dictionaries/backup/（文件名加时间戳，如 symptoms.json.bak_20260811_143000）；
5. 写入对应 JSON 文件；
6. 重新加载内存术语库。

响应体:

```JSON
{
  "code": 200,
  "msg": "导入完成",
  "data": {
    "type": "symptom",
    "total": 1000,
    "imported": 980,
    "failed": 20,
    "failures": [{"row": 5, "reason": "LLM 转换结果缺失 standardTerm 字段"}]
  }
}
```

路径: GET /api/dictionary/terms  // 作用：只读查询/自动补全，从内存术语库按类型与关键词过滤

请求参数: type（disease/pattern/symptom/herb/formula）、keyword（名称或别名包含匹配）

响应体:

```JSON
{
  "code": 200,
  "msg": "success",
  "data": {
    "terms": [{"standardTerm": "头痛", "aliases": ["头疼"]}]
  }
}
```

路径: POST /api/dictionary/rollback  // 作用：根据备份文件名将术语库恢复到指定版本（一键回滚）

请求体:

```JSON
{
  "type": "symptom",
  "backupFilename": "symptoms.json.bak_20260811_143000"
}
```

后端处理流程: 校验 data/dictionaries/backup/ 下备份文件是否存在 → 存在则用备份文件覆盖当前 data/dictionaries/*.json → 重新加载内存术语库。

响应体:

```JSON
{
  "code": 200,
  "msg": "版本恢复成功",
  "data": null
}
```

术语维护说明：不提供新增/修改/删除接口。需调整术语时，直接编辑 data/dictionaries/*.json 对应条目，或重新导入国标文件；需回滚时通过 rollback 接口按备份文件名恢复指定版本。

# 二、 拓展功能设计

### 拓展1\. 诊疗逻辑一致性检查

**功能描述**:

### 拓展2-4\. 数据统计（症状频次/证候分布/方剂中药频次）

**功能描述**: 对已标准化病历批量执行三类统计（统一接口 POST /api/stats，按 type 区分）：①症状频次统计——计算各症状出现频率，按频次降序排列；②证候分布统计——展示不同证候对应病例数量的分布；③方剂和中药频次统计——分别统计方剂、单味中药的使用频次。

**性能说明**：当前方案使用 Java 内存聚合统计，适用于≤1 万条病历；若数据量达到 3 万条或统计查询变慢，可将 structured_data 症状 / 证候字段索引到 Elasticsearch，启用 ES 聚合优化（_terms 聚合），统计接口响应时间从秒级降至毫秒级。数据规模口径以 `需求分析报告.md §4.1`（单次批量上限 3 万条）与 `后续开发方案.md §1.3` 为准。

一批已标准化的病历ID列表，携带 type 指定统计类型。

**输出数据流**:

# 附录C：AI应用功能设计

> 说明：本节定义系统后续 AI 应用增强功能的设计规范（实施规划见《docs/后续开发方案.md》），与附录A（structuredData 模型）、附录B（业务编码表）平级。数据模型沿用附录A，所有结构化数据展示统一复用。

## C.1 归一溯源提示

**功能描述**: 对图谱术语归一结果提供可解释溯源，展示「原文 → 标准词」的转换依据与命中层级，提升 AI 质控的可解释性（非黑盒）。

- **分区卡片展示**: 结构化数据按 9 类分区（疾病/症状/舌象/脉象/证候/病因/治法/方剂/中药），空区隐藏；实体条目显示「标准词（content）」+ 小字「原文：sourceText」；中药条目显示「名称 + 剂量」+ 原文。
- **溯源触发条件**: `content ≠ sourceText` 时，条目右下角显示小斜线 icon，悬停弹出「原文：{sourceText} → 标准词：{content}【命中层级：精确/包含/模糊】」。
- **命中层级字段**: 归一循环将 `normLevel`（1=精确 / 2=包含 / 3=模糊）写入 structuredData 实体；`normLevel` 缺失时降级为仅显示「原文 → 标准词」（不显示层级）。
- **三级命中分布**: 数据清洗结果（CleanResultVO）新增 `normByLevel {exact, contain, fuzzy}`，清洗结果区展示各层命中计数。

## C.2 AI质控解读卡

**功能描述**: 对单条病历生成自然语言质控预检报告，结论均由规则引擎依据字段缺失 / 归一命中 / 逻辑冲突计算，每个结论可溯源。

- **位置与触发**: 病历详情弹窗底部「AI质控解读」按钮 → 点击后骨架屏（约1秒）→ 展开报告区。
- **报告模板**:
  1. 完整性分析：21 字段缺失清单；
  2. 缺项重点：核心要素（症状/疾病/证候/舌象/脉象/中药）缺失；
  3. 归一命中：n 处归一（精确/包含/模糊各层计数）；
  4. 关键提示：如"辨证结论为空""处方缺失"；
  5. 声明：`AI辅助分析，最终以人工复核为准`。
- **数据源**: 行 21 字段 + structuredData + normLevel → **规则出结论**（完整性 / 缺项 / 归一命中），再由 `POST /api/ai/interpret`（`LlmClient`）**LLM 叙述**生成报告；**LLM 不可用 → 降级模板叙述**、保留规则结论。
- **空态**: 无 structuredData 时仅输出完整性分析。

## C.3 AI助手悬浮窗（全局）

**功能描述**: 全站右下角悬浮 AI 助手，面向使用者回答**本项目相关问题**（数据 / 功能 / 流程 / 判定原因），**不回答技术实现问题**，体现"AI 辅助、人工兜底"的人机协同设计。

- **挂载**: `MainLayout.vue`，所有登录页可用。悬浮球为中式圆钮（墨绿·药丸 icon），展开面板约 360×480。
- **快捷指令**: 这份病历为什么被判定待复核 / 当前合格率与待复核构成 / 这个功能怎么用 / 我接下来该做什么 / 术语标准化的依据是什么。
- **规则问答路由**: 业务问题（数据/功能/流程/判定原因）→ `LlmClient` 对话 + 规则检索：`记录数/合格/待复核/无效`→stats；`归一/分布`→normByLevel；`当前病历`→活跃详情；**技术实现问题兜底「这属于系统实现细节，建议查看设计文档或咨询开发同学」**。
- **状态共享**: pinia store `stores/ai.js` 暂存 `activeRecord`（详情点击写入）、`normByLevel`（最近清洗写入）、`stats`；无数据时指令降级提示。
- **约束**: 单轮问答（无会话历史）；z-index 置顶但不遮菜单。

## C.4 AI质控评分与批量重算

**功能描述**: 落地文档"必做15 终末质控评分"的真实算法（calculateScore），替代测试数据随机分数，评分依据可溯源（非黑盒）。

- **评分算法（QcScorer）**: 满分 100，按错误类型累计扣分，最低扣至 0：
  1. 核心要素（症状/疾病/证候/舌象/脉象/中药）缺失，每项 -6（漏抽）/ -12（真缺失）；判空按 structuredData 非空判断，structured 为空再回退查原始列，两者皆空才判缺失；
  2. 辨证逻辑冲突（证候-治法/方剂/中药规则校验不通过），每项 -10；规则未覆盖的证候不判冲突（不误杀）；
  3. 格式错误（age 非数字/性别非男女）、重复数据，每项 -5。
- **严重问题判定（直接 invalid）**: 核心要素真缺失 ≥3 项；文本无法解析。
- **分级路由**: score≥90 且无逻辑错误 → 合格（进入数据清洗）；60≤score<90 或逻辑冲突 → 待复核（进入人工复核，复核时限 7 个工作日）；score<60 或严重问题 → 无效（隔离归档，禁止导出）。
- **逻辑一致性（LogicChecker）**: 内置固定规则表，不支持自编辑——3 条证候映射（风寒感冒→辛温解表→麻黄汤/桂枝汤；风热感冒→辛凉解表→银翘散/桑菊饮；暑湿感冒→清暑祛湿→新加香薷饮）+ 2 条舌脉规则（舌红×脉沉迟、舌淡×脉数）。
- **接口**: `POST /api/qc/score`（单条评分）；`POST /api/qc/score/batch`（全库重算，事务 + 逐条幂等，返回分级分布统计；管理员操作）。
- **预检单落库**: `records.qc_results` 写入 `{score, grade, deductions:[{type,item,points,reason}], logicConflicts, serious, checkedAt}`；待复核病历自动生成 `review_tasks`（pending，deadline=+7 工作日）。

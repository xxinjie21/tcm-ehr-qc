# 缓存场景审查与改造方案

> **审查对象**：`java-backend`（Spring Boot 4.1 + MyBatis-Plus + Redis/Redisson/Elasticsearch）、`frontend`（Vue 3 + Element Plus + ECharts）。
> **审查目标**：识别「页面聚合多类统计、原始查询耗时长、数据变更频率低、读请求量大」且允许采用 Cache-Aside（查询时建缓存、数据变更时主动删缓存）的业务接口。
> **数据规模基准**：`records` 约 4 万行，`structured_data` 合计约 157 MB。
> **交付形态**：本文为审查记录 + 改造方案，只读审查，未改动任何源码。
> **关联文档**：《性能优化与 Redis 应用审查报告》（R3/R8/W 系列口径同源）、《优化方案与待修复清单》。

### 1.4 关键发现

1. **既有 Cache-Aside 只覆盖了前端不调用的 `/stats/all`**：`StatsCache`（`common/cache/StatsCache.java`）的 TTL 抖动、版本号前缀失效、单飞、降级、空值哨兵一应俱全，但真正每次进首页都在打的 A1/A2/A3 与最重的 B **全部零缓存**。

## 二、是否适合 Redis 缓存（逐场景）

| # | 结论 | 理由 |
|---|---|---|
| A1 overview | **适合（弱收益）** | 读多写少、非法实时。但计数已下推 SQL（毫秒级），缓存收益小；且依赖 grade/governed，单条质控写路径（`processOne`）不触发失效 —— 批处理路径已被 `QcBatch:527` 兜住、缺口当前不可达（§8.6 第 4 条）；若将来出现单条写入口，缓存前必须先补失效点。 |
| A2 extra | **适合（收益中）** | 全表 `GROUP BY` ×3 + 5 次词典读取，每次进首页都打；数据仅导入 / 清洗 / 复核后变化，符合模式。 |
| A3 governance/stats | **适合** | 全表聚合、仅管理员、变更低频。 |
| B standardization-report | **最适合（收益最大）** | 全量拉取 + 全量解析，秒级，读触发频繁（报告页），变更是低频批处理。唯一约束：Value 可能大，必须限制体积、且 **Key 必须带词典版本**（换词表数字会变但不是数据变更）。 |
| C stats/all | 已是该模式 | 现成参考实现，可直接复用其机制。 |
| D deduction-stats | **有条件适合** | 命中 `qc_results` 快路径仅 216ms，缓存收益小；但**回退退化到 4.9s** 的场景收益巨大。适合 60s 短 TTL。 |
| E review/tasks/count | **不适合** | 本身就是廉价 COUNT；且「超期数」随墙钟变化（`deadline_time < now`），**无数据变更也会变**，缓存会产生语义漂移。 |
| F records/search | **不适合** | 筛选 / 分页参数组合无界 → Key 空间爆炸；本质是列表不是聚合，应靠索引 / keyset（管理员 2.8s 应优化 SQL 而非缓存）。 |

> **关于用户设想的确认**：「无数据变更时只算一次存 Redis，变更时删 Key，查库后重建」——这正是标准 **Cache-Aside**，且与项目既有 `StatsCache` 结构、`StatsCacheInvalidator` 门面、审查报告 R3/R8/W 系列口径完全一致。要补的是**覆盖面**与**失效完整性**，而非重新设计。

## 三、改造方案

以 A2（extra）+ B（report）为主，复用现有机制，不引入 Spring Cache / `@Cacheable`。

### 3.1 泛化 `StatsCache`

把 `common/cache/StatsCache.java` 从「只缓 wordFreq」泛化为一套通用统计缓存入口：

- **Key**：`tcm:ehr:cache:stats:{scope}:v{n}:{kind}:{md5(params)}`
  - `scope`：`ALL`（管理员）/ orgId / `NONE`（复用 `scope():218`）
  - `kind`：`overview` / `extra` / `gov` / `report` / `deduction`
  - **report 特殊**：md5 入参须含 `start + end + dictVersion`（词典换版必须换 Key）
- **失效**：版本号自增（`bumpVersion:205`），**禁用 `KEYS`**（已有纪律，`RedisKeys.PREFIX = tcm:ehr:`）
- **TTL**：
  - overview / extra / gov / deduction：**60 ± 10s 抖动**（`ttl():155`）
  - report：**120–300s ± 抖动**（变更更稀、计算更重）
  - 空值哨兵 10s（`NULL_TTL:60`）
- **白名单**：沿用 `cacheable:236`（科室限字符、日期 `yyyy-MM-dd`、grade 枚举；**证候校验已随 `2594db5` 删除**）；**report 的 start/end 也按此校验**

### 3.2 完整读写时序

**读路径**：查 Redis → 命中且非哨兵则返回；未命中 → 单飞锁（`SETNX tcm:ehr:cache:stats:lock:{key}`）→ 只有领跑者查库计算 → 写 Redis（带抖动 TTL）→ 返回；跟随者短暂等待后重读或自行计算。

**写路径（Cache-Aside 五条铁律，项目已有正确范式）**：

1. 先改库、后失效；
2. **失效必须在事务提交后**（`DistLock.afterCommit`，参见 `GovernanceServiceImpl.java:253`）——`deleteRecords` / `deleteByFilter` / `clean` 已是 afterCommit；
3. 失效失败靠 TTL 兜底；
4. **必须补一个失效点**：`QcServiceImpl.updateScoreFields`（单条质控改 grade）当前不失效，接缓存后须追加 `invalidateStats()`，否则 overview / extra / report 会脏读。
5. **必须修正失效粒度（关键正确性缺口）**：现有 `StatsCache.invalidateForWrite()`（`:102-105`）只 bump `scope()`（管理员 = `ALL`）与 `"ALL"`，**不含「被改数据实际所属组织」**；而 `RecordServiceImpl.importRecords` 用 `setOrgId(RequestUtils.currentOrgId())`（`:174`）落地数据 → 管理员导入的数据落在其归属组织 `org_admin`，但失效只 bump `ALL` ⇒ `org_admin` 的**普通用户**统计脏读（≤TTL 兜底）。扩展缓存后此缺口从「无影响」变为「真实脏读」，**必须先修**（方案见 §3.6）。

### 3.3 并发三防

| 风险 | 方案 | 现有依据 |
|---|---|---|
| 穿透 | ① Key 空间白名单化（治本，非法参数直接绕过缓存现算）② 空值哨兵缓存 10s | `cacheable:236`、`NULL_SENTINEL:69` |
| 击穿 | 单飞锁，过期瞬间只一个请求回源 | `loadSingleFlight:109` |
| 雪崩 | ① TTL 随机抖动 ② 版本号前缀失效（不 `KEYS`、不批量同秒过期）③ Redis 异常降级现算 | `ttl():155`、`bumpVersion:205` |

### 3.4 伪代码

```java
// 查询接口（泛化后的 StatsCache）
public <T> T getOrLoad(String scope, String kind, Object params,
                       Duration baseTtl, Supplier<T> loader, Class<T> type) {
    String key = keyOf(scope, kind, currentVersion(scope), params);   // ...:v{n}:{kind}:{md5}
    if (!cacheable(params)) return loader.get();                      // 穿透：白名单外直连
    String json = readQuietly(key);                                   // Redis 异常 → null
    if (json != null) {
        if (NULL_SENTINEL.equals(json)) return null;
        T cached = parseQuietly(json, type);
        if (cached != null) return cached;
    }
    return loadSingleFlight(key, baseTtl, loader, type);              // 击穿：单飞
}

private <T> T computeAndCache(String key, Duration baseTtl, Supplier<T> loader, Class<T> type) {
    T vo = loader.get();
    try {
        if (vo == null) redis.opsForValue().set(key, NULL_SENTINEL, NULL_TTL);
        else redis.opsForValue().set(key, objectMapper.writeValueAsString(vo), jitter(baseTtl));
    } catch (Exception e) { log.debug("[统计缓存] 写失效，下次现算: {}", e.getMessage()); } // 降级
    return vo;   // Redis 挂了也照常返回现算结果
}

// 使用：看板扩展
public StatsVO extra(FiltersDTO filters) {
    return statsCache.getOrLoad(scope(), "extra", filters, TTL_BASE,
            () -> extraFromDb(filters), StatsVO.class);   // 未命中 -> 查库计算 -> 回填
}

// 数据变更接口（不改业务语义，只在提交后失效）
@Transactional
public void deleteRecords(DeleteRecordsDTO dto) {
    recordMapper.deleteByIds(dto.getIds());
    DistLock.afterCommit(StatsCacheInvalidator::invalidateStats);   // 提交后删缓存
}

// 补齐的失效点（当前缺失）
public ScoreResultVO updateScoreFields(...) {
    recordMapper.updateScoreFields(...);
    StatsCacheInvalidator.invalidateStats();     // 改 grade → overview/extra/report 需失效
    return ...;
}
```

### 3.5 异常兜底

- **Redis 不可用 = 自动降级直连 DB**：读 / 写 / 锁全部 `try-catch` 吞异常，走 `loader.get()` 现算，绝不抛 500（现有 `readQuietly:162`、`computeAndCache:139`、`loadSingleFlight:109` 已是此语义）。
- 反序列化失败同样回退现算（`parseQuietly:171`）。
- 版本号 key 不设 TTL（见 `bumpVersion:205` 注释），数量上界 = 组织数 + 常量。

### 3.6 失效粒度修正（正确 + 性能）

**问题**：失效取的 scope 是「**请求者视角**」（`scope()`），而数据落地 / 变更的 org 是「**数据视角**」。二者在**管理员操作**时不等 —— 管理员 `scope() = 'ALL'`，但数据落 `RequestUtils.currentOrgId()`（其归属组织），或被改记录本属别组。

**方案（兼顾正确与性能）**：失效时**同时** bump「请求者 scope」与「被改数据所属 org」。

| 写路径 | 涉及的 org | 失效做法 |
|---|---|---|
| 单条新增 / 修改（`createRecord` / `updateRecord`） | 该记录的 `orgId`（1 个） | `invalidateStats(record.getOrgId())` |
| 导入（`importRecords` / `importRows`） | `RequestUtils.currentOrgId()`（1 个） | `invalidateStats(RequestUtils.currentOrgId())` |
| 按 ID 删（`deleteRecords`） | 这些记录的 `orgId` 集合 | 删前 `SELECT DISTINCT org_id WHERE id IN (...)` 取集合 |
| 按筛选删 / 清洗 / 批次（`deleteByFilter` / `clean` / `NlpBatch` / `QcBatch`） | 数据域内涉及的所有 org | **在已有的分批扫描循环里顺手收集 `orgId`**（本来就在遍历，**零额外查询**）→ 循环结束一次 `invalidateStats(orgIds)` |

**性能要点**：

- **不新增查询** —— 跨 org 的路径本来就在分批遍历数据，顺手收集即可；
- bump 次数 = 涉及 org 数（通常 1~几十），每次 `INCR` 均 O(1)；
- 批量导入同一 org 仍只 bump 1 次（集合去重）；
- **不采用「bump 全部 org」**：需枚举 org 列表 + O(组织数) 次 `INCR`，管理员写频繁时开销随组织数增长，性能不可控。

**门面签名（最小改动）**：

```java
// StatsCache 侧：bumpVersion 是 private，故在类内提供入口
public void invalidateOrg(String orgId) {
    if (orgId != null && !orgId.isBlank()) bumpVersion(normalize(orgId));  // normalize = scope() 里那套 replaceAll 规整
}

// 门面：保留无参版（org 已知且等于 currentOrgId 的场景，行为不变）
public static void invalidateStats() {
    StatsCache c = statsCache; if (c != null) c.invalidateForWrite();
}

// 门面：新增跨 org 版（管理员按筛选删 / 清洗 / 批次）
public static void invalidateStats(Collection<String> orgIds) {
    StatsCache c = statsCache; if (c == null) return;
    c.invalidateForWrite();                       // 仍清「请求者 scope + ALL」
    new LinkedHashSet<>(orgIds).forEach(c::invalidateOrg);
}
```

**兜底**：即便某路径漏 bump，仍有 ≤TTL（60s）兜底；`ALL` 缓存始终失效（管理员视角永远正确）。

## 四、风险评估、上线验证与回滚

### 4.1 改造风险

1. **失效不全 → 脏读**：① 必须补 `updateScoreFields`；② **必须修失效粒度** —— 现有门面只 bump「请求者 scope + ALL」，管理员操作时**不覆盖「被改数据所属 org」**，见 §3.6；③ 复核 10 处失效点是否都覆盖新 `kind`。
2. **事务内失效**：新写路径一律用 `DistLock.afterCommit`。
3. **Key 空间失控**：白名单 + md5，禁止把任意筛选塞进 Key。
4. **report Value 体积**：只存派生 VO，**不存全量 Row**，建议设上限（如 1 MB），超限不缓存。
5. **词典版本漂移**：report Key 必须含 `dictVersion`。
6. **跨实例**：版本号存 Redis，天然共享；`VersionedCache` 是进程内，勿混用。
7. **共享 Redis 实例**：已切 db1 + `tcm:ehr:` 前缀隔离。

### 4.2 上线验证

- **基准**：4 万条真实数据上，改造前后各计时一次 overview / extra / report，用实测替换估算。
- **正确性**：同一参数下「首次现算结果 == 二次缓存结果」断言测试（项目已有 75 个测试类可依托）。
- **命中率**：补 Actuator + Micrometer，在 `getOrLoad` 命中 / 未命中各打计数器。
- **并发**：模拟热点 Key 失效瞬间并发，验证单飞只回源一次。
- **观测**：`INFO keyspace` 确认 db1 仅 `tcm:ehr:` 前缀、key 数随 TTL 收敛。

### 4.3 回滚方案

- 缓存为**附加层、不改数据、可重算**：回滚零数据风险。
- 首选**开关降级**：加配置项（如 `stats.cache.enabled=false`）使 `getOrLoad` 直接 `loader.get()`，无需重新部署即可摘除。
- 备用：revert 提交；或临时清 `tcm:ehr:cache:stats:*`（用 `SCAN` 分批，**禁用 `KEYS`**）。

## 五、不适合 Redis 的场景 + 非 Redis 替代优化

> 以下场景**不能 / 不宜用 Redis 缓存**（语义不允许、Key 无界、强一致、单 Key 过大）。逐条给出**替代优化手段**——即「用不了 Redis 就用别的方式」的落点。

| 场景 | 为何不用 Redis | **替代优化（非 Redis）** |
|---|---|---|
| `POST /records/search`、列表 / 详情 | 筛选分页组合无界 → Key 空间爆炸；本质是列表非聚合 | ① **索引**：为 `records(org_id, department, visit_time)` 建复合索引，覆盖管理员全库排序分页；② **keyset 分页**替 `LIMIT offset`；③ **ES 召回**：多字段模糊检索走 `EsTermIndexServiceImpl`，不用 `LIKE '%x%'`；④ **前端**：筛选防抖 + 时间窗必填 |
| `review/tasks/count` 超期数 | 随墙钟变（`deadline_time < now`），无数据变更也变 → 缓存语义漂移 | ① **拆分计数**：非时间相关的两个计数可缓存，超期数每次现算（单条 `COUNT` 走索引很便宜）；② 给 `deadline_time` 加索引，COUNT 走覆盖索引 |
| 令牌版本号 `tcm:auth:ver:*` | 强一致、不可丢失 | **保留 Redis + 版本号**（已是正确设计）；若极端必须去 Redis → MySQL `token_version` 列 + 本地短 TTL（接受 ≤N 秒撤销延迟，属安全降级） |
| 词典 / QC 规则读 | 要求变更即刻生效、强一致 | 保持「写路径删 Key + `VersionedCache` + afterCommit」（正确）；**去 Redis 的替代**：进程内 `VersionedCache` + 写路径本地失效 —— 但**多实例下各实例缓存不一致**，仅单实例部署可考虑 |
| report 若大到几十 MB | 单 Key 过大 | ① 只缓存**派生指标 VO**（不存全量 Row）；② **物化表 + 定时预计算**（任务算好落表，读时直查）；③ 分页 / 流式返回 |
| `POST /api/stats`（遗留接口） | 前端零调用 | 直接归档删除，不必优化 |

### 5.1 进程内缓存（Caffeine）作为 Redis 的替代

**适用前提**：单实例部署、可容忍多实例短暂不一致、数据量小（进程内存可承载）、变更低频。

- **依赖状态（2026-10-17 复核）**：`caffeine` **已在依赖树上** —— `pom.xml:144-145` 声明 `3.1.8`（`9eda480` RegexCache 替换时引入，`b0a3aa6` 批次3 行缓存续用），`-o` 离线构建可行。**本文所有「用 Caffeine」的建议可直接执行，无需先加依赖**。（原稿「不在依赖树、不得写成已有依赖」已作废，见 §8.6 第 2 条。）
- **与 Redis 缓存的取舍**：

  | 维度 | Redis（跨实例） | Caffeine（进程内） |
  |---|---|---|
  | 一致性 | 全实例共享，失效一次全生效 | **各实例独立**，写后需广播或短 TTL 兜底 |
  | 延迟 | 网络往返（~0.1–1 ms） | 纳秒级 |
  | 容量 | 大（受 Redis 内存） | 受 JVM 堆约束 |
  | 适用 | 多实例、需跨实例失效 | 单实例、只读为主、可容忍抖动 |

- **项目内已有等价物**：`common/utils/VersionedCache.java`（119 行）就是**进程内版本号缓存**，与 Caffeine「有界 LRU + 版本失效」重叠。**若要进程内缓存，优先复用 `VersionedCache`，不必新增依赖**（详见《自研组件替换计划》§2.4）。

                          Duration baseTtl, Supplier<T> loader, Class<T> type) {

       if (json != null && !NULL_SENTINEL.equals(json)) {

## 十二、实施记录（2026-10-17 · 报告「秒回」＝ SWR）

**问题**：§十一 的 180s TTL 只能让报告「有一段不重算的窗口」，窗口一过，用户仍要等一次 ~5s 冷算。

**实测：那 5s 花在哪**（4 万行 `records`，`SUM(LENGTH(...))` 直接读盘）：

| 项 | 实测 |
|---|---|
| `structured_data` + `qc_results` 合计 | ~110MB（96.5MB + 13.1MB） |
| 服务端读这两列（含全量磁盘读） | **~3.0s**（连跑三次 3.03/3.03/3.01s 不变） |
| 窄列基线（`SUM(score)`） | 0.10s |
| `innodb_buffer_pool_size` / `records` 表体 | 128MB / 290MB data + 43MB index |

结论：报告**已做列投影**（§十一 的 C1，`RecordColumnNameGuardTest` 守卫）、无 `ORDER BY`，
**SQL 侧无剩余空间**；那 ~3s 是**磁盘 I/O**（表体超过 buffer pool，重复读不变快），
另 ~2s 是 Jackson 解析。故改走 **stale-while-revalidate**：不追求更快，只让它别挡在用户前面。

**机制（`StatsCache.getOrLoadSwr`）**

| 项 | 做法 |
|---|---|
| 双 key | `dataKey`（值不变，TTL = 基准 ×10 = **30min**，兜住「后台一直不成功」的上界）+ `dataKey:fresh`（`"1"`，TTL = 基准 **180s**） |
| 读 | data 在 + fresh 在 → 命中；data 在 + fresh 没了（**时间到期**）→ **立即返回旧值** + 后台单飞重算；data 没了 → 阻塞现算 |
| 后台池 | 1~2 线程、有界队列 16、守护线程、`DiscardPolicy`（满则丢弃，下次读再触发）、`@PreDestroy` 关闭 |
| 单飞 | 后台重算复用原有 `LOCK_PREFIX` 锁，多实例/并发只算一次 |
| **正确性** | 写入 → `invalidateForWrite()` bump 全局版本 → key 段变 → 两把 key 皆空 → **仍阻塞现算新值**（时间到期才走秒回） |
| 降级 | Redis 不可用 → 直接现算；后台失败只记日志、留旧值到 30min 硬 TTL，之后回落阻塞 |

**关键前置（本轮发现的真实风险）**：报告现算体读线程绑定的请求上下文
（`RequestUtils.currentOrgId()` ×3、`RecordFilter.domainOrgId()` / `viewAllOrgs()`）。
后台重算线程里这些一律退化成 `"unknown"` 与 fail-closed，**会回填错误（甚至空）的报告**。
故在请求线程捕获 `ReportContext(orgId, domainOrgId, viewAllOrgs)` 快照显式传入
（`RecordFilter` 增 `buildForAggregate(orgId, filters, viewAllOrgs)` 加法式重载），
使现算体与线程无关 —— 与批任务 `qc_task.role` 快照同一做法。

**改动清单**：`StatsCache`（新增 `getOrLoadSwr` / `refreshAsync` / 双 key / 后台池，非 SWR 调用方行为不变）、
`RecordFilter`（新重载）、`StandardizationReportServiceImpl`（`ReportContext` + `computeReport(f, ctx)` + 改接 `getOrLoadSwr`）。
前端、其它 kind、表结构**均未改**。

**验收**

- 单测：`StatsCacheTest` 新增 6 条（新鲜命中 / 陈旧秒回且返回旧值 / 遗留值按陈旧 / 写入后阻塞且落 v1 / 反序列化失败现算 / Redis 故障现算），`mvn test` 全量 **572/572 通过**。

## 一、总体评价

**根因方向：后端 SQL 层，不是前端。**

病历列表的排序键是 `ORDER BY visit_time DESC, id ASC`（`RecordFilter.java:315`），而 `records` 表上**没有任何索引能匹配这个排序键**——因此**每一次列表查询都必须把该机构的全部 4 万行读出来做 filesort**（`EXPLAIN ANALYZE` 实测：`Sort: records.visit_time DESC, records.id` + `Index lookup ... rows=40000`）。在这条主因之上，还有两处放大器：

1. **后台批处理用偏移分页循环**：`QcServiceImpl.deductionStats` 与 `QcBatchServiceImpl.run` 都是 `while(true) { selectPage(new Page<>(pageNo, 1000), wrapper) }`，4 万条 = 41 页，**每页都重排一次全表**，实测扫完 4 万行需 **4.9 秒**（缓存态）/ **26.9 秒**（未缓存）。
2. **统计接口把全表载入 JVM 堆并重复解析 JSON**：`StatsServiceImpl.recordsFor()` 用 `selectList` 一次性拉 4 万行（≈320MB）进堆，`/api/stats/all` 对同一份列表连续调 4 次 `statsFor` → `agg` → `objectMapper.readValue(structured_data)`，**每条记录解析 5 次 3.7KB JSON**（合计 20 万次）。病历列表**首屏并发的 5 个接口**里，`/api/stats/overview` 与 `/api/governance/stats` 各需 **0.57 秒**（需 `grade`/`governed` 列，走不了覆盖索引）。

**前端侧基本健康，但也没有为大数据量做任何准备**：全仓库没有任何 >200 的 `pageSize` 调用，病历列表实际上限是 50（`PAGE_SIZES_STANDARD = [10,20,50]`），`el-table` 每次只渲染当前页。**前端从未一次性接收 4 万条，也从未全量渲染 4 万 DOM 节点**——「前端全量渲染导致卡顿」这一假设在本代码库**不成立**（详见附录 C）。但浏览器真机实测表明：`el-table` 的渲染成本是 **≈3ms/行、26.1 个 DOM 节点/行**，50 行 170ms、1000 行 2.97s、**4 万行外推 108 秒**（20000 行已把浏览器拖到 90 秒超时）。所以「业务要能检索 4 万条」这条约束，在**前端**这一侧必须靠**虚拟滚动**兑现，而不是靠限制条数。前端另有两个真实问题：「无请求取消/防抖」导致并发重查询把后端放大，以及深分页无防护。

### 综合评分：⭐ **2 / 5**

| 星级 | 含义 |
| --- | --- |
| ⭐⭐⭐⭐⭐ | 无需改动 |
| ⭐⭐⭐⭐ | 轻微优化即可 |
| ⭐⭐⭐ | 有优化空间但可用 |
| **⭐⭐** | **大数据量下明显退化，存在可定位的结构性缺陷** ← 当前 |
| ⭐ | 不可用 |

判分依据：功能正确、代码规范、索引与分页注释都写得很清楚（甚至已经预见到「3.5 万条量级需留意 deleteByFilter 与 clean」），**但索引未与排序键对齐、批处理仍用偏移循环**，导致 4 万条时列表页单次交互 0.2~1.0 秒、质控扣分统计 13~27 秒、统计看板约 10 秒。补齐索引 + 批处理改游标后，列表首页可降到 **1.8ms**（实测 98 倍提升），可回到 4~5 星。

## 三、分项问题清单

### P0（阻断业务）

---

#### P0-1 排序键 `visit_time DESC, id ASC` 无匹配索引，每次列表查询读全表 4 万行 + filesort

**【问题描述】**
`RecordFilter.build()` 末尾固定 `wrapper.orderByDesc("visit_time").orderByAsc("id")`。当前 `tcm_ehr` 库实测索引为：
`PRIMARY, idx_grade, idx_records_org, idx_records_visit_time, idx_registration_no, idx_status, uk_records_org_text_hash`。

- `idx_records_org (org_id)` 单列：只能定位机构，无法提供 `visit_time` 有序性 → 必须读全表再排序。
- `idx_records_visit_time (visit_time)` 单列：缺 `org_id` 前导列，机构过滤用不上。

`EXPLAIN ANALYZE` 实测（4 万行）：
```
-> Limit: 10 row(s)
-> Sort: records.visit_time DESC, records.id, limit input to 10 row(s) per chunk
-> Index lookup on records using uk_records_org_text_hash (org_id = 'ORG-A')  (rows=40000)
```

**实测耗时（4 万行）**

| 场景 | 当前（配置①） | 补索引后（配置②） | 提升 |
| --- | --- | --- | --- |
| 列表首页 `size=10`（全内存缓存） | **176.7 ms** | **1.8 ms** | **98×** |
| 列表首页 `size=50` | 288.3 ms | 3.1 ms | 93× |
| 列表首页 `size=200` | 364.0 ms | 11.3 ms | 32× |
| 列表首页 `size=10`（未命中缓存） | 705.6 ~ 1053.8 ms | — | — |
| 列表 + 时间区间筛选 | — | 0.13 ms | — |

> ⚠️ **关键坑**：`database-init.sql:86` 与 `data/migration-06-records-org-visit-time.sql` 声明的是**升序**复合索引 `idx_records_org_visit_time (org_id, visit_time)`，而它在当前库里**尚未执行**。但**即使执行了也解决不了本问题**——实测把该升序索引建上之后，执行计划里 `Sort` 依旧存在，优化器甚至没选它。原因：`visit_time DESC, id ASC` 这个「前降后升」的组合，任何**全升序**复合索引都无法满足。

**【优化方案】**

**方案 A（推荐，MySQL 8.0+，零代码改动）**
```sql
-- 与排序键逐字对齐的降序复合索引
ALTER TABLE records
  ADD INDEX idx_records_org_vt_id (org_id, visit_time DESC, id ASC);
```
实测 `EXPLAIN ANALYZE`：`Index lookup on records using idx_records_org_vt_id` —— **无 Sort**，首页 1.8ms。

**方案 B（兼容 MySQL 5.7，需改一处代码）**
MySQL 5.7 不支持降序索引。把次级排序键方向反转（`RecordFilter.java:315`）：
```java
// 原：wrapper.orderByDesc("visit_time").orderByAsc("id");
wrapper.orderByDesc("visit_time").orderByDesc("id");
```
配套索引（全升序）：
```sql
ALTER TABLE records ADD INDEX idx_records_org_vt_id (org_id, visit_time, id);
```
实测 `EXPLAIN ANALYZE`：`Index lookup on records using idx_asc3 (reverse)` —— **无 Sort**，0.116ms。

**注意事项（数据准确性，必须遵守）**
- ❌ **不要为了省排序而删掉次级键 `id`**。`RecordFilter.java:314` 的注释是对的：同 `visit_time` 的病历必须靠 `id` 决定先后，去掉它会在页边界出现**重复行 / 漏行**。
- ✅ 方案 B 把 `id ASC` 改成 `id DESC`，只改变「同一接诊时间内的显示先后」，**分页稳定性不受影响**（仍是全序），但会改变 UI 上同秒记录的排列顺序——需产品确认可接受。
- ✅ 建议同步把 `idx_records_org_visit_time (org_id, visit_time)` 迁移脚本执行掉（它虽不解决排序，但对 `COUNT(*) WHERE org_id=?` 等仍有用），并补齐 DDL 里另一个缺失的 `idx_department_visit_time`（见 P1-3）。
- 该索引会新增约 10MB 索引空间（4 万行实测索引总量 10.1MB），可忽略。
- 建索引请用 `ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE`（MySQL 8 支持在线 DDL），避免锁表。

#### P0-2 后台批处理用偏移分页循环，扫完 4 万行需 4.9~26.9 秒

**【问题描述】**
`QcServiceImpl.deductionStats`（`QcServiceImpl.java:378`）与 `QcBatchServiceImpl.run`（`QcBatchServiceImpl.java:485`）都是同一形态：

```java
int pageNo = 1;
while (true) {
    Page<Record> page = baseMapper.selectPage(new Page<>(pageNo, BATCH_PAGE_SIZE), wrapper); // 1000/页
    ...
    if (records.size() < BATCH_PAGE_SIZE) break;
    pageNo++;
}
```

两个放大器：
1. 每页 `ORDER BY visit_time DESC, id ASC LIMIT offset,1000` → **每页都重排一遍剩余全表**，总代价 O(页数 × 全表)，而不是 O(全表)。
2. MyBatis-Plus `selectPage` 默认 `searchCount=true` → **每页额外多发一次 `COUNT(*)`**，41 页就是 41 次。

**实测耗时（4 万行，投影 `id, grade, qc_results`，扫完全部 4 万行）**

| 扫描方式 | 配置① 当前索引 | 配置② 补索引后 |
| --- | --- | --- |
| offset 循环（现实现） | **4878.6 ms** | 2077.6 ms |
| **游标（keyset）循环** | 3553.3 ms | **216.5 ms** |
| 未命中缓存时 offset 循环 | **26909.8 ms** | — |

配置② 下 **游标 vs offset = 9.6×**；配置①→② 的游标循环 = **16.4×**。

**【优化方案】**

**后端改造（推荐）**
1. **批处理改用主键/游标分页**，彻底去掉 `OFFSET`：
   ```java
   // 首页
   ... WHERE org_id = ? ORDER BY visit_time DESC, id ASC LIMIT 1000
   // 后续页：以上一页末条的 (visit_time, id) 为锚点
   ... WHERE org_id = ?
         AND (visit_time < :lastVt OR (visit_time = :lastVt AND id > :lastId))
       ORDER BY visit_time DESC, id ASC LIMIT 1000
   ```
   实测（配置②）扫完 4 万行仅 **216.5ms**，且**页数无关**——第 1 页与第 40 页耗时相同。
2. **关掉逐页 COUNT**：批处理只需要「扫到没有为止」，不需要总数。用 `Page<>(pageNo, size, false)`（`searchCount=false`）或直接走 `selectList` + 游标。41 次 COUNT 累计约 669ms。
3. 若必须保留分页语义，至少把 `wrapper` 的 `orderByDesc("visit_time").orderByAsc("id")` 在**批处理场景**下换成只按 `id` 排序（`FiltersDTO` 重载的调用方是聚合/批处理，排序对它们无意义——`RecordFilter.java:312` 的注释已经点出这一点），配 `(org_id, id)` 索引即可。

**注意事项（数据准确性）**
- 游标分页依赖 `(visit_time, id)` 是**严格全序**。`id` 是主键（`varchar(36)` UUID），本身唯一 → 组合键唯一，**不会漏行也不会重复**。
- 锚点必须用「上一页**最后一条**」而不是「第一条」，且必须**包含 `id`**（同 `visit_time` 有多条时只比较 `visit_time` 会漏）。
- 若处理过程中数据被并发删除/新增，游标分页可能出现边界抖动——批处理场景建议在同一事务/快照内完成，或接受「本轮可能漏掉刚插入的行」（与现状的偏移分页相比并无更差）。
- **不要**通过「只处理前 N 条」来提速（`MAX_SCAN_RECORDS = 40000` 已是业务上限，不可再降）。

#### P0-3 `/api/stats/all` 一次性把 4 万行（≈320MB）载入 JVM 堆，且每条记录重复解析 5 次 JSON

**【问题描述】**
`StatsServiceImpl.recordsFor()`（`StatsServiceImpl.java:246`）：
```java
QueryWrapper<Record> wrapper = RecordFilter.build(RequestUtils.currentOrgId(), filters);
return baseMapper.selectList(wrapper);   // 无分页、无投影
```
`/api/stats/all`（`:125-133`）拿到这份 list 后连续调用：
```java
vo.setDisease(statsFor(records, "disease"));       // agg(records, "diseases")     → 解析 1 次/条
vo.setSymptom(statsFor(records, "symptom"));       // agg(records, "symptoms")     → 解析 1 次/条
vo.setPattern(statsFor(records, "pattern"));       // agg(records, "patternList")  → 解析 1 次/条
vo.setPrescription(statsFor(records, "prescription")); // agg("formulaList") + agg("herbs") → 解析 2 次/条
```
而 `agg` → `extractFromStructured`（`:340`）每次都执行 `objectMapper.readValue(r.getStructuredData(), ...)`。

**合计：4 万条 × 5 次 = 20 万次 3.7KB JSON 解析**，外加 4 万行 × ~8KB ≈ **320MB 一次性进堆**。

**实测参照**：库内仅 500 行时，`/api/stats/all` 已需 **120ms**，而同页的 `/api/stats/overview` 只需 9ms、`/api/stats/extra` 40ms —— 线性外推到 4 万行约 **9~10 秒**，并有 OOM 风险（`selectList` 把全表实体一次性物化）。

**【优化方案】**

**后端改造（按优先级）**
1. **解析一次、多处复用**：把 `List<Record>` 先映射成 `List<Map<String,Object>>`（或只抽出 `diseases/symptoms/patternList/formulaList/herbs` 五个数组），**每条只 `readValue` 一次**。仅此一项即可把 20 万次解析降到 4 万次（约 5 倍）。
2. **只取需要的列**：`selectList` 前加 `.select("id", "structured_data")`，避免把 21 个文本列 + `qc_results` 一起拉进堆。
3. **改到 SQL 侧聚合**：用 `JSON_TABLE` 把 `structured_data` 展开成行后在 SQL 里 `GROUP BY` 计数，只把 Top10 结果带回 JVM（`records` 表数据 314MB，全表在 DB 侧聚合仍可接受）。
4. **加缓存**：统计结果是「准实时」语义（页面已有 `FreshnessTag` 提示读取时刻），可加 60s 缓存。系统已有 Redis（`spring.data.redis` 已配置），直接复用。
5. **流式/分批**：若短期不动 SQL，至少把 `selectList` 改成游标分批（1000/批）并在每批内解析一次，避免 320MB 堆峰值。

**注意事项（数据准确性）**
- 缓存 TTL 需与业务确认。医疗数据要求实时性的口径下，建议 **60s 短 TTL + 写入病历/跑完质控后主动失效**，而不是长 TTL。
- 「解析一次复用」不改变任何统计口径，属于纯性能优化，**风险最低、收益明确**，建议先做这一步。
- 用 `JSON_TABLE` 时注意 `structured_data` 可能为 NULL / 非合法 JSON（未结构化的旧病历），SQL 侧要能容忍，不能因此丢记录——现有 `extractFromStructured` 的 fallback（证候回退到 `pattern` 原始列）语义要在新实现里保留。

#### P1-1 偏移分页在深页衰减（前端 `jumper` 可直接跳到第 4000 页）

| --- | --- | --- | --- |
| 首页 `LIMIT 0,10` | 176.7 ms | 1.8 ms | 2.1 ms |

| 第 4000 页 `LIMIT 39990,10` | **832.1 ms** | 133.7 ms | **2.2 ms** |

即使补了正确索引，`LIMIT 39990,10` 仍要「跳过 39990 个索引项 + 40000 次回表」，无法靠索引消除。

- **前端**：`jumper` 输入页码时给出加载提示（现有 `searching` 状态已能显示「正在检索病历…」），避免用户以为页面卡死。
- **注意**：不要用「限制最大页码 / 最大条数」来规避（违反本次硬性约束）。

#### P1-2 `SELECT *` 把 2 个 JSON + 21 个文本列全拉进 JVM，且每行解析 JSON 只为读一个布尔值

**【问题描述】**
`RecordServiceImpl.searchRecords`（`RecordServiceImpl.java:457`）：
```java
QueryWrapper<Record> wrapper = RecordFilter.build(RequestUtils.currentOrgId(), dto); // 未 .select(...)
Page<Record> p = baseMapper.selectPage(new Page<>(page, size), wrapper);             // → SELECT *
for (Record r : p.getRecords()) {
    boolean manual = StructuredDataMeta.isManuallyEdited(objectMapper, r.getStructuredData()); // 完整解析 3.7KB JSON
    vo.getRecords().add(new SearchVO.Item(r.getId(), summarize(r), ...));                   // 实际只用 3 个字段
}
```

**实测体积（4 万行临时库）**：`structured_data` 均值 **3748 字符**、`qc_results` 均值 173 字符；单条整行 = **51244 字节 / 10 条**（≈5.1KB/行）。
**线上真实数据采样（500 行）**：`structured_data` 均值 **3471**、最大 **4562** 字符；`qc_results` 均值 166 字符。

即：列表每页白白从 DB 传 5.1KB × N，然后每行再解析 3.7KB JSON，只为拿 `_meta.manuallyEdited`。

**接口载荷实测（不是问题，仅作对照）**：pageSize 10/20/50/200 → **2074 / 4083 / 10085 / 40193 字节**。

**【优化方案】**

**后端改造**
1. **加字段投影**：`wrapper.select("id", "grade", "visit_time", "gender", "age", "score", "chief_complaint", "tcm_diagnosis", "western_diagnosis")` —— 把 21 个文本列 + 2 个 JSON 收敛到列表真正需要的 9 列。
2. **把 `manuallyEdited` 落成标量**：新增 `manually_edited TINYINT` 列（或在 `qc_results` 里冗余），列表查询彻底不再触碰 `structured_data`。这是收益最大的一步——`summarize()` 只需 3 个短文本字段。
   - 迁移：新增列 + 一次性回填（`UPDATE records SET manually_edited = ...` 由应用层解析后回写），此后由写入路径维护。
3. 若暂不改表结构，至少把 `isManuallyEdited` 的解析结果缓存（同一次请求内按 id 去重），或改成轻量字符串包含判断。

**实测参考**：4 万行下「投影不含大字段」vs「SELECT *」首页 = **122.8ms → 1.2ms**（补索引后）。加索引后列表只读 10~200 行，投影对**列表接口**收益有限；但对**批处理**（要读 4 万行）收益显著。

**注意事项（数据准确性）**
- `summarize()` 的回退链是「主诉 → 中医诊断 → 西医诊断」，投影必须包含全部三个字段，**漏一个会让摘要显示错**。
- 新增 `manually_edited` 列必须与 `_meta.manuallyEdited` 严格同源，且要覆盖**所有写入路径**（导入、单条新增、编辑、NLP 重解析、质控重算）。建议在回填后用一次性校验脚本比对「列值 vs JSON 解析值」是否全等，再切换读取源。

#### P1-3 筛选列无索引：`department` / `pattern` 全表扫描

**【问题描述】** 实测（4 万行）：

| 查询 | 当前 | 补索引后 |
| --- | --- | --- |
| `COUNT(*) WHERE org_id=?` | 5.6 ms | 5.2 ms（本就走覆盖索引，**不是问题**） |
| `COUNT(*) + department=?` | 87.3 ms | **2.4 ms** |
| `SELECT DISTINCT department WHERE org_id=?`（科室下拉） | 86.0 ms | **8.1 ms** |
| `COUNT(*) + grade=?` | 12.0 ms | 16.4 ms（`idx_grade` 已够用） |
| `COUNT(*) + pattern LIKE '%肝郁%'` | 90.8 ~ 976 ms | 90.9 ~ 585 ms（**前导通配，索引无效**） |
| 列表 + `department` 筛选 | 152.5 ms | **1.7 ms** |

**【优化方案】**
- **后端**：补 `idx_department_visit_time (department, visit_time)`（DDL 已声明但线上缺失）→ 改为与查询同形的 `(org_id, department)` 或 `(org_id, department, visit_time DESC, id ASC)`。实测 `(org_id, department)` 即可让 `COUNT + department` 变成覆盖索引扫描（3.1ms）并把 `DISTINCT department` 降到 8.1ms。

  2. 复用已有的 **Elasticsearch**（项目已配 `windows-es` 容器）做病历检索，`pattern` 走 ES；
  3. 若 `pattern` 实际是**标准化后的证候名**，优先改成**等值匹配**（`pattern = ?`）走字典下拉，而不是模糊匹配——既快又准。
- **前端**：`TermInput` 已有词典联想，可引导用户从词典选标准证候名，从源头减少 `%...%` 查询。
- **注意**：`department` 下拉（`useDepartments`）在 `Records.vue` / `Qc.vue` / `Review.vue` 都会调，建议前端做会话级缓存（后端也可加短 TTL 缓存）。

#### P1-4 `deleteByFilter` 一次性取全部 id 进内存

**【问题描述】**
`RecordDeleter.deleteByFilter`（`RecordDeleter.java:73`）：

#### P1-5 前端无请求取消 / 无防抖 → 并发重查询把后端放大

**【问题描述】**
`usePagedList` 只有**响应侧取号**（`seq`，latest-wins，慢的旧响应被丢弃），**没有 `AbortController`**；`request.js` 里也没有 `signal`。实测代码走查确认全仓库无请求取消。

后果：用户快速切换筛选 / 连点翻页时，N 个请求同时在飞，**每一个都在后端跑一次 4 万行 filesort**（未命中缓存时每次 0.7~1.05s）。前端虽然只采用最后一个响应，但后端已经白干 N 次，且占用 Hikari 连接池（`maximum-pool-size: 20`）。

`Review.vue` 一进页就并发 4 个 `searchRecords`（3 个 `pageSize=1` 拿 total + 1 个列表）→ 4 次全表排序。

**【优化方案】**
- **前端**：
  1. `request.js` 支持传入 `signal`；`usePagedList.load()` 在发起新请求前 `abort()` 上一个（取号逻辑保留，作为双保险）。
  2. 筛选输入（`TermInput` 的关键词、`el-select` 的科室）加 **300ms debounce**，`el-date-picker` 的 `change` 事件再触发查询（现在是每次变更即查）。
  3. 翻页按钮加「请求进行中禁用」（`searching` 已存在，接到 `:disabled` 即可），避免连点。
- **后端**：
  4. 新增轻量 `POST /api/records/count`（**只执行 COUNT，不做 SELECT**），供 `pageSize=1` 那类「只要总数」的调用替换。实测 `COUNT(*) WHERE org_id=?` 仅 5.5ms，比「COUNT + SELECT 全表排序」便宜一个数量级。
  5. 现有 `pageSize=1` 的调用点（`Records.vue:446`、`Review.vue:252-254`、`NlpBatchPanel.vue:241`）改用它。
- **注意**：`AbortController` 取消的是**客户端等待**，Spring MVC 侧不一定能中断已在执行的 SQL。所以**根治仍要靠 P0-1 的索引**（把单次查询从 700ms 降到 2ms），取消只是减少排队与连接占用。

#### P1-6 首屏并发的两个聚合接口各需 0.57 秒（缺覆盖索引）

**【问题描述】**
进 `/records` 实测同时发出 5 个后端接口。其中两个是**全量聚合**：

```sql
-- RecordMapper.selectOverview（/api/stats/overview）
SELECT COUNT(*) AS totalRecords,
       COALESCE(SUM(CASE WHEN grade = '合格'   THEN 1 ELSE 0 END), 0) AS qualifiedCount,
       COALESCE(SUM(CASE WHEN grade = '待复核' THEN 1 ELSE 0 END), 0) AS pendingReviewCount,
       COALESCE(SUM(CASE WHEN grade = '无效'   THEN 1 ELSE 0 END), 0) AS invalidCount
FROM records WHERE (#{viewAll} = 1 OR org_id = #{orgId})

-- RecordMapper.selectGovernanceStats（/api/governance/stats）形态同上，另用 governed 列
```

两个问题叠加：

1. **`(#{viewAll} = 1 OR org_id = #{orgId})` 这种「参数化 OR」写法**会让优化器难以稳定地按 `org_id` 收窄（实测虽仍选中 `idx_records_org`，但语义上等同于给索引选择制造障碍）。建议拆成两条 SQL 由 Java 侧二选一。
2. **聚合需要 `grade` / `governed` 列，而 `idx_records_org (org_id)` 不含它们** → 无法 index-only，必须回表读 4 万行完整聚簇行。

**实测（4 万行）**

| 查询 | 当前 | 补覆盖索引后 | 提升 |
| --- | --- | --- | --- |
| `selectOverview` | **578.1 ms** | **11.9 ms** | 48× |
| `selectGovernanceStats` | **570.7 ms** | **11.9 ms** | 48× |
| `selectDepartments`（已补 `(org_id,department)`） | 12.4 ms | — | — |
| 对照：纯 `COUNT(*) WHERE org_id=?` | 6.4 ms（覆盖索引） | — | — |

**【优化方案】**
```sql
ALTER TABLE records ADD INDEX idx_records_org_grade_gov (org_id, grade, governed);
```
实测 `EXPLAIN ANALYZE`：`Covering index lookup on records using idx_records_org_grade_gov (org_id = 'ORG-A')` —— **纯索引扫描，不回表**。

**注意事项（数据准确性）**
- 该索引只覆盖 `grade` / `governed`。若后续统计新增依赖列（如 `status`、`score`），需要把列追加到索引尾部或另建覆盖索引，**不要**因为「已经有了」就假设任意聚合都走索引。
- 拆 `viewAll` 分支时，两条 SQL 的**数据域口径必须与 `RecordFilter` 完全一致**（管理员看全部 / 其余看本组），否则看板数字会与病历列表对不上——这是现有注释（`RecordMapper.java:33-36`）已经强调过的风险。

#### P2-1 无虚拟滚动（当前不是瓶颈，但会限制 `pageSize` 上限）

**【问题描述】** `RecordTable.vue` 用普通 `el-table` + `:max-height="420"`，**全量渲染当前页**；全仓库无 `row-key` / `reserve-selection` / `el-table-v2` / 虚拟滚动组件。

**【为什么现在不是瓶颈】** 病历列表 `PAGE_SIZES_STANDARD = [10,20,50]`，`pageSize` 默认 10，后端 `@Max(200)`；全仓库**没有任何 >200 的 `pageSize` 调用**（`PAGE_SIZES_WIDE = [20,50,100,200]` 只被 `Dictionary.vue` 的词典页使用，与病历无关）。所以前端每次最多渲染 50 行 DOM。

**【实测代价（浏览器真机，Vue 3.5.42 + Element Plus 2.14.5，列结构与 `RecordTable.vue` 逐列对齐）】**

| 行数 | 渲染耗时 | 表格内 DOM | 最长长任务 | JS 堆增量 |
| --- | --- | --- | --- | --- |
| 10（默认 pageSize） | 38.8 ms | 329 | 0 | 4.0 MB |
| 50（当前上限） | **170.5 ms** | 1373 | 130 ms | 14.8 MB |
| 200（后端上限） | 558.0 ms | 5290 | 433 ms | 60.6 MB |
| 1000 | 2974.1 ms | 26179 | 2229 ms | 227.9 MB |
| 5000 | 15811.5 ms | 130623 | 12394 ms | 1197.6 MB |
| 10000 | 26408.9 ms | 261179 | 26384 ms | 1109.1 MB |
| 20000 | **超时 90s（浏览器卡死）** | — | — | — |

**边际成本 ≈ 2.1~3.3 ms/行、恒定 26.1 个 DOM 节点/行** → 外推 **4 万行 ≈ 108 秒渲染 + 104 万 DOM 节点**。

**这张表回答了两个问题**：
- 为什么现在不卡：`pageSize ≤ 50` 时渲染只占 39~171ms，相对后端 0.2~1.0s 的查询耗时不是主因；
- 为什么不能放开 `pageSize`：**一旦按「业务需要检索 4 万条」直接放宽到一次拉全量，浏览器会彻底卡死**。所以「不限制最大查询条数」这个约束，在**前端**这一侧必须靠**虚拟滚动**来兑现，而不是靠限制条数。

**【优化方案（前瞻性，非当前必须）】**
- 若未来需要「一屏看更多」或「导出/全量勾选」，再引入虚拟滚动（`el-table-v2` + `AutoResizer`，或 `@vueuse/core` 的 `useVirtualList`）。
- 引入时必须同时补 `row-key="id"` + `reserve-selection`，否则跨页勾选会错乱。
- **不要**为了「看起来流畅」而把 `pageSize` 上限从 200 往下调——这属于本次明令禁止的「限制最大查询条数换性能」。

#### P2-2 勾选不跨页，「全选」语义需在 UI 澄清

**【问题描述】** `onSelectionChange = rows => selectedIds.value = rows.map(r => r.id)`；无 `row-key` / `reserve-selection`，翻页即清空勾选。表格表头的「全选」复选框**只选中当前页**（≤50 条）。

**【影响评估】** **不影响功能正确性**：
- `handleBatchDelete` 提交的是当页勾选的 id，后端 `filterAccessibleIds` 会再按数据域过滤（安全）；
- 批量质控提交的是 **`filters`**（`Qc.vue:478` → `recomputeQc({ filters: {...} })`），不是 id 列表，后端按 filter 重新取数 —— 这是**正确且高效**的设计，不需要把 4 万个 id 传到前端再传回。

**【优化方案】**
- 前端：在「共 {{ total }} 条」旁边补一句说明，把「勾选 = 选中本页 N 条」与「按筛选范围操作 = 作用于全部 {{ total }} 条」明确区分（现在 `danger-zone` 的 `danger-note` 已部分做到，可再强化）。
- 若产品确实需要「跨页全选 4 万条再批量删除」，正确做法是**提交 filters**（复用 `delete-by-filter`），而不是把 4 万个 id 传到前端——既省流量又避免 id 列表被篡改。

#### P2-3 统计结果无缓存

**【问题描述】** `/api/stats/all`、`/api/stats/extra`、`/api/qc/deduction-stats` 每次进入页面都重算，即使筛选条件完全没变。

**【优化方案】**
- 后端：对「同一 orgId + 同一筛选条件」的统计结果加 Redis 缓存，TTL 60s；病历写入 / 质控重算 / 批量任务完成后**主动失效**。
- 前端：`Qc.vue` 的 `getDeductionStats` 在筛选条件未变化时不重复请求（现在 `onMounted` 与「查询」按钮都会触发）。
- **注意**：医疗数据实时性优先，TTL 不宜过长；页面已有 `FreshnessTag` 提示「数据为本次页面读取时刻」，可复用它向用户说明缓存新鲜度。

**（现状核实）** 全仓库**没有任何查询缓存**：无 `@Cacheable` / `@EnableCaching` / `CacheManager`；Redis（`StringRedisTemplate` / Redisson）目前只用于 JWT token（`JwtUtil`）与分布式锁。所以这一项不是「调优现有缓存」，而是**从零引入**——收益明确（`/api/stats/*`、`/api/qc/deduction-stats` 都是纯读聚合），但需要先把 P0/P1 的索引问题解决，否则缓存只是把慢查询的结果存起来，冷启动仍然慢。

---

#### P2-4 排序功能实际未实现（业务要求 vs 代码现状的差距）

**【问题描述】**
本次硬性约束写着「病历列表需要支持检索、**筛选、排序**、分页、勾选、批量质控」。但代码走查结果：

| 检查项 | 结果 |
| --- | --- |
| 前端 `el-table` 是否可排序 | ❌ 全仓库无 `sortable` / `sort-change` / `default-sort` |
| 后端是否接受排序参数 | ❌ `SearchDTO` 无 `sort` / `orderBy` 字段 |
| 排序键 | 硬编码 `ORDER BY visit_time DESC, id ASC`（`RecordFilter.java:97` 与 `:315`） |

即：**当前是「固定排序」，不是「用户可排序」**。这不是性能缺陷，而是功能覆盖差异——但它**直接影响性能方案的走向**：如果后续要补「按评分排序 / 按接诊时间正序 / 按分级排序」，那么：

- **每新增一个可排序列，都需要一条与该排序键对齐的复合索引**（`(org_id, score DESC, id ASC)` 等），否则每个新排序都退化成 4 万行 filesort（回到 P0-1 的问题）；
- 且次级键 `id` 必须一起进入索引，否则分页稳定性仍会破。

**【优化方案】**
- **后端**：`SearchDTO` 增加受白名单约束的 `sortBy` / `sortOrder`（**不要**把用户输入直接拼进 `orderBy`——SQL 注入风险）；`RecordFilter` 按白名单映射到固定列名。
- **后端**：为白名单里每个可排序列准备对应的 `(org_id, <sortCol> <dir>, id ASC)` 索引；或者先只开放 `visit_time`（已有索引），其余列在明确需求后再加。
- **注意**：次级键方向必须与索引定义一致（见 P0-1 的坑）。

#### P2-5 深分页无防护（前端交互层）

见 P1-1。补充前端侧建议：`el-pagination` 的 `jumper` 允许直接输入第 4000 页，实测该请求在 4 万条下为 832ms（当前索引）/ 133ms（补索引后）。建议在 `jumper` 提交时复用已有的 `searching` 状态显示「正在检索病历…」（现已具备），并在 `jumper` 输入超过某个量级时给出提示。**不要**限制可跳页码（违反本次约束）。

| 3 | 补 `(org_id, grade, governed)` 覆盖索引 | 首屏 `/api/stats/overview` **578ms → 11.9ms**；`/api/governance/stats` **571ms → 11.9ms（48×）** | 纯 DDL |

| 顺序 | 动作 | 预期收益 |
| --- | --- | --- |
| 6 | `searchRecords` 加 `.select(...)` 字段投影；`manually_edited` 落列 | 每页少传 5.1KB/行；批处理读 4 万行时收益最大 |

| 8 | 导出链路 `filterQualified` 改流式分批 | 内存恒定；证候筛选的 4 万次 JSON 解析降到每批一次 |

| 11 | 新增 `/api/records/count` 端点，替换所有「只取 total」的 `pageSize=1` 调用 | 每次省一次全表排序 |

### 第 3 批（P2，择机）

12. `pattern` 模糊查询：全文索引 / ES / 改等值匹配三选一
13. 统计接口加 Redis 短 TTL 缓存 + 主动失效（**当前零缓存**，属从零引入）
14. 虚拟滚动（**实测 4 万行渲染需 108 秒**，仅在放开 `pageSize` 或做「全量勾选」时才需要）
15. 勾选语义在 UI 上澄清
16. 若补「用户可排序」：为每个白名单排序列建对应 `(org_id, <col> <dir>, id ASC)` 索引

### 优先级判断依据（对应本次审查要求）

- ✅ **先排查「接口一次性返回海量数据 / 全量 DOM 渲染」**：实测两者**都不成立**——接口每页最多 40KB（pageSize=200），前端每次最多渲染 50 行。因此**不把这两项列为 P0**，避免把优化资源投到错误方向。
- ✅ **其次 SQL 索引**：这是**真正的根因**，列 P0-1。
- ✅ **再其次 count 统计**：`COUNT(*) WHERE org_id=?` 本身只要 5.5ms（覆盖索引），**不是瓶颈**；但「每次 `selectPage` 都发一次 count」在批处理里被放大 41 倍，列 P0-2。带筛选的 count（`department` / `pattern`）因缺索引而慢，列 P1-3。
- ✅ **最后前端数据处理逻辑**：前端逻辑均为 O(当前页)，无 O(n²)，无全量遍历，**无需改动**。

| **多用户并发压测** | ⚠️ 未做 | 单请求成本已量化；并发放大风险已从代码层指出（Hikari `maximum-pool-size: 20`、无请求取消），但未做并发基准 |
| **导出接口的端到端耗时** | ⚠️ 未实测 | 只做了代码层定位（`filterQualified` 全量 `selectList` + 逐条 JSON 解析），未构造 4 万条导出实测 |
| **`/api/stats/extra`、`/api/stats/standardization-report` 在 4 万条下的成本** | ⚠️ 未逐一实测 | 已知它们与 `/api/stats/all` 走同一个 `recordsFor()` 全量 `selectList`，结论可类推（P0-3） |

**另外澄清一处容易误判的地方**：`el-table` 无虚拟滚动、勾选不跨页，这两点属实（见 P2-1 / P2-2），但在当前 `pageSize ≤ 50` 的约束下**不构成卡顿原因**。把它们当成 4 万条卡顿的根因会是方向性错误。

### D.1 方法

项目自带的 Vue **3.5.42** 与 Element Plus **2.14.5** 被复制到独立目录（`D:\tmp\ai-review\bench\`）搭建基准页，

### D.3 真实页面（dev server `:3000`，后端库内 500 行）

| 指标 | 实测值 |

### D.4 结论

1. **前端不是 4 万条卡顿的根因**：当前 `pageSize ≤ 50`，渲染只占 39~171ms。
2. **但前端也没有为「4 万条」做任何准备**：无虚拟滚动时 4 万行需要 108 秒——所以「不限制最大查询条数」这一约束在**前端**只能靠**虚拟滚动**兑现（P2-1）。
3. **首屏并发 5 个接口**，其中 2 个聚合接口在 4 万条下各 0.57s（P1-6）——首屏体验由最慢的那个决定。

## 附录 E · 与业务硬性约束的对应

| 约束 | 本报告是否遵守 |
| --- | --- |
| 业务不可简化（检索/筛选/排序/分页/勾选/批量质控全保留） | ✅ 全部方案均保留现有功能；排序键只改次级键方向（方案 B）或完全不动（方案 A） |
| 数据分页/筛选/总数必须准确，不可丢包/总数错误/勾选错乱 | ✅ 明确**禁止**删除次级排序键 `id`（会导致页边界重复/漏行）；游标分页用 `(visit_time, id)` 唯一全序；`total` 与列表同 wrapper 同口径；勾选现状无错乱（仅不跨页，已在 P2-2 说明） |
| 禁止用「限制最大查询条数」换性能 | ✅ 本报告**无一条**方案涉及降低 `pageSize` 上限、截断查询条数或限制最大页码。全部方案是：索引对齐、字段投影、游标分页、SQL 侧聚合、缓存、请求取消 |
| 区分网络耗时 / 后端查询耗时 / 前端 JS 计算渲染耗时 | ✅ 后端 SQL 耗时单独实测（附录 B.1/B.2）；接口往返单独实测（附录 B.4，含 500 行时的固定开销 ~13ms）；前端 JS 经代码走查确认为 O(当前页)，未做独立实测（因前端从未承载 4 万条，见附录 C） |

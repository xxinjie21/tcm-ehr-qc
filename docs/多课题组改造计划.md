## 一、背景：现状的三个问题

1. **`管理员` 是 `审核员` 的严格超集** —— 34 个 `@RequireRole` 里「仅审核员」**0 处**。这不是职责分离，只是功能裁剪。

2. **`grade='待复核'` 被当成权限维度用**。而 `grade` 是质控评分产出的**业务结论**（合格/待复核/无效）。把它接到授权决策上，造成两个具体后果：
   - 审核员复核通过一份病历后，**立刻失去访问它的权限**（`RecordFilter:81` + `AiServiceImpl:531`）
   - 一次批量重算会**批量翻转可见性**（`QcServiceImpl:283` 改写成百上千条 `grade`），用户没做任何操作，页面内容就变了

3. **复核队列其实不依赖 `grade`** —— `ReviewServiceImpl:71-74` 用的是 `review_tasks.status='pending'`。`grade` 分域是重复且粗糙的近似。

**改造后定位**：系统面向多课题组共用 —— 各组数据互相隔离，共用一套配置（质控规则/词典/LLM），管理员管组建与审批，组长管本组成员。

## 三、权限模型

### 3.1 角色分两层（作用域不同，不塞进同一枚举）

```
users.role          {管理员, 用户}                    ← 系统级
group_members.role  {owner(组长), member(组员)}        ← 组内级
```

### 3.2 权限矩阵

| 身份 | 本组数据 | 跨组数据 | 成员管理 | 共用配置写 | 组建/审批 | 日志可见 |
|---|---|---|---|---|---|---|
| 管理员 | ✅（**暂定，可一键收紧**） | ✅（同上） | ❌ | ✅ | ✅ | **全部** |
| 组长 owner | ✅ | ❌ | ✅ 本组 | ❌ | ❌ | **仅自己** |
| 组员 member | ✅ | ❌ | ❌ | ❌ | ❌ | **仅自己** |
| 待分配池（无组） | ❌ | ❌ | ❌ | ❌ | ❌ | 仅自己 |
| 审批中 | ❌ | ❌ | ❌ | ❌ | ❌ | 仅自己 |

**两条口径的由来与走向**

1. **日志 = 普通用户只看自己的**（用户原话）。服务端强制：`GET /api/logs`、`/actions`、`/export` 三接口在非管理员时追加 `operator = 当前用户名` 条件。参考实现同 `ILogService.listRecentByOperator`（`operation_log` 已有 `idx_operator` 索引）。副作用：`keyword`（匹配操作人/对象/详情）仍可搜到别人日志的能力在强制条件下被关闭 —— 这是"只看自己"的必然结果。
2. **管理员当前「能看数据」是暂定值**。用户要求：先放开，将来要改成"不能看"，且**改动要小**。做法见 §4.4 —— 收敛到一个配置开关，改动点只有一处，数据层零改动。

### 3.3 状态机

```
用户注册 ──┬─ 只注册 ──────────────→ users.status=pending（待分配池）
           │                          无组 → 看不到任何数据
           │
           └─ 注册 + 申请建组 ──────→ research_groups.status=pending
                                      users.has_pending_group=1
                                      从待分配池隐藏（避免被组长重复拉走）
                                              │
                                    管理员审批 │
                              ┌───────────────┴───────────────┐
                          通过 │                          拒绝 │
                              ▼                              ▼
                    groups.status=active              groups.status=rejected
                    has_pending_group=0               code 改写为 rej_<id>_<原code>
                    users.status=active                  （释放编码供他人申请）
                    申请人成为 owner                     users 回待分配池
                                                          可立即重新申请
                              │
                    组长从池里加组员 → role=member
                    全部组员可见本组数据
```

- 管理员可 `stopped`（停用组）：停用后组员**不能登录**，数据保留不删；可 `activate` 恢复。
- `research_groups.code` 有 UNIQUE 约束 → 拒绝时改写 code，避免编码被永久占死。

## 四、身份解析机制（本次新增的核心设计）

### 4.1 每请求解析组，而不是放进 JWT

| 项 | 来源 | 生效时延 | 理由 |
|---|---|---|---|
| `userId` / `username` / `role` | JWT claim | 最长 24h（`jwt.expire-hours=24`） | 角色变更低频，由管理员操作 |
| **`groupId` / 组内角色** | **每请求查 `group_members`** | **立即** | 移除成员/转让组长/停用组必须立即生效，不能等 24h |

`JwtInterceptor.preHandle` 增加：按 `userId` 查组，把 `currentGroupId` / `currentGroupRole` 写入 request 属性。

**查询必须同时满足两个条件，否则出现两个真实漏洞：**

```sql
-- 取该用户的"主组"，且该组必须处于生效状态
SELECT m.group_id, m.role
  FROM group_members m
  JOIN research_groups g ON g.id = m.group_id
 WHERE m.user_id = ?
   AND m.is_primary = 1          -- ① 一人多组时必须显式取主组，否则返回哪组不确定
   AND g.status = 'active'       -- ② 组被停用后必须查不到
```

| 漏掉 | 后果 |
|---|---|
| 漏 ① `is_primary = 1` | 表上是 `UNIQUE(group_id, user_id)`，**允许一人多组**；不指定主组时取到哪组取决于 SQL 返回顺序 → **同一用户不同请求可能看到不同数据** |
| 漏 ② `g.status = 'active'` | 停用组只挡了登录，`group_members` 的行仍在 → 查组照常返回 `groupId` → **旧 token 在 24h 内照样能看数据**（停用形同虚设） |

> 配套索引：`INDEX(user_id, is_primary)`（`group_members` 建表时即加）。

**可用性耦合（必须知道）**：`JwtInterceptor` 从「纯解析 JWT、不碰 DB」变为**每请求查库**。DB 不可用时若直接抛异常，**全站 500**（含登录与 LLM 配置读取）。建议：解析失败时**降级为「无组」**（走 §4.3 的 fail-closed，用户看到空态而非报错），并把 DB 故障与权限拒绝在日志上区分开。

> 代价是每请求一次索引查询。本项目规模下可忽略，换来"移人/停用立即生效"。

### 4.2 身份访问器（`RequestUtils` 现状缺 `currentUserId`）

`JwtInterceptor` 已写入 `request.setAttribute("currentUserId", …)`，但 `RequestUtils` **没有暴露它**。需补：

```java
public static final String ATTR_USER_ID   = "currentUserId";     // 新增
public static final String ATTR_GROUP_ID  = "currentGroupId";    // 新增
public static final String ATTR_GROUP_ROLE= "currentGroupRole";  // 新增
public static String currentUserId()   { return attr(ATTR_USER_ID); }
public static String currentGroupId()  { return attr(ATTR_GROUP_ID); }
public static String currentGroupRole(){ return attr(ATTR_GROUP_ROLE); }
```

### 4.3 Fail-closed：无组用户必须"查不到数据"

`RecordFilter.build(groupId, …)` 在 `groupId` 为空时，**必须生成返回空集的查询**，而不是不加条件（不加条件 = 看到全库 = 最严重的越权）。

```java
if (groupId == null || groupId.isBlank()) {
    // fail-closed：无组用户任何 records 查询都返回空，绝不能退化成"不过滤"
    wrapper.eq("id", "\u0000__no_group__");
    return wrapper;
}
wrapper.eq("group_id", groupId);
```

> 这是本改造**最关键的一行代码**。单元测试必须覆盖 `groupId == null` 的分支。

### 4.4 管理员数据可见性的「一个开关」设计

用户要求：**先放开（管理员能看到数据），将来改成不能看，且改动要小。**

关键前提：§4.3 的 fail-closed 已经存在 —— `groupId` 为空即查不到任何数据。因此"管理员能否看数据"**不需要任何数据层改动**，只需决定登录后 `currentGroupId` 是什么。

**设计：新增一个配置开关 `auth.admin-can-view-data`（默认 `true`）**

| 开关值 | 管理员的 `currentGroupId` | 结果 |
|---|---|---|
| `true`（当前，默认） | 解析为 `DEFAULT-2026` | 能看到存量数据 |
| `false`（将来） | **置空** | 复用 fail-closed → 看不到任何数据 |

**收紧时只需改一行**（`JwtInterceptor` 解析组之后加一个判断）：

```java
// JwtInterceptor.preHandle —— 解析出 groupId 之后
if (isAdmin(request) && !adminCanViewData) {
    groupId = null;            // 复用 fail-closed，数据层零改动
}
```

**为什么这样改最小**

| 方案 | 将来收紧的改动量 |
|---|---|
| **本方案（配置开关 + 置空）** | **1 处判断 + 1 行配置**，数据层 / SQL / 前端 / openapi 零改动 |
| 不入组（我原先的写法） | 改回去要把 `admin` 塞进 `group_members`，再迁数据 |
| 逐个接口加 `isAdmin` 判断 | 散落多处，漏一处就漏一个出口 |

**代价与风险（需知悉）**

- 开关置 `false` 后，管理员**在任何数据页面都看不到内容**（空态），这是设计意图（"数据主权在组"），但需要提前告知使用者。
- 管理员若同时是某组的 `owner`/`member`，置 `false` 会连本组数据一起看不到。**迁移脚本（§5.3）因此不把 `admin` 设为任何组的 owner**，只作为普通 `member` 加入 `DEFAULT-2026`，便于日后单独调整。

## 五、数据模型

### 5.1 新增 2 张表

```sql
CREATE TABLE IF NOT EXISTS research_groups (
  id VARCHAR(36) PRIMARY KEY,
  code VARCHAR(50) NOT NULL UNIQUE COMMENT '组唯一编码，如 NEURO-2026；申请时即校验，防抢占',
  name VARCHAR(100) NOT NULL COMMENT '组显示名，可重复',
  purpose VARCHAR(500) COMMENT '用途说明（可选），供管理员审批判断',
  status VARCHAR(20) NOT NULL DEFAULT 'pending' COMMENT 'pending/active/rejected/stopped',
  applied_by VARCHAR(36) COMMENT '申请人（= 首任组长）',
  reviewed_by VARCHAR(36),
  reviewed_at DATETIME,
  reject_reason VARCHAR(300) COMMENT '拒绝理由，申请人可见',
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_group_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='课题组';

CREATE TABLE IF NOT EXISTS group_members (
  id VARCHAR(36) PRIMARY KEY,
  group_id VARCHAR(36) NOT NULL,
  user_id VARCHAR(36) NOT NULL,
  role VARCHAR(20) NOT NULL COMMENT 'owner=组长 / member=组员',
  is_primary TINYINT NOT NULL DEFAULT 1 COMMENT '主组标记，预留一人多组',
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_group_user (group_id, user_id),
  INDEX idx_member_user (user_id) COMMENT '每请求按 user_id 解析组，必须有',
  CONSTRAINT fk_member_group FOREIGN KEY (group_id) REFERENCES research_groups(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='课题组成员';
```

> **一人一组的落地方式**：当前用应用层约束（一个 `user_id` 只允许出现在一个非 `rejected` 组的成员行里），结构上保留 `is_primary` 以便将来支持多组而无需改表。

### 5.2 修改 4 张表

```sql
ALTER TABLE users

  ADD COLUMN has_pending_group TINYINT NOT NULL DEFAULT 0

ALTER TABLE operation_log ADD COLUMN group_id VARCHAR(36) COMMENT '操作时所属组，留痕用';
```

### 5.3 存量迁移（严格按序，幂等）

```sql
-- 1. 兜底组（幂等：已存在则跳过）
INSERT INTO research_groups (id, code, name, status, purpose)
SELECT 'grp-default-2026', 'DEFAULT-2026', '默认课题组', 'active', '存量数据归集'
WHERE NOT EXISTS (SELECT 1 FROM research_groups WHERE code = 'DEFAULT-2026');

-- 2. 存量病历归入兜底组（幂等）
UPDATE records SET group_id = 'grp-default-2026'
WHERE group_id IS NULL OR group_id = '';

-- 3. 存量任务归入兜底组（幂等）
UPDATE review_tasks SET group_id = 'grp-default-2026' WHERE group_id IS NULL OR group_id = '';
UPDATE nlp_task     SET group_id = 'grp-default-2026' WHERE group_id IS NULL OR group_id = '';

-- 4. 账号状态
--    admin  → 系统管理员；按用户要求「先放开数据可见」，故归入兜底组（普通 member，非 owner）
--    auditor→ 归入兜底组并担任组长（兜底组必须有 owner）
UPDATE users SET status = 'active' WHERE username IN ('admin', 'auditor');

-- 4a. 兜底组组长：auditor
INSERT INTO group_members (id, group_id, user_id, role)
SELECT 'gm-audit-0001', 'grp-default-2026', u.id, 'owner'
FROM users u WHERE u.username = 'auditor'
  AND NOT EXISTS (SELECT 1 FROM group_members WHERE user_id = u.id);

-- 4b. admin 以普通 member 入组，使其当前能看到存量数据。
--     刻意不给 owner：owner 身份会牵连 §4.4 开关（置 false 时连本组也看不到），分开更可控。
--     将来改为「管理员不能看数据」时，只把 auth.admin-can-view-data 置 false 即可，无需改数据。
INSERT INTO group_members (id, group_id, user_id, role)
SELECT 'gm-admin-0001', 'grp-default-2026', u.id, 'member'
FROM users u WHERE u.username = 'admin'
  AND NOT EXISTS (SELECT 1 FROM group_members WHERE user_id = u.id);
```

> **`admin` 入组是「暂定放开」的实现方式**。改为"不能看"的路径见 §4.4：只把 `auth.admin-can-view-data` 置 `false`，`JwtInterceptor` 解析出组后置空 `groupId`，数据层靠 §4.3 的 fail-closed 自动拦下 —— **一行判断、一行配置，不动数据、不动 SQL、不动前端**。

**迁移顺序不可颠倒**：先建表/加列 → 再填数据 → 最后加非空约束（本次不加 `NOT NULL` 也是这个原因）。代码对空 `group_id` 降级为"无数据"，因此即使迁移未跑完也不会出错。

### 6.3 ⚠️ 审核发现的漏点（13 类 / 20 处）

## 十二、风险与缓解

| 风险 | 缓解 |
|---|---|
| 忘记某条查询路径的组过滤 → **越权** | `RecordIsolationTest` 逐条覆盖 §6.3 的 20 处（含 4 处硬编码 `ROLE_ADMIN`）；一致性脚本列出 `RecordFilter` 全部 15 处外部调用点 |
| `RecordFilter` 无组时退化成"不过滤" → **全库可见** | §4.3 fail-closed 硬约束 + 专门单测 |
| 存量 `group_id` 迁移未执行 → 数据不可见 | `group_id` 不加 NOT NULL；迁移幂等；代码对空组降级为"无数据" |
| 组变更不生效（JWT 24h 缓存） | 组**不进 JWT**，`JwtInterceptor` 每请求查 `group_members` |
| 自助建组被滥用 | `code` 唯一 + 管理员审批 + `has_pending_group` 限制同一时间一个申请 |
| 拒绝后 `code` 被永久占用 | 拒绝时改写为 `rej_<id>_<原code>` |
| 组长离职 → 孤儿组 | `leave` / 移除组长前强制指定继任者，否则拒绝 |
| 组停用后组员数据 | 数据保留不删；停用只挡登录 |
| openapi 按 CRLF 改 → 整份 diff 炸开 | 明确 **BOM + LF**，`python -X utf8` 读写 |
| 日志无界增长（purge 已删，文件侧也已删） | 只剩入库侧：运维约定定期归档 `operation_log`（见 `开发指南与待办.md`）。**未闭环**，见「待用户拍板」#5 |
| **`qc.batch.max-records: 30000` < 真实数据集 35,355** | **功能阻塞（非性能项）**：`QcServiceImpl:210-214` 超限直接抛异常，全库重算**现在就 400**。见「待用户拍板」#1 |
| 管理员开关置 `false` 后管理员看不到任何数据 | §4.4；需提前告知使用者；`admin` 仅作 `member` 入组以便单独调整 |
| **查组漏 `g.status='active'` → 停用组形同虚设** | 停用只挡了登录，旧 token 24h 内照样能看数据。§4.1 已要求 join `research_groups` 判状态 |
| **查组漏 `is_primary=1` → 一人多组时取组不确定** | 表上是 `UNIQUE(group_id,user_id)`，允许多组。§4.1 已要求固定取主组 + 建 `INDEX(user_id, is_primary)` |
| **`JwtInterceptor` 查库失败 → 全站 500** | 从"不碰 DB"变成"每请求查 DB"，DB 挂会波及登录与只读接口。§4.1 已要求降级为"无组"（走 fail-closed）而非抛异常 |
| **`actions()` 绕过 `buildWrapper` → operator 条件加不上** | `selectDistinctActions` 是无参数硬编码 SQL，§6.6 已单列；漏改则普通用户仍能看到他人操作类型 |

## 十四、最容易漏的三处（执行时重点盯）

1. **§6.3 的 13 类 / 20 处绕过 `RecordFilter`（或绕过其数据域）的查询** —— 现在靠"仅管理员"挡着，删门禁后即**直接越权**。R3 必须先补校验，R4 才能删门禁（**顺序不可反**）。
2. **`Dashboard.vue:258`** 是 `userStore.role` 的**数据分支**（不是 UI 门禁），只改界面会漏。
3. **openapi 是 BOM + LF**（0 个 CR 字节），按 CRLF 写补丁会让整份文件 diff 炸开。

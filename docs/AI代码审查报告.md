### 2.1 评判依据：为什么这几个环节最关键

体验的优先级不由「代码难易」决定，而由三个可量化的维度决定。本章所有优先级判定都走这三条，不凭直觉：

| 判据     | 含义                         | 为什么它决定优先级                                     |
| -------- | ---------------------------- | ------------------------------------------------------ |
| 人时消耗 | 频次 × 单次耗时              | 用户每天/每批要在这里花多少时间；消耗越大，改一秒都值  |
| 错误代价 | 做错的后果 × 可逆性          | 错了要重来、或影响下游交付物，代价远高于「多滚一次屏」 |
| 阻塞性   | 这一环卡住，后面是否全走不通 | 阻塞环节的体验缺陷会把整条链路一起拖住                 |

据此对主任务链逐环判定：

| 环节               | 频次           | 单次耗时                               | 错误代价                                       | 阻塞性                      | 判定 |
| ------------------ | -------------- | -------------------------------------- | ---------------------------------------------- | --------------------------- | ---- |
| 批量解析 + 质控    | 每批必跑       | 极高（500 条实测 89 秒，3.5 万条更久） | 中（可重跑）                                   | 强（不解析完无法质控/复核） | 关键 |
| 人工复核           | 每批都有待复核 | 极高（逐条读原文 + 对照 + 裁决）       | 高（裁决直接影响定级与导出）                   | 强（复核不完，导出不完整）  | 关键 |
| 结果数字可信度     | 每次看板/报告  | 低                                     | 极高（口径分裂会让用户按错数字决策，且不自知） | 中                          | 关键 |
| 失败可识别         | 每次操作       | 低                                     | 高（静默失败会让用户把「没做」当成「没问题」） | 中                          | 关键 |
| 术语词典维护       | 低频           | 中                                     | 中（影响全链路归一准确率）                     | 中                          | 重要 |
| 日志审计、组织管理 | 低频           | 低                                     | 低                                             | 弱                          | 一般 |

结论：**最需要优先关注的是「批处理的进度与结果反馈」与「人工复核」两个人时黑洞，以及「数字可信度」与「失败可识别」两个信任底座。** 前者决定用户累不累，后者决定用户敢不敢信。本系统在「信任底座」上的既有做法（不静默降级、失败态带追踪码）是明显优点，见 2.12。

### 2.8 中：抽取服务不可用时，同一屏出现两种互相矛盾的说法

> 取证方式：临时停掉 `python-nlp`（:8001）后，走「载入病历 → 执行抽取」。测完服务已恢复。

- 位置：`NlpExtract.vue:81-86`（正确的一处）与 `StructuredDataCard.vue:144/148`（错误的一处）
- 实测：NLP 不可达时，后端 `POST /api/nlp/extract` 返回 **HTTP 200 · code 200**，9 类实体全空，只在 `unavailableReason` 字段里写 `SERVICE_UNREACHABLE`。此时同一屏上出现两句：
  1. 「自动抽取功能**已经开启，但抽取服务当前连不上**（服务可能未启动或中途停止了）……请联系系统管理员恢复抽取服务后重试」—— 说得对
  2. 「**已抽取，但没有识别出要素** / 抽取已经执行过，只是这段原文里没有可归一的要素」—— 说得不对
- 根因：`StructuredDataCard` 只按「有没有数据」二分（`neverParsed = parsed === null`），**不读 `unavailableReason`**。服务挂掉时后端返回的是「空对象」而不是 null，于是它判成「抽取跑过了、只是原文里没要素」。
- 影响：两句指向同一个结果，而卡片那句更靠下、更像「结论」，用户很可能采信它 —— 于是结论变成「这份病历本身没写要素」，真相却是服务没启动。这正是项目自己立过的规矩所禁止的（「没做不许说成没问题」）。
- 附带（口径不一致，供参考）：项目对「上游不可用」有两套约定 —— 归一（ES）故障返回 **503 + code=1010**（硬失败）；抽取（NLP）故障返回 **200 + code=200 + `unavailableReason`**（软降级）。`NlpController.java:57` 的接口说明确认后者是**有意设计**。软降级本身没错，但它把「服务挂了」与「跑完没结果」压成同一个 `code=200`，任何只判 `code` 的消费方都会踩到上面这个坑。
- 对标做法：上游故障要按**原因**分述，而不是按「有没有结果」分述（GitHub Actions、Vercel 的失败页都会先写清是「构建失败」还是「网络超时」）。本项目其实已经把四态（`DISABLED` / `SERVICE_UNREACHABLE` / `MODEL_MISSING` / 真·无要素）写在 `NlpExtract.vue:73-104` 里了。
- 改进方向：让 `StructuredDataCard` 复用同一套 `unavailableReason` 判断，四态各给各的文案；顺带把「两套降级口径」在接口契约里写清（哪类故障是硬失败、哪类是软降级），避免下一个消费方再踩。

**L· 进入结构化解析页时对「抽取服务已挂」零提示**（低）
- 实测：NLP 已停的情况下打开 `/nlp-extract`，`alerts=[]`、`msgs=[]`、空态仍是「尚未抽取」，**页面没有任何提示**。
- 影响：用户必须走完「载入 → 执行抽取」才知道服务不可用（一次无效操作）。因为有正确提示兜底，故列低。
- 方向：首次抽取失败后常驻一条提示条，或进入页面时探一次服务状态。

### 2.10 低：字号无令牌、点击目标偏小、导出按钮在 1366×768 被裁

- **字号缺令牌且档位碎片化**：`theme.css` 设了 `--el-font-size-base: 13px`，但全前端实测 15 种字号取值，其中 11~14px 区间就有 7 档（11 / 11.5 / 12 / 12.5 / 13 / 13.5 / 14）。用得最多的不是声明的基准 13px，而是 12.5px（76 处），其次是 12px（55 处）、13px（41 处）、11.5px（25 处）。**主题里没有任何 `--fs-*` 字号令牌**，全部是字面量。0.5px 的阶梯人眼几乎分辨不出，却制造了实际的不一致；另有 11px、11.5px 两处小于 12px 的正文。对标 Ant Design / Material 3 的做法是给出 4~6 档具名字号令牌（caption / body / subtitle / title），所有页面只许引用令牌。
- **链接型按钮点击目标偏小**：表格操作列的「查看」「删除」「扣分明细」「规则配置」等 `link` 型按钮，实测命中区为 32×19px 或 58×19px，高度仅 19px；表内还有 12×12px 的图标目标。WCAG 2.5.8（Target Size, Minimum, AA）要求最低 24×24 CSS px，Apple HIG 建议 44×44pt、Material 3 建议 48×48dp。鼠标操作的内网桌面工具实际影响有限，故列低，但 12×12 的图标目标值得单独确认是否可点中。
- **治理页导出按钮在 1366×768 被裁 4px**：实测「预览数据集」「导出下载」的纵坐标为 748，按钮底边约 772px，而视口高 768px，即主交付动作在小屏上恰好被切掉。1440×900 下页面仅溢出 30px。这是典型的「临界高度」问题，只需把筛选区压缩一行即可解决。

### 2.11 对标商业产品的可借鉴做法（提炼）

把上面散落的对标收拢成可直接落地的五条思路：

| 思路                       | 商业产品做法                                                                          | 对应本系统的哪一处                                                        |
| -------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 主从布局取代纵向堆叠       | 左列表 + 右详情，选中即右栏刷新（Stripe、Linear、Notion）                             | 结构化解析页：选择病历与解析工作区左右分栏，消灭 1000px 的滚动落差        |
| 结果优先、配置收进抽屉     | 报表首屏只放结果，口径与配置默认收起（Google Analytics、Metabase）                    | 质控校验页：规则配置折叠，扣分构成与预检列表上移首屏                      |
| 长任务给进度、给失败下钻   | 逐条状态 + 失败高亮 + 只看失败筛选（GitHub Actions、Vercel 构建日志）                 | 批处理解析与质控：500 条 / 3.5 万条时用户最需要知道「跑到哪了、错了几条」 |
| 一个指标只出现一次且可下钻 | 卡片即入口，同值不重复占位（Stripe Dashboard）                                        | 首页看板：去掉重复的「待复核」                                            |

| 上游故障按原因分述         | 服务不可达 / 功能未开 / 模型缺失 / 真无结果，四态各说一件事（GitHub Actions、Vercel） | 结构化解析页：结果卡片与提示条共用同一套 `unavailableReason` 判断         |

### 2.12 体验角度做得好的部分

以下均为实测确认，不是阅读代码的推测：

- **整页不需要下拉**：11 个页面 × 2 档视口，`documentElement` 的溢出量全部为 0。页面滚动统一收敛在 `main#main-content` 一个容器内，顶栏与侧栏常驻不动 —— 这是正确的应用外壳做法，也符合项目「页面根撑满一屏」的既定口径。这条是系统体验的底色，值得保持。
- **表格高度守住硬下限**：有数据行的表格实测高度为 352 / 352 / 355 / 360 / 445px，全部不低于 352px 硬下限；无数据行时按内容自适应（96 / 121 / 299px），符合预期。
- **失败态有出口**：统一的 `EmptyState` 在失败时给出「重试」与「联系管理员」两条出口，并提示携带追踪码，比多数同规模系统的「白屏 + 控制台报错」好得多。
- **图表有无障碍摘要**：首页趋势图的 `aria-label` 写明了数据范围与最新值（实测读得「质控趋势折线图，共 12 个月；最新 2025-12 合格率 100%，待复核 0 条」）。图表本身是 canvas，这条文本是屏幕阅读器唯一的入口，属主动加分项。
- **危险操作有二次确认**，且确认弹窗的交互形态在全站保持一致。
- **抽取降级文案按原因分四态**：`NlpExtract.vue:73-104` 按 `unavailableReason` 分 `DISABLED` / `SERVICE_UNREACHABLE` / `MODEL_MISSING` / `UNKNOWN` 四支，各说一件事，并把端口、字段名这类技术细节挪到后端日志。实测停掉 NLP 后，页面说的是「抽取服务当前连不上……请联系系统管理员恢复」，而不是笼统的「未开启」。
- **空结果不许覆盖已有数据**：抽取无产出时「写回结构化数据」按钮被禁用，并写明理由「本次没有抽到任何要素，写回会把原有结构化数据清空，已禁用」—— 实测该按钮确为 `disabled`，因此本轮降级实测**没有对数据库产生任何写入**。
- **人工复核页载入后主动定位**：点「进入复核」后 `scrollIntoView` 到任务卡，实测 `scrollTop` 0→336，用户不会以为「点了没反应」。
- **复核底部操作条吸底常驻**：`复核通过` 实测 `top=771`，任何滚动位置都在视口内 —— 长表单里主操作永远够得着。
- **复核提交后有常驻反馈条并留痕**：反馈条写明「状态 / 重新评分 / 剩余问题」，同时落 `operation_log`（实测 `action=人工复核`、detail 含结果与意见），事后可追溯是谁在什么时候裁定了哪条病历。

### 2.13 本章未验证项

- **ES 不可用时（503 + code=1010）的页面表现**：本轮只临时停了 NLP，未停 ES，故归一硬失败时用户看到什么未实测。
- **真机触控操作**：窄屏已实测（1366×768 / 1024×768 / 768×1024 / 390×844，开 `hasTouch`），触控目标尺寸也已量（见 2.10），但**未在真机 / 真实触屏上做点击操作验证**。
- **窄屏结论的适用边界**：应用外壳明写 `min-width: 1024px`（`MainLayout.vue:193`，注释说明是刻意取舍），故 768 / 390 视口下整页横向溢出 256px / 634px、布局完全不重排。这是**有意的桌面优先设计**，不作为缺陷，但也意味着窄屏与触屏不在设计目标内。
- **大数据量下的体验**：实测基于 500 条演示数据；3.5 万条时的列表响应、进度反馈、失败下钻体验未实测。

## C. 本轮新增的 P0 级问题（第一版未覆盖）

**P0-N1｜批量任务可「0 处理却报 COMPLETED」【实测】**
- 现象：提交 500 条筛选型任务，日志立刻出现「没有待处理项…直接收尾」→ `结束：COMPLETED，成功 0，失败 0；共 500 条 · 已处理 0`。
- 根因链：把内存兜底改为查 `nlp_task_items` 后，**筛选型任务本没有明细**，无条件读表得到**空集合**；而 `null` 与 `[]` 在判断里行为相反（`!= null` 对空列表为真），于是走进了「ID 型任务」分支并被空集合守卫收尾。此前同一处还产生过 `IN ()` 的 MySQL 语法错（`SELECT id FROM records WHERE (org_id = ? AND id IN ()) LIMIT 0`）。
- 影响：**用户会以为解析完成**，后续质控全部建立在不完整数据上；属「最危险的一类」——界面显示成功，数据是空的。
- 修复：分流判据改为「该任务**有没有明细行**」，恢复原 `null → runByFilter` 语义；空集合守卫保留但只对 ID 型任务生效。
- **仍缺**：能拦住它的**集成测试**（见 P0-N2）。

**P0-N2｜缺「提交 → 落库 → 执行 → 终态」的集成测试网【实测】**
- 本轮同一片代码连续 3 次回归，**全部由真机/实测发现**，334 个单测无一拦住：① `IN ()` 空集合语法错；② 筛选型任务被误收尾；③ 残词阈值从 1 改到 2 误删真术语。
- 判断依据：这三次都属于「单测覆盖不到的**组合行为**」（空集合 × 任务类型 × 终态语义），而它们恰好都在**用户最高频的批量链路上**。
- 方向：Spring Boot Test + MockMvc 覆盖四条路径（筛选型 / ID 型 / 取消 / 执行异常），断言**终态 + 已处理数 + 成功/失败数**三者自洽。

**P0-N3｜归一率的天花板由词典规模决定（产品完整性缺口）【实测】**
- 实测构成：未归一合计 **3326**（症状 3026 + 病因 300）；症状侧 **97 种不同内容**（≥3 字 81 种 / **2736 次**、两字 16 种 / 290 次）；病因侧仅 5 种（寒湿/风寒/气虚/阳虚/阴虚）—— **系统根本没有病因词典，故病因 100% 未归一**。
- 影响：归一率是产品的核心指标，却**无法通过任何用户操作改善**；病因字段整列未归一，用户会误判为系统故障。
- 方向：① 病因词典优先补齐（**5 个词覆盖 300 次**，投入产出比最高）；② 未归一 TOP-N 旁给「加入词典 / 生成提案」入口（把统计变成可行动清单）。

## E. 用户体验：以第一版实测为准，本追加只补「修复后的变化」

**判定依据沿用第一版**：人时消耗 / 错误代价 / 阻塞性。据此**最关键的两个环节**是（与第一版一致）：

1. **批量解析的状态真实性**（代价大 + 用户无法自证 + 高频）—— 本轮实测的 P0-N1 正是它的最坏形态；已修，但**需要集成测试锁死**，否则下次改动仍会复发。
2. **未归一清单的可行动性**（用户唯一能主动改善核心指标的地方）—— 现状给的是统计，不是待办；配合 P0-N3 的病因缺词典，用户会陷入「看着低分、无从下手」。

**本轮已改善的体验点（可复验）**：
- 质控页「质控评分标准」面板：原写「每个 -1 **上限 -5**」（分段后已不成立）→ 改为「未命中词典的每个 -1；超过 5 个后每再满 5 个追加一档（分段扣分…）」；
- 规则配置弹窗（改完保存即生效那一处）：原写「最多扣 5 分」→ 改为「…后按档累加（每满该条数再加扣一档，不再封顶）保存即生效；已评过的病历需重跑质控才会更新」；
- 标准化质量报告页：**原先没有任何「本页不会自动刷新」的说明**（控件其实齐全：立即重跑质控 / 重跑解析+质控 / 进度条 / 刷新 / 报告时间 / 「解析早于词表，需重跑」标记）→ 已在顶部加醒目提示条，讲清三种场景该点哪个按钮。

> **一处提醒**：这三处均为**前端文案/提示**改动，刷新浏览器即可见；而**分段扣分、归档 NPE、空集合、筛选型分流、单字残词、别名入口**六处是**后端行为**，必须**重启后端**才生效——这正是「改了但用户看不见」的根源，建议把「改动生效条件（前端热更 / 需重启）」写进团队约定。

## F. 未测 / 存疑（本追加同样不把它们当结论）

1. 前端真机交互的主链路点击与网络异常清单：`agent-browser` CLI 已可用（`nodejs-global\agent-browser.cmd`），但 `snapshot` 子命令**挂起未解决** —— 但注意：**第一版已用无头 Edge 完成 11 页 × 多视口实测**，故此项应表述为「补充验收」而非「空白」；
2. 3.5 万条端到端性能（单条 / 全库 / 分页 / 聚合四组耗时）；
3. NLP 推理实测与模型缺失降级路径；
4. ES 归一按实体逐条查词的 QPS 放大效应；
5. 多实例并发（Redisson 已定方案，卡在离线 Maven 仓库需一次联网构建；RabbitMQ 未落地）；
6. 安全细项（LLM 密钥加密落库、响应脱敏、审计覆盖面）。

## G. 落地优先级（本追加的建议顺序）

**P0**：① 状态真实性四态化 + `已处理=0 且 总数>0` 不得报完成；② 补四条路径的集成测试；③ 病因词典补齐（5 词 / 300 次）+ 未归一 TOP-N 给「加入词典 / 生成提案」入口
**P1**：④ 3.5 万条四组耗时 + ES 归一 QPS 标定；⑤ 一次联网构建落地 Redisson；⑥ 「附属步骤失败」统一为结构化 `warnings[]`；⑦ 清理存量注释失真、旧 API 路径给下线时间表
**P2**：⑧ 导入 dry-run 预览与回滚；⑨ 数据新鲜度徽标全站统一；⑩ 解决 `snapshot` 后补真机 E2E；⑪ 实体类型判定归属唯一化（Python 判、Java 只校验 + 兜底并注明「兜底不应成为常态」）

## H. 一句话总结

系统的工程质量基线是好的（**编译 / 测试 / 构建 / 权限契约四项硬指标全绿**，且已有无头实测的体验证据）；本轮真正暴露的不是「写错了什么」，而是**「改动引发的连锁回归缺少测试网来兜」**——三次回归都在用户最高频的批量链路上、且都是**静默**的。因此下一步的性价比最高项不是加功能，而是**把「提交 → 落库 → 执行 → 终态」这条链路用集成测试锁死**，并让**终态永远与已处理数自洽**。

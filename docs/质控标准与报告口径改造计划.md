## 一、归一率图：剔除无词典类型（`cause`）

### 1.1 现状取证

「各类术语归一率」图的每一根条，来自后端 `coverage()`：

- `StandardizationReportServiceImpl.java:425` —— 遍历 **`EntityTypes.all()`**，把**全部 9 类**实体都放进 `byField`。
- `StandardizationReportServiceImpl.java:446` —— 只有 `if (t.dict())` 才回填 `termCount`；`cause` 的 `dict=false`，故 `termCount` **恒为 0**。
- `EntityTypes.java:79` —— `new EntityType("cause", "病因", "causeList", false, null, …)`：**`dict=false` 且 `dictionaryFile=null`**，`data/dictionaries/` 下也确实**没有** `causes.json`（只有 diseases/formulas/herbs/patterns/pulses/symptoms/tongues/treatments 8 个）。
- `StandardizationCharts.vue:108-109` —— 前端只过滤 `c.total > 0`，**不排除无词典类型**。

⇒ 结果是：只要病历抽出了病因实体（实测 303 份里 **300 份**有 `causeList`，值均为 `{"content":"情志","source":"rule"}`），图上就会出现一根「病因 归一率 0%」的条，而这个词表**根本不存在**。用户看到的「有病因但没有对应术语库」正是此因。

### 1.2 方案

**在后端 `coverage()` 剔除无词典类型**，而非只在前端过滤。

- 改 `StandardizationReportServiceImpl.java:425` 的遍历：由 `EntityTypes.all()` 改为只取 `t.dict()` 为真的类型（与 `:342 dictQuality()`、`:373 crossTypeDuplicates()` 已有的 `if (!t.dict()) continue;` 口径一致）。
- 前端 `StandardizationCharts.vue` **不动**：`total > 0` 的过滤保留（它解决的是「方剂/治法没数据也占位」这一独立问题）。

选后端的理由：`coverage` 数组是 `GET /api/standardization/report` 的公共出口，前端图、导出、AI 解读都可能消费；在后端收敛口径，避免各处各判一次。

### 1.3 影响面（已核验）

| 位置 | 是否受影响 | 说明 |
|------|-----------|------|
| 图一「各类术语归一率」 | ✅ 按预期消失 | 病因不再出现 |
| 图二「未归一实体 TOP-N」 | ❌ 不受影响 | 该图数据来自 `unmatched()`（`:480-514`），**只扫 `row.symptoms`**，与 `coverage` 无关 |
| 甲类「词典质量」表 | ❌ 不受影响 | `:342` 本就跳过 `dict=false` |
| 跨类重名检查 | ❌ 不受影响 | `:373` 本就跳过 `dict=false` |
| 病因本身的可见性 | ✅ 仍可见 | 抽取结果页 `NlpExtract.vue:648`、复核详情 `ReviewDetailPanel.vue:214`、结构化卡片 `structured.js:19` 都仍显示病因；只是不再进「归一率」这张图 |
| 质控扣分 | ❌ 不受影响 | `cause` 的 `countsUnnormalized=false`，本就不计未归一扣分 |

### 1.4 验收方式

1. 取一份含病因的病历，调 `GET /api/standardization/report`，断言 `coverage` 数组**不含** `label="病因"` 的元素。
2. 断言同一响应里其余 8 类（疾病/证候/症状/中药/方剂/舌象/脉象/治法）**仍在**。
3. 前端图一条数 = 后端 `coverage` 长度（无 `total=0` 类型时）。

## 二、AI 复核：现状说明与启用指引（不改代码）

### 2.1 现状（代码取证）

**「AI 预检 + 人工复核」这个模式，系统里已经是了**；真正缺的是 **LLM 未配置**。

- `AiServiceImpl.java:505-530` `review()`：
  - **结论（评分/分级/扣分项）来自规则重算** —— `QcScorer.score(...)`，与质控页看到的判定**同源同组织**（`:519-520`）；
  - LLM 只用来**补建议文本**（`:523` `llmClient.chat(AI_REVIEW_SYSTEM_PROMPT, …)`）；
  - `:526-528` `source = llmOk ? "llm" : "rule"`，LLM 不可用时**直接回规则预检单**，保证「有结论可看」。
- 前端 `ReviewDetailPanel.vue:65-71`：`aiSource === 'rule' ? '规则预检（LLM 未启用）' : 'AI 建议'`。
- **当前实际状态**：`user_llm_config` 表为空、`data/llm-config.json` 不含 api-key ⇒ 页面显示的是**规则预检**，不是 LLM 建议。

### 2.2 责任边界（建议明确写入产品口径）

| 环节 | 由谁做 | 依据 |
|------|--------|------|
| 判定「合格/待复核/无效」 | **规则** | `QcScorer.java:112-126`，可复现、可申诉 |
| 生成「为什么扣分、建议怎么改」 | **LLM**（不可用时回退规则文案） | `AiServiceImpl.java:523-528` |
| 最终采信与否 | **人工复核人** | `review_tasks` 状态流转 |

⇒ **AI 不做判定、只做建议**。这是刻意设计：判定必须可复现，否则复核结论无法追溯。**不建议**把 LLM 结论直接写成 `grade`。

### 2.3 如何让 AI 建议真正生效（配置步骤）

1. 以目标账号登录 → 「AI 配置」页 → 填入 baseUrl / model / **api-key** → 保存（落到 `user_llm_config`，**每人一份**）。
2. 连通性自检用 **`POST /api/llm/test`**（`GET /api/llm/config` 的 `available` 只表示「参数齐备、客户端装配成功」，**不发模型请求**，不能当连通性证据）。
3. 回到复核详情，「AI 预检建议」区块的角标应从「规则预检（LLM 未启用）」变为「AI 建议」。
4. 若仍显示规则预检：查该账号 `user_llm_config` 是否落库、api-key 是否被 `LlmSecretCipher` 正常加解密。

### 2.4 待定项（需用户拍板后才动代码）

- 是否要**批量预生成** AI 建议（当前是按需触发，打开详情才算）？
- 是否要把 AI 建议**落库留痕**（当前只在前端展示，刷新即重算）？
- 是否要给 LLM 建议加**采纳/驳回**按钮，回流为规则调优依据？

### 3.3 分值口径对照

| 项 | 浙江表（S2） | 本系统 `QcRuleSet.defaults()` |
|----|-------------|------------------------------|
| 总分制 | 100 分，按项目分值分配 | 100 分，**扣分制**（`score = max(0, 100 − 总扣分)`，`QcScorer.java:109-110`） |
| 完整性 | 分散在各项目内 | 6 要素，**真缺失 −12 / 漏抽 −6**（`QcRuleSet.java:61-63`） |
| 单条最重 | 单项否决 = 扣 10 分（不累积） | 完整性单项 −12（**比浙江表单项否决还重**） |
| 逻辑一致性 | 分散在「诊断」「首次病程录」内 | 14 条 × **−10/条**（`QcRuleSet.java:103`） |
| 格式 | 分散 | 2 条 × **−5**（`:77`） |
| 标准化 | 无对应项 | 8 类，**每处 −1，前 5 处线性，之后每满 5 处追加一档**（`:96-98`） |
| 重复 | 「不合理复制单项否决 / 不当复制酌扣 1–3 分」 | 「内容完全一致」**二值 −5**（`:185`） |
| 分级线 | 90 以下乙级、80 以下丙级 | 合格 ≥90、无效 <60 或真缺失 ≥3（`:119-123`） |

**两个必须说清的口径差异**：

1. **本系统 90 分是「合格线」，浙江表 90 分是「甲级线」** —— 数字相同、含义不同，不能直接互比。
2. **6 要素全缺 = 扣 72 分 → 得分 28 → 直接判「无效」**（`QcScorer.java:113-116`：真缺失 ≥3 即「无效」）。即**只缺 3 项就已「无效」**，与浙江表「90 以下才降级」的宽容度差异很大。

### 3.4 差距清单（按性质分三档）

**甲档 · 结构性缺失（受数据模型硬约束，不建议本轮做）**

`records` 表只有 **21 个内容字段**（`RecordServiceImpl.java:82-86`：登记号/门诊号/性别/年龄/就诊次数/中西医诊断/现病史/主诉/自述/望诊/脉/舌/查体/证候/处方/随访/疗效/科室/医师/就诊时间），**没有任何「书写完成时间 / 签署 / 手术 / 首页编码」字段**。

⇒ 上表里 ❌ 的 8 项（首页、时限、查房、病程频次、围手术期、知情同意、会诊、医嘱单）**在当前数据模型下无法实现**，不是工作量问题。要做需先扩字段 + 改导入模板 + 改前端表单，属**另一个项目**。

**乙档 · 口径偏差（改配置即可，低风险）**

1. 完整性单项 **−12 分**偏重：6 要素里缺 3 项即「无效」，而浙江表同级缺陷多为 −0.5~−2 分。
2. 一致性单条 **−10 分**：理法方药不一致扣 10 分合理，但 14 条规则**可叠加**，理论上限 140 分，需确认是否符合预期。
3. 重复检测只有「完全一致」二值 −5，缺梯度。
4. 分级线 90/60 与「真缺失 ≥3 即无效」两条线**互相干扰**：分数还没低于 60，可能已因缺失项判无效。

**丙档 · 内涵维度可补（需新增规则类型，中风险）**

1. **主诉能导出第一诊断**（S3 明确要求）—— 需新增「文本蕴含」型规则，当前规则类型（regex/enum/一致性/标准化）**都不支持**。
2. **四诊完整性** —— 在完整性要素里加「面色/闻诊」，但需先有对应抽取能力。
3. **辨证依据充分性** —— 需 LLM 参与判定，与 2.2「AI 不做判定」冲突，需先定边界。

另外两点：**望诊填充率 29.9%，但 6 要素里没有望诊**（只有舌象、脉象）；**辨证结论有 12152 种不同取值**，而一致性规则只覆盖 9 个证候。

**六、补测：纳入「标准化」维度后的完整分布**

上面第一~四节的仿真是**不完整**的 —— 它只算了完整性 + 格式 + 一致性，**漏了「术语标准化」**（该维度需要 NLP 抽取结果）。用「中药 token 是否命中 `herbs.json`」+「证候分段是否命中 `patterns.json`」做近似后补齐：

| 场景 | 不同分数取值 | 最高频占比 | 分级（合格/待复核/无效） | 扣分构成 |
|------|-------------|-----------|------------------------|----------|
| 现状（含年龄 bug，无标准化） | 25 | 63.3% | 69.0 / 18.8 / 12.3 | 格式 35.7 / 完整性 62.6 / 一致性 1.6 |
| 仅修年龄正则（无标准化） | 15 | 69.0% | 69.0 / 18.8 / 12.3 | 格式 0.1 / 完整性 97.4 / 一致性 2.5 |
| 现状 + 标准化 | 74 | 44.0% | 61.3 / 26.4 / 12.3 | 格式 26.4 / 完整性 46.3 / 标准化 26.1 / 一致性 1.2 |
| **修年龄正则 + 标准化（预期稳态）** | **62** | **48.0%** | 69.0 / 18.8 / 12.3 | 格式 0.0 / 完整性 62.8 / **标准化 35.5** / 一致性 1.6 |

**修正后的结论**：

1. **分数层面的区分度没有第一~四节说的那么糟** —— 标准化维度贡献 35.5% 的扣分，把取值数从 25 拉到 **62**、集中度从 63.3% 降到 **48.0%**。原因是中药词典命中率有真实跨度：**P10=0.53 / P50=0.69 / P90=0.83**（497526 个中药 token 命中 69.4%）。
2. **但分级完全不变（69.0 / 18.8 / 12.3）** —— 标准化扣分只在 1~5 分内移动，而阈值是 90 / 60 / 3 三档粗线，够不到档位。**分级区分度的问题在阈值口径，不在扣分计算。**
3. 「调权重」依然被证伪：修掉年龄误伤后，**分数更集中**（69% 满分），说明信号的多样性才是瓶颈。

### 3.6 关键推翻：A②「一致性规则按词典生成」的前提不成立

原设计假设「可以把硬编码的 9 条一致性规则换成按词典生成」。实测证否：

| 检验项 | 结果 |
|--------|------|
| 词典里有「证候 → 方药」映射吗 | **没有**。`patterns.json` 2080 条证候名、`herbs.json` 667 条药名，两者之间**无关系表** |
| 真实「辨证结论」能对上词典证候吗 | 整串精确命中 **0.4%**（134/35354）；子串命中 **9.4%**（3309）；**70% 完全不命中** |
| 最高频证候在词典里吗 | **不在**。出现 326 次的「脾虚湿滞」、154 次的「脾虚痰湿」、112 次的「阳虚湿滞」**全部不在** `patterns.json` |
| 证候写法有多碎片 | 28128 条非空里有 **12152 种**不同写法；TOP1 只占 0.9%，TOP1000 才覆盖 28.8% |

⇒ 「按词典生成」**无法扩大覆盖面** —— 上限就是那 9.4%。要真做「理法方药一致性」，需要**外部的证候—方药知识库**（中医教材/指南/专家整理），那是**数据工程**，不是代码改造。

**结构改造仍值得做**（用户已确认「要一起」）：把映射源从 Java 硬编码 List 改为**外部可配置文件**，代码支持任意条数、缺文件回退内置默认。这样「不再硬编码」在代码层面完成，内容层面由知识库填充，互不阻塞。

### 3.7 关键推翻：A③「重复改近似重复」价值极低

严格归一化（去掉所有数字/标点/空白后全列比对）后：

| 指标 | 值 |
|------|-----|
| 重复行 | **188 / 35354（0.5%）** |
| 重复组数 | 112 |
| 最大重复组 | 18 |

⇒ 影响面 0.5%，**不值得为它改判定逻辑**。放宽阈值能多抓一些，但会引入误报（真实病历本来就大量同构）。**建议不做**。

### 3.8 结论：B「连续型规则」建议不做

| 理由 | 说明 |
|------|------|
| 文本长度是**质量代理**，不是质量本身 | 现病史 P10=51 / P90=430 的差异里，既有「写得详细」也有「复制粘贴灌水」。按长度扣分会**奖励灌水**，与质控目标相悖 |
| 数据里有**更可靠**的缺失信号 | 望诊填充率仅 29.9%（真实缺失），比长度可靠得多。要做也是把「望诊」纳入完整性要素，而不是按长度计分 |
| 改动面大于收益 | 当前规则类型（regex / enum / 一致性 / 标准化）**都不支持「连续型」**，需新增规则类型 + 前端表单 + 判定逻辑 |
| A 做完后分数取值已达 62 个 | 集中度 48%，继续加维度的边际收益递减 |

**建议**：**不做 B**。若后续仍觉得维度不够，优先做「望诊纳入完整性要素」——它需要先补 `EntityTypes` 里的望诊类型 + 词典，属独立小项。

### 3.9 修正后的候选方案

| 方案 | 内容 | 状态 |
|------|------|------|
| **A · 止血 + 结构** | ① 修年龄正则（**已落地**）；② 一致性映射源改外部配置文件 —— **不做**（内容层无知识库，只做骨架不值得）；③ ~~重复改近似重复~~（**实测否掉**） | ① 已做，② 否 |
| **B · 连续型规则** | 按文本长度/丰富度计分 | **不做**（见 3.8） |
| **C · 形式质控** | 首页/时限/知情同意… | 需扩数据模型，单独立项 |
| **D · 分级阈值口径** | 合格线 90 → 95 + 前端去硬编码 | ✅ **已落地**（见 3.10） |

### 3.10 D 的设计依据（合格线 90 → 95）

**关键实测：分数几乎是「真缺失要素数」的阶梯函数**

| 真缺失数 fm | 90-100 | 80-89 | 70-79 | 60-69 | 0-59 | 小计 |
|---|---|---|---|---|---|---|
| 0 | 24380 | 630 | 11 | 0 | 0 | 25021 |
| 1 | 0 | 4895 | 70 | 0 | 0 | 4965 |
| 2 | 0 | 0 | 1022 | 8 | 0 | 1030 |
| 3 | 0 | 0 | 0 | 551 | 483 | 1034 |
| 4 | 0 | 0 | 0 | 0 | 2930 | 2930 |
| 5 | 0 | 0 | 0 | 0 | 302 | 302 |
| 6 | 0 | 0 | 0 | 0 | 72 | 72 |

⇒ 标准化只造成 ±8 的扰动，**几乎不足以跨越档位**；分数区间与 fm 一一对应。

**三条结论**

1. **阈值调整只能在台阶上划线，不可能创造新的区分度** —— 分级区分度的天花板由「只有 6 个要素」这个结构事实决定，不是阈值选错。
2. **`invalid = 60` 在真实数据上不单独生效**：得分 < 60 的病历 **100% 都已因「真缺失 ≥ 3」判无效**（实测：分数 < 60 且真缺失 < 3 的条数 = **0**）。两条规则不冗余（结构判据 / 量值判据），但会互相遮蔽。
3. 因此唯一有效的杠杆是**合格线**。

**取值推导**（不拍脑袋）：`qualified = 100 − 标准化档位(cap=5) = 95`
含义 = 核心要素无真缺失 + 无逻辑冲突 + 术语未归一不超过一档。原值 90 是「按演示数据集调优的示例」（`QcRuleSet` 原注释），无推导依据。

**效果**（35354 份离线仿真）：

| 阈值 | 合格 | 待复核 | 无效 |
|------|------|--------|------|
| 90/60/3（原） | 69.0% | 18.8% | 12.3% |
| **95/60/3（新）** | **60.7%** | **27.0%** | 12.3% |

**不新增档位的理由**：新增「优秀」档需改 `StatsCache.GRADES` 固定集合、`QcServiceImpl` 的 grade→status switch、`RangeFilter.vue` 选项、`GovernanceServiceImpl` 的 `grade='合格'` 过滤 —— 影响面大且会波及存量数据，收益（约 55/14/19/12 的四档分布）不值这个风险。

**顺带修掉一处真实分叉**：`RecordTable.vue:174` 把 `>=90 / >=60` 硬编码在评分配色里，而 `utils/grade.js` 明确写着「阈值必须来自后端规则，前端不写死数值」。已改为按后端返回的 `grade` 着色。

> ⚠️ 分数口径一变，存量病历需整体重算，历史复核结论受影响 —— 先冻结、备份 `records.score/grade/qc_results` 再改。
> ⚠️ 合格线 90 → 95 会使**待复核量增加约 8.2 个百分点**（≈2900 份/35354），复核工作量相应上升 —— 这是有意为之（把「术语也不规范」的病历纳入复核），但上线前应确认人力可承接。

## 四、规则集与规则标准同步更新机制

用户原话：「**更新规则就要更新规则标准，这两个是一起的**」。

### 4.1 现状：运行时说明已经同源（这块是好的）

- `QcRuleDescriber.java:26` `describe(QcRuleSet)` —— 从**当前生效规则对象**实时生成人话说明；
- 前端 `Qc.vue:203` 有「查看完整规则说明」折叠区，`:264` 拉 `GET /api/qc/rules` 的 `descriptions`；
- 即「界面上看到的规则说明」**必然**与生效规则一致，不会分叉。

### 4.2 缺口：没有书面标准文档

- `docs/` 下**没有**任何质控规则说明书（`ls docs/` 的 12 个文件中无对应项）；
- 规则散落在 `功能设计文档.md:865`、`QcRuleSet.java:125-187` 的代码注释里；
- **没有任何机制**保证「改了 `QcRuleSet` 却忘了改标准文档」被发现。

### 4.3 方案

**新增 `docs/质控规则与评分标准.md`**，作为唯一权威书面标准，内容：

1. **依据**：S1/S2/S3 条款号（外部标准 → 本系统规则的映射）；
2. **规则清单**：按「完整性 / 格式 / 一致性 / 标准化 / 重复 / 阈值」六段，逐条列**规则名、触发条件、分值、口径说明**；
3. **定位声明**：本系统只做**中医内涵质控**（结构化数据层面），不含形式质控（首页/时限/知情同意…），并说明原因（3.4 甲档）；
4. **口径公式**：把 `QcScorer` 的计分公式（含标准化的分段扣分）写成可核对的文字。

**新增守卫测试 `QcRuleStandardDocTest`**，防「规则改了文档没改」：

- 读 `docs/质控规则与评分标准.md`；
- 断言文档中出现了**全部**默认一致性规则名（14 个）、全部完整性要素名（6 个）、全部格式规则 label（2 个）、以及三个阈值数字；
- 任一新规则未写入文档 → 测试失败，提示「请在标准文档补登」。

这样把「两者是一起的」从**口头约定**变成**CI 会拦的硬约束**。

|------|------|

| `java-backend/src/test/java/com/tcm/ehr/common/config/QcRuleStandardDocTest.java` | 新建 |

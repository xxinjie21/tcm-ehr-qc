### 1.2 批间依赖

```
批G（NLP 抽取，无依赖） ──────────────┐（硬前置）
                                      ▼
批A（基底，无依赖） → 批B（治理与公共能力，内部顺序） → 批C（消费端可并行）/ 批D（3.3·5.1 并行）→ 批E（收尾）
批F（病历数据与审计，无依赖）─── 与批A~批D 并行 ─────────────────────────────────────────────┘（7.4 供批D）
```

**依赖说明**
- **批G 是批B 的硬前置**：批B·2.3 的评分规则中"核心字段缺失 ≥3 项 → 直接判 invalid"，而 NLP 未接通时规则兜底只能补 **舌象/脉象/病因/治法 4 类**，**证候/方剂/中药 3 类核心项拿不到** → 真实病历会几乎全部命中"核心缺失 ≥3"被判无效，2.3 的"分级分布合理"验收在真实数据上无法达成（现有 500 条能跑通是因为 `structured_data` 由 seed 按词典预生成，非真实抽取）。因此 **`/api/nlp/extract` 可用（模型文件就位）是批B 开工的前置条件**；
- 批B 内部 `2.1 → 2.2 → 2.3 → 4.1` 严格执行：2.2 依赖 2.1 卡片（v1→v2）；4.1 依赖 2.3 的 batch/clean；
- 批C 三项互不依赖：3.1 依赖 2.2（normLevel）、3.2 依赖 2.2/2.3（normByLevel/stats）、4.2 依赖 2.3+4.1；
- 批D：**3.3 与 5.1 互不依赖、可与批C 并行**；5.1 复核工作台的"按条件筛选待复核"依赖 **批F·7.4** 的病历查询接口；
- 批F：**病历数据与审计（链路第 1 环）**，与批A~批D 无依赖，可并行；批A~批D 的起点默认"已有 seed 数据"，**真实链路入口由批F 补齐**；
- 抽取（批G `/api/nlp/extract`）：**Python FastAPI 服务（:8001）加载 `hwtcmner`** 6 类 + 规则兜底（舌/脉/病因/治法），模型缺失时仍可用；Java `PythonNlpClient` 转发；seed 为过渡，接通后走真实抽取；
- LLM：②词典转换 ③助手 ④解读 ⑤复核意见 统一走 `LlmClient`（**基于 Spring AI 2.0 `ChatClient`**，双 provider：`ollama` 本机 / `openai` 兼容；`llm.enabled` 总控，失败自动降级）；**判定地基=规则引擎**（评分/分级/归一 不依赖 LLM）。

### 1.3 数据规模化（≥3 万条真实数据）

> 真实病历规模 ≥3 万，替换原"500 条内存假设"，全链路数据访问采用 **SQL 优先**。
>
> **口径来源**：已与 `docs/需求分析报告.md §4.1` 对齐——该文档原"单次批量处理上限 100 条"已改为 **3 万条**，`docs/项目设计文档.md` 的性能章节与中间件结论（Redis 改为"需要，仅用于任务防重"）同步更新。
>
> **边界**：本节的性能基准**仅约束非 NLP 环节**（评分 / 统计 / 导出）。NLP 解析受模型推理速度约束（**Python 服务（FastAPI）加载 hwtcmner，CPU 单条数百毫秒**，须批量送推理），**全库 3 万条解析属离线批处理，按小时计（约 2~4 小时）**，不纳入 §1.3 的分钟级基准。

| 环节 | 规模化要求 |
|------|-----------|
| 过滤 / 分页 | `RecordFilter` 改 **QueryWrapper 条件 + selectPage 分页**（SQL），不再全表内存过滤；仅小范围子集可用内存 |
| 清洗 / 批量重算 | **分页游标分批**（每批 500~1000），逐批提交 + **单条本地事务** + 失败清单累计（见批B·2.3） |
| 统计 / 图谱 | **SQL GROUP BY + JSON 函数 + LIMIT**（topN：图谱节点 200 / 边 800，**yml 可配置** `qc.graph.max-nodes / max-edges`，默认不变），不逐个病历内存解析 |
| 导出 | **流式**：CSV 逐行输出 / JSON Jackson streaming，3 万可导出（v1 仅子集 / 流式同步导出） |
| 防重 | Redis `SETNX tcm:task:{type}` 单 key + EX 900s（见 §8.7） |
| 索引 | 补 `(department, visit_time)` 复合索引（见 §5.3） |
| 性能基准 | 3 万全量重算 ≤3min；单页查询 ≤300ms；统计 / 概览 ≤2s |
| 验证数据 | 新增 `data/seed-30k.py`（**性能验证用，非演示数据**，与 seed-database.py 演示基线区分） |

#### 批B · 2.3 AI质控评分（分数真实化）

- **目的**　：按文档9.2 实现真实评分（calculateScore），替代随机分数。
- **改动点**：QcScorer / LogicChecker / QcController / batch 重算入口 / qc_results 预检单。
- **开发流程**：重算入口前端先行 预览桩 → 审核 → 后端评分 → batch 重算验证。
- **验收标准**：batch 后分级分布合理（非 85/12/3 随机）；抽查 `qc_results` 扣分明细与 score 一致；border 例（60/90 分）路由正确。**注：真实数据上的"分级分布合理"以批G 已接通为前提**（见 §1.2 / §7）；批G 未完成时仅能对 seed 数据验收。

**后端算法**

| 模块 | 设计 |
|------|------|
| `common/utils/QcScorer.java` | **判空规则**：核心字段按 structured_data 非空判断<br>structured 为空再回退查原始列（pulse/tongue/pattern/prescription）<br>两者皆空才判缺失 |
| 三层扣分 | ① 核心缺失各 -15（脉象/舌象/证候/治法/方剂/中药，共6项）<br>② 逻辑冲突各 -10（证候-治法 / 证候-方剂 / 证候-中药）<br>③ 格式+重复+症状为空 各 -5（age 非数字 / 性别非男女 / 文本MD5重复 / symptoms 为空） |
| 严重判定 | 核心缺失 ≥3；证候-治法与证候-方剂同时冲突；文本无法解析（三者之一命中）→ **直接 invalid**：分数**保留扣完值**（`score=max(0,扣完)`）**仅用于统计**，`grade="无效"`、`serious=true`；**分级与分数独立判定**，不因 invalid 强制归零 |
| 分级路由 | ≥90 且无逻辑冲突 → 合格<br>60~89 分或存在逻辑冲突 → 待复核<br>60 分以下或严重问题 → 无效 |
| `common/utils/LogicChecker.java` | 证候→治法→方剂规则（固定写死）：<br>· 风寒感冒 → 辛温解表 → 麻黄汤/桂枝汤<br>· 风热感冒 → 辛凉解表 → 银翘散/桑菊饮<br>· 暑湿感冒 → 清暑祛湿 → 新加香薷饮<br>舌脉规则：舌红×脉沉迟、舌淡×脉数 → conflict<br>**未覆盖证候不判冲突** |

**接口**

| 接口 | 说明 |
|------|------|
| `POST /api/qc/check` | 事前质控（缺失 / 格式 / 查重），入参 `QcCheckDTO`，返回 `QcCheckVO`（**必做11-12**）；与 `QcScorer` **共用判空 / 格式 / 查重口径**（单源） |
| `POST /api/qc/check/logic` | 诊疗逻辑一致性（**拓展1**），入参 `LogicCheckDTO`，返回 `LogicCheckVO`；与 `LogicChecker` **共用同一规则表**（单源） |
| `POST /api/qc/score` | 单条评分，入参 `QcScoreDTO`（结构化数据），返回 `ScoreResultVO` |
| `POST /api/qc/score/batch` | 全库/范围内重算（**分页分批 + 单条本地事务**，见 §1.3），返回分级分布 + **失败清单**；**无批量前置清理**（review_tasks 由单条幂等 upsert 收敛，见下）；**上限 `qc.batch.max-records`（默认 3 万，yml 可配）**：超限返回 400「超过单次上限，请缩小范围或子集操作」，前端超范围提示分片 / 子集 |

**`ScoreResultVO` 与 `qc_results` 写入结构（可溯源）**

 "grade": "待复核",
 "deductions": [
 {"type": "核心字段缺失", "item": "脉象", "points": 15, "reason": "pulseList 与 pulse 均为空"},
 {"type": "逻辑冲突", "item": "证候-方剂", "points": 10, "reason": "风寒感冒 不匹配 银翘散"}

| 项 | 明细 |
|----|------|

**与现有链路联动（含 review_tasks 一致性与事务）**
- 重算后看板 overview 数字自动正确；导出/预览只导"真实合格"；`governed` 不重置；
- **review_tasks 幂等 upsert（单条事务内）**：`grade=待复核` → 该病历已有非 obsolete 任务则**更新**（issueType/score），否则**新建**（deadline=+7 工作日）；`grade≠待复核` → 该病历 pending 任务置 **`is_obsolete=true`**；**无批量前置清理**；查询统一过滤 `is_obsolete=false`；

- **事务边界**：外层不包全局事务；单条=本地事务（评分+写 records+review_tasks 原子）；异常→记失败 ID、跳过并汇总失败清单（不回滚整体、不自动重试）；

## 8. 开发规范与协作

### 8.1 后端规范

- **分层**：`common`（config/domain/exception/interceptors/utils）+ `controller` + `domain`（dto/po/vo）+ `mapper` + `service`（接口）+ `service/impl`（实现）；
- **命名**：`I*Service` 接口 + `*ServiceImpl` 实现（`@Service`）；绑表服务 `extends IService<Po>` / `ServiceImpl<Mapper,Po>`；
- **响应**：统一 `Result{code,msg,data}`，文件流接口（导出/日志）除外；
- **异常**：业务异常由 `GlobalExceptionHandler` 统一出口（401 / 400 / 500 → Result），**Controller 禁止 try-catch 兜错**；
- **留痕**：清洗 / 导出 / 导入 / 回滚 / 复核等关键操作调用 `OperationLogger` 写 `logs/operation.log` 并入库 `operation_log`（**双写不做强一致、`try-catch` 分别捕获、仅留痕**；**以文件为准，库写失败不阻塞业务、仅缺审计页展示**）；
- **领域过滤**：范围筛选 / 数据域（角色行级权限）**统一走 `RecordFilter`**（批B · 4.1 公共工具），**禁止在业务方法中手写 where 条件**，避免口径漂移；**执行顺序固化：数据域（`operatorScope`）→ 用户筛选（filters），二者取交集（先降权再筛，防筛选绕过数据域）**；
- **并发一致性兜底**：review_tasks 幂等 upsert（SQL 语义）即**数据层兜底**（重复 batch 不重复建任务）；Redis 锁仅防重复触发，**不依赖锁保证状态正确**；
- **LLM 提示词归档**：Prompt 统一固化在 `LlmClient`（常量 / 配置），不散落前端或各接口，调整走代码评审 + 文档同步；
- **结构化数据契约**：`structuredData` 字段以功能设计 **附录A** 为唯一权威；字段变更先改文档再改代码；NLP 写入前校验必填键；
- **业务规则单源**：复核截止时间 / 工作日由后端 `ReviewTaskUtil` 一处生成，前端只读展示、不重算业务规则；
- **鉴权**：JWT（`JwtInterceptor`），放行 login / register。

### 8.2 前端规范

- **主题**：中式变量 `--ink/--paper/--line/--ochre/--danger`（见 `theme.css`），不加渐变 / emoji / 骨架滚动动画；
- **组件复用**：PanelCard / StatCard / BarList / TermInput / StatsFilter→RangeFilter / StructuredDataCard（新增），优先复用不新建；
- **请求**：统一走 `utils/request`（响应拦截 + blob 下载 `utils/download`）；接口封装于 `api/*.js`；
- **预览桩 定位（收紧）**：仅用于审核预览，**不上运行页**；合 main 前切真；接口未就绪用空态提示、不显示假数据；
- **契约对齐**：预览桩数据结构**必须与 openapi VO 完全对齐**（字段名/类型一致），仅填假值、不增删字段；

### 8.3 契约纪律

- 新增 / 变更接口：**先更新 openapi.yaml，再实现代码**；响应字段以 openapi 为准；
- **角色标注（强制）**：每个接口的 `description` 首部必须带 `【权限：…】`，四档取值——`仅管理员` / `登录即可` / `管理员 / 审核员` / `公开`，与 §1.2、§8.8 一致；新增接口漏标视为契约不完整，MR 不予合入；
- 错误码查 openapi 附录B（2001 / 4001 / 1006 / 2003 等）；前置校验统一 `IllegalArgumentException` → HTTP 400。

### 8.4 git 工作流

- 每线独立 commit、可独立回滚；commit 格式 `feat|fix|docs|refactor(scope): 描述`；
- 前端先行：见 §4.1；
- **分支模型**：见 §4.3（4 个长期分支：`main` + `XXJ`/`YC`/`ZRC`）；
- **MR 流程**：开发分支完成任务 → **提交 MR 到 main → 代码评审 + 验收测试通过 → merge**；main 保持随时可演示状态；**预览桩 / 静态假数据文件（如 graph-preview.js）须在切真接口、MR 合入前删除**；
- **MR 检查项**：合 main 前执行 `grep -rn "graph-preview|静态假数据" src/` 扫描，禁止预览桩数据文件合入；
- **菜单动态渲染**：评审 / MR 前前端菜单必须按登录角色**动态渲染**，**不得硬编码全开**；仅演示截图可临时以管理员账号截图；

### 8.7 并发防护约定

- **前提**：单机单实例部署，**无分布式一致性问题**；并发仅需防"同一人连点 / 重复提交"；
- **任务防重**：全库写操作（质控重算 batch / 数据清洗 clean）用 Redis **`SETNX tcm:task:{type} NX EX 900s`**（type=`batch`/`clean`，复用已有 RedisTemplate `setIfAbsent(key,val,Duration)`）抢占：执行中再触发 → 返回"任务进行中，请勿重复提交"；正常完成在 `finally` 中 `DEL` 主动释放；**进程崩溃由 EX 自动过期兜底（防死锁）**；单 key 即可（单管理员同一时刻只跑一个 batch，不做范围 hash）；
- **前端防重**：按钮提交后 disabled + loading，前端先拦一道，后端锁兜底；
- **时长监控**：任务开始 / 结束打日志，记录耗时；≥3 分钟打 **warn 日志**；3 万全量 ≤3min，余量充足；前端同步接口显示「执行中（当前范围：…）」+ 预计文案，**实时进度条不做**（同步接口无法轮询）；
- **幂等**：batch / clean 重复调用结果一致（review_tasks 由单条幂等 upsert 收敛、无前置批量清理，见 批B·2.3）；
- **词典文件**：导入 / 回滚 / 备份方法加 JVM 锁（synchronized），避免并发覆盖词典 JSON 与 ES 索引重建冲突。

### 8.8 角色鉴权约定

| 角色 | 菜单 | 接口权限 |
|------|------|---------|
| 管理员 | 8 项全量（首页/病历/结构化解析/质控校验/复核/清洗导出/词典/审计） | 全部（含治理/词典/质控/导出 等管理操作） |
| 审核员 | 首页看板 + 人工复核 | 登录、看板统计、复核（批D）、**病历读取（批F，数据域限 `grade='待复核'`）** |

- **机制**：`@RequireRole("管理员")` + `RoleInterceptor`（未过 → 403 + Result）；前端路由 `meta.roles` + 守卫，`MainLayout` 按登录 menus 渲染；
- 后端强制拦截越权：审核员直输管理 URL 返回 403；
- **数据域（行级权限）**：审核员可读数据域=`grade='待复核'`（复核域），管理员=全库；`/api/ai/*` 与病历读取同域过滤；**执行顺序：先数据域、后用户筛选，取交集（见 §8.1）**；
- **新增接口默认**：写操作默认"仅管理员"，只读默认"登录即可"，复核专接口默认"双角色"。

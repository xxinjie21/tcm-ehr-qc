> 记录时间：2026-10-05 · 数据规模：**35,500 条**（自造 35,000 条标记数据 + 真实 500 条）
> 数据来源与清理：`tools/gen-bench-data.py`（只写 `org_id='bench-org'` ⇒ 清理一条 DELETE）
> 计时口径：SQL 用 MySQL 服务端 `NOW(6)` 前后差（不含进程启动）；接口用 HTTP 往返（含序列化与网络）
> **本文件是「批次 12 动工前必须先有当前值」那条规则的凭据**；未测项如实标注，不编数字。

## 一、SQL 层（MySQL 服务端计时）

| 场景 | 基线 | 加 `idx_records_visit_time` 后 |
|---|---|---|
| 单条（按 id） | 1.65 ms | —（已命中主键） |
| 全库计数 | 1.94 ms | — |
| 分页 offset **500**（第 25 页，真实深度） | **235 ms** | **25 ms** |
| 分页 offset 2000 | — | 111 ms（单次读数，疑抖动） |
| 分页 offset 10000 | — | 47 ms |
| 分页 offset 30000 | 195 ms | **48 ms** |
| 按科室聚合（5 组） | 224 ms | — |
| **按月聚合（12 组）** | **249 ms** | **14.6 ms** |
| JSON 扫描（`structured_data->'$.symptoms[0].normLevel' IS NULL`） | 215 ms | 183 ms |

**结论**：索引命中类（单条/计数）本就毫秒级，不必动；**聚合**受索引收益最大（17×）；深 offset 不是索引能解决的问题（属键集分页范畴，用户极少翻到，记为已知限制）。

## 二、接口层（HTTP 往返，各 3 次）

| 接口 | 3 次读数（ms） | 形态判断 |
|---|---|---|
| `/stats/overview` | 181 / 207 / 234 | 整表载入 Java 归约（`StatsServiceImpl:105`） |
| `/stats/departments` | 246 / 251 / 248 | 同上 |
| **`/stats/standardization-report`** | **6231 / 4821 / 3539** | **整表载入 + 逐条解析 JSON**（`…ReportServiceImpl:81/291`）⇒ **全场最热** |
| `/governance/stats` | 302 / 296 / 300 | 同族 |

**与 SQL 的落差是关键证据**：按月聚合 SQL 只要 **14.6 ms**，而报告接口要 **3.5~6.2 s** ——
差在两个数量级的不是数据库，而是「把 3.5 万行拉进 JVM、逐条 `JSON.parse` 再归约」这一层。

## 三、两次测量教训（写给后来者）

1. **单次读数不足以下结论**：首次复测深分页得到 1034 ms（比基线慢 5 倍），据此写过「索引拖慢深分页」；
   补齐三档深度 + 去掉索引做对照后，确认那只是**瞬时抖动** —— 索引在三档深度上都更快。
2. **测量口径要写清**：SQL 服务端计时与 HTTP 往返含的东西不同（前者不含进程启动、后者含网络与序列化），
   两者不可直接比较，所以本文件分两张表记。

## 追加（2026-10-05 晚）：12d 试点的实测结论 —— **已回退**

批次12 · 12d 曾把报告的八个消费方全部改走库内 JSON_TABLE 聚合（unmatched / coverage /
normalizableRate / score+qc / range+dataset / byMonth），并摘掉了整表载入。功能**逐位等价**
（3026/20/0/270/2736、九类、361/361、84 组、capped 234、数据集 500/10/320 全中），
但在 35,500 条上**更慢**：

| 数据量 3.5 万条 | 改造前 | 改造后（三次） |
|---|---|---|
| /stats/standardization-report | 6231 / 4821 / 3539 ms | **8675 / 9170 / 9025 ms** |
| /stats/overview（旁证） | 181-234 ms | 312 ms |
| /stats/departments（旁证） | 246-251 ms | 314 ms |

已做的定位（给数字，不猜）：口语症状子查询 819ms、selectByMonth 双派生表 773ms、
症状展开 284ms、九类 UNION 224ms。**但纯 COUNT(*) 也要 216ms**，说明经
`docker exec + mysql CLI` 的每条查询有约 200ms 固定开销 —— 这些数字**不能**当作接口耗时的证据。
已知几条加起来约 1.3s，远小于接口的 9s，**9 秒的归属未能定位**，需要在应用侧做 profiling。

### 本轮新增的两条测量教训

1. **测量通道自身有固定开销时，不能用它给被测对象定量。** CLI 每条查询约 200ms，
   拿它去判断「哪条 SQL 是瓶颈」会得出错误结论；要用应用内的计时或 DB 侧的慢查询日志。
2. **基线的数据量必须与复测一致。** 基线在 3.5 万条上测得，而库里当时已被清成 500 条，
   差一点就用 500 条的 217ms 去对比 3.5 万条的 6231ms —— 那是苹果比橘子。

### 留下的东西（未回退）

- `tools/verify-unmatched-sql.py`：八项不变量验收脚本（分项自洽、TOP 明细、规则夹具）。
  下次再走 SQL 路线可直接复用；它证明了「SQL 能算对」，只是这个数据量下不划算。
- 本次结论本身：**先量后改**，且**改完要再量**；未证明获益的改动不进主干。

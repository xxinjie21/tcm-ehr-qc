1. **单次读数不足以下结论**：首次复测深分页得到 1034 ms（比基线慢 5 倍），据此写过「索引拖慢深分页」；

## 追加（2026-10-05 晚）：12d 试点的实测结论 —— **已回退**

批次12 · 12d 曾把报告的八个消费方全部改走库内 JSON_TABLE 聚合（unmatched / coverage /
normalizableRate / score+qc / range+dataset / byMonth），并摘掉了整表载入。功能**逐位等价**
（3026/20/0/270/2736、九类、361/361、84 组、capped 234、数据集 500/10/320 全中），
但在 35,500 条上**更慢**：

| 数据量 3.5 万条 | 改造前 | 改造后（三次） |
|---|---|---|
| /stats/standardization-report | 6231 / 4821 / 3539 ms | **8675 / 9170 / 9025 ms** |
| /stats/overview（旁证） | 181-234 ms | 312 ms |
| /stats/departments（旁证） | 246-251 ms | 314 ms |

已做的定位（给数字，不猜）：口语症状子查询 819ms、selectByMonth 双派生表 773ms、
症状展开 284ms、九类 UNION 224ms。**但纯 COUNT(*) 也要 216ms**，说明经
`docker exec + mysql CLI` 的每条查询有约 200ms 固定开销 —— 这些数字**不能**当作接口耗时的证据。
已知几条加起来约 1.3s，远小于接口的 9s，**9 秒的归属未能定位**，需要在应用侧做 profiling。

### 本轮新增的两条测量教训

1. **测量通道自身有固定开销时，不能用它给被测对象定量。** CLI 每条查询约 200ms，
   拿它去判断「哪条 SQL 是瓶颈」会得出错误结论；要用应用内的计时或 DB 侧的慢查询日志。
2. **基线的数据量必须与复测一致。** 基线在 3.5 万条上测得，而库里当时已被清成 500 条，
   差一点就用 500 条的 217ms 去对比 3.5 万条的 6231ms —— 那是苹果比橘子。

### 留下的东西（未回退）

- `tools/verify-unmatched-sql.py`：八项不变量验收脚本（分项自洽、TOP 明细、规则夹具）。
  下次再走 SQL 路线可直接复用；它证明了「SQL 能算对」，只是这个数据量下不划算。
- 本次结论本身：**先量后改**，且**改完要再量**；未证明获益的改动不进主干。

## 11.2 · ES 归一 QPS（2026-10-06 实测，补齐批次 11 的缺项）

**测量口径**：本机、ES 7.17.22（docker）、顺序单线程 200 次取均值；同时给出「ES 直连」与
「接口层」两列，用来互相印证 —— 接口每次内部恰好 **1 次** ES 检索。

| 口径 | 200 次耗时 | 单次 | QPS |
|---|---|---|---|
| ES 直连 `_search` on `term_symptom`（72 条） | 1306 ms | 6.53 ms | **153 req/s** |
| ES 直连 `_search` on `term_disease`（1364 条） | 472 ms | 2.36 ms | **424 req/s** |
| 接口层 `POST /governance/normalize`（type=symptom） | 2701 ms | 13.5 ms | **74 req/s** |

**读法**：接口 13.5 ms − ES 6.5 ms ⇒ 约 **7 ms** 是鉴权/序列化/线程等固定开销。
症状索引比疾病索引慢近 3 倍（6.53 vs 2.36 ms），与索引规模不成正比，属于分词/词典特性差异，
不额外解释。

**这不是什么**：不是并发压测（单线程顺序），不含 P95，也没测批量接口。
数字用于回答「当前每次归一要花多少时间」，供批次 12b 判断批量化能省下多少。

### 对 12b 的意义（先量后改）

- 现状：`EsTermNormalizer.normalize` → `recall` → `esTermIndexService.search(...)`，
  即 **每个术语一次 ES 往返**；批量路径 `EntityNormalizer:87` 对每个实体循环调用它。
- 量化：症状类 6.53 ms/次 ⇒ 一次 40 个实体的解析，仅 ES 往返就约 **260 ms**。
  这部分正是「批量 + 同批 LRU」能省掉的上限（同批内重复术语越多、省得越多）。
- 12b 的验收因此可测：**ES 请求次数下降**（打点）+ **结果与改造前逐条一致**（对照）。

## 12b 进展与「还差的一寸」（2026-10-06）

**12b 原文**：ES 归一逐术语往返 → 批量 + 同批 LRU；验收「请求数下降；结果与改造前逐条一致」。

| 半 | 状态 | 凭据 |
|---|---|---|
| **同批 LRU** | ✅ **已上线生效** | `EsTermIndexServiceImpl.search` 上加键 `type\|org\|input` 的 LRU（上限 4096）；`rebuild` 一开始清空它 —— 否则重建后仍命中旧结果，即 12g 所虑的脏读。4 个单测锁住（同术语两次只打 1 次 ES / 键含三者 / 清后重查 / 空白不发请求） |
| **批量（`_msearch`）** | ✅ **已实现并已测，但尚无生产调用方** | `searchBatch` 一次往返查 N 个术语；用 msearch 而非 `bool.should`，因为后者无法把命中归属回输入，而 msearch 的子查询与单条 search **逐字相同**、响应按序返回 ⇒「逐条一致」是结构性的 |
| 预取链路 | ✅ **已测通** | 一次 `searchBatch`（1 次 msearch）之后，对同批术语的逐条 `search` **zero 次 ES** |

**还差的一寸（如实记）**：`EntityNormalizer` 里有多处逐实体循环（`:310` 症状 · `:363` 中药 · `:401`
其他实体 …），它们各自在循环内调用 `termNormalizer.normalize(type, orgId, raw)`。要让「批量」
在生产里生效，需要在每个循环**之前**用该循环同样的 type 字面量与 `rawOf(content, sourceText)`
预取一次。这需要逐个循环核对 type 字面量（`:363` 用的是 `"herb"` 这样的字面量），
是一次改动面较大的接线，本次未做 —— 因此**当前生产上生效的是 LRU 那一半**，
批量的收益尚未落到实际请求上。

**这不是等价性问题**：两条路径都只读召回结果，且批量与逐条共用同一份缓存键，
接线前后归一结果不会有任何差异（同样的候选、同样的 `EsTermNormalizer` 三级判定）。

## 12c · 清洗耗时（2026-10-06 实测，先量后改且改完再量）

**基线（旧代码）**：3.5 万条、`POST /governance/clean` = **443.1 秒**。
返回体给了元凶线索：`cleared/deduped/isolated` 全为 0、`repaired` 为 0 ——
即绝大多数行**本来就无需改动**，而代码对每一行都发一次 `updateCleanFieldsWithoutStatus`。

**改动**：只在 `repaired > 0` 时才写（`repaired` = 四个字段 trim 后与原值不同的个数；
为 0 表示库里存的正是 trim 后的值，那条 UPDATE 不改变任何数据）。语义等价，不是「少做」。

**改完再量（新代码）**：**166.8 / 151.6 秒** ⇒ 约 **2.8 倍**。
两次的返回体与基线一致（total 35500、各计数 0），说明行为没变。

### 一次差点写错的测量，值得记

新代码的第一次测量报 **52.3 秒**，看起来是 **8.5 倍** —— 但那一次**以 500 失败告终**
（`Lock wait timeout exceeded`）。原因是：我用 `job_kill` 停掉的是 **PowerShell 作业**，
而 8080 上那次清洗的**服务端请求并没有被取消**，它继续持有大事务的行锁，
于是 8081 的更新撞上它、等满 50 秒超时。库里印证：`Innodb_row_lock_waits=2`、
`row_lock_time_max=50006ms`（正好是 50 秒超时）。

⇒ 教训与之前那条同源：**测量通道不能改变被测对象**。这次是「停客户端 ≠ 停服务端」，
上一条是「日志截断把 java 进程一起杀了」。若没查失败原因，就会把 8.5 倍写进结论。

**未做的另一半**：`selectList` 仍把 3.5 万条整批读进内存（12c 原文的「流式」），
剩下的约 150 秒主要在这里与逐行 JSON 校验上 —— 留作下一步，单独量。

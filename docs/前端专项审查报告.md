## 二、性能瓶颈

### 2.1 不必要的重渲染

- **`components/AiAssistant.vue:40` 模板内调 `lines(m.text)`**（定义在 `:116`）
  成因：函数在模板中调用无缓存，而 `draft` 双向绑定输入框，每敲一个字符触发整面板重渲染。
  影响：消息越多、回答越长，每键都把全部回答重新 `split`/`filter`；20 条消息时每键约 0.5~2ms，输入有可感知迟滞。
  方案：push 消息时预存 `lines`，或提为 `computed(() => messages.value.map(m => ({...m, lines: lines(m.text)})))`。
  收益：每键模板计算由 O(全部消息文本) 降为 O(1)。

- **`views/Records.vue:186` 的 `v-for="f in fieldsOf(g)"`**（定义在 `:292`）
  成因：每次渲染都 `map+filter` 重建 21 个字段对象，数组引用全变。
  影响：新增页每次重渲染（含输入每键）重建字段定义数组并 diff 全部表单项。
  方案：把 `FIELD_GROUPS.map(g => ({...g, fields: fieldsOf(g)}))` 提到模块级常量。
  收益：每次重渲染少 21 次对象创建，并让 `v-for` 引用稳定。

- **`views/Qc.vue:88/89/91/94` 的 `fmtOf(t.field)` 与 `customFormats`**（定义在 `:484` / `:486`）
  成因：`fmtOf` 每次 `find` 一遍 `form.format`；`customFormats` 是 `filter` 内嵌 `some`，O(n×m)。
  影响：规则项多时，弹窗每次重渲染做数十次线性查找。
  方案：`fmtOf` 结果提为 `computed` 的 Map（`{field: rule}`）；`customFormats` 用 Set 缓存 catalog field。
  收益：查找由 O(n×m) 降为 O(1)。

### 2.2 耗时计算

- **`views/Qc.vue:179` 的 `barWidth(t.points)`**（定义在 `:387`）
  成因：`Math.max(1, ...byType.map(...))` 逐行调用，每行重算一次 max。
  影响：`byType` 有 n 行就重算 n 次，O(n²)；n 约 10，绝对量小但属可完全消除的开销。
  方案：提为 `computed` 求一次最大值，模板只做除法。
  收益：每次重渲染少 n 次全量 map。

- **`views/Review.vue:103/143/149` 重复调 `originalText(f.key)`**（同字段调 2~3 次），`:135` 的 `isFixed`
  成因：函数每次 `map`/`filter`/`join`；`editValues` 双向绑定，每键触发整面板重渲染。
  影响：9 个对照字段 × 每字段约 3 次 = 每键约 27 次数组操作，外加 `estimate` 重算。
  方案：`originalTextMap = computed(() => Object.fromEntries(COMPARE_FIELDS.map(f => [f.key, originalText(f.key)])))`，模板改读 map。
  收益：每键数组操作由约 27 次降为 9 次。

### 2.3 阻塞操作

- **`views/Dashboard.vue:295` 的 `handleResize` 未节流**（监听在 `:291`）
  成因：每次 `resize` 事件同步对两个 ECharts 实例调 `resize()`，无 rAF / 防抖。
  影响：拖拽窗口时每秒可触发 60+ 次双图重排，主线程抖动明显。
  方案：用 `requestAnimationFrame` 合并，或 100ms 防抖；卸载时取消待执行帧。
  收益：resize 期重排次数降一个数量级。

- **`views/NlpExtract.vue:770` 轮询双请求且后台空转**
  成因：`setInterval(() => { poll(); loadBatchList() }, 2000)` 单 tick 发 2 个请求，且与标签页可见性无关。
  影响：任务运行期间每 2s 固定 2 次请求；3.5 万条的长任务累计上千次无效拉取。
  方案：`loadBatchList` 降频（如每 10s）；`watch(activeTab)` 在非批量标签时 `stopPoll`，切回再启。
  收益：轮询请求量降约 80%。

### 2.4 请求层

- **`views/Dashboard.vue:258` 管理员多一轮瀑布** —— `await governanceStats()` 串在 `:251` 的 `Promise.all` 之后。三接口本可并行，却写成「两块并行 + 一块串行」，管理员每次查询多等一个 RTT（内网约 20~80ms）。方案：并入 `Promise.all`（非管理员传 `Promise.resolve(null)`）。

- **5 处列表请求无竞态保护** —— `Records.vue:312`、`NlpExtract.vue:400`、`Qc.vue:609`、`AuditLog.vue:145`、`Review.vue:286` 均直接 `await` 后覆盖 `rows`/`total`，无 latest-wins 序号或 `AbortController`。3.5 万条下翻页 / 改筛选的响应耗时差异大，**慢的旧响应会覆盖新结果**，出现「页码与数据不符」。方案：仿 `components/TermInput.vue:32` 的 `seq` 取号，回来时 `if (mine !== seq) return`；或给 axios 传 `signal`。收益：消除脏渲染，无额外请求。

- **科室下拉重复请求** —— `components/RangeFilter.vue:73-81` 的 `onMounted` 调 `getDepartments()`；Records / Qc / NlpExtract / Governance 四页各自挂载 `RangeFilter`，每次进页重拉同一份 DISTINCT。科室列表变动极低频，属纯浪费。方案：在 `api/stats.js` 或 Pinia 做 Promise 单例缓存。

## 五、加载速度

- **Element Plus 全量引入（首要问题）** —— `src/main.js:3-5`：
  ```js
  import ElementPlus from 'element-plus'
  import 'element-plus/dist/index.css'
  app.use(ElementPlus, { locale: zhCn })
  ```
  未用 `unplugin-vue-components` 按需引入，全量注册组件 + 全量 CSS。实测 `element-plus-*.js` = **939 kB（gzip 302 kB）**、`index-*.css` = **363 kB**，且 `dist/index.html:44` 对它做了 `modulepreload` → **在首屏关键路径上**。
  影响：首屏 JS 约 1.05 MB（vue 112 kB + element-plus 939 kB），CSS 363 kB 渲染阻塞；3G 弱网下仅 element-plus 单 chunk 的传输与解析可占 1.5~2.5s，是首屏时间主因。
  方案：引入 `unplugin-vue-components` + `unplugin-auto-import`，只对 `ElMessage` / `ElMessageBox` 显式引入。
  收益：element-plus chunk 约 939 → 300 kB 级，CSS 363 → 60~100 kB，首屏 gzip 减约 200+ kB。**全局影响**：8 个页面共用引入方式，改造后全部受益；需回归验证 `el-table` / `el-dialog` / `el-select` 等被正确自动解析。

- **无 gzip / brotli 预压缩** —— `vite.config.js:5-6` 的 `plugins: [vue()]` 未装 `vite-plugin-compression`，产物目录无 `.gz` / `.br`。若部署侧（nginx）未开 gzip，`dist/assets` 共约 **2.3 MB** 将原样传输。方案：加 `vite-plugin-compression`。收益：服务端未压缩时首屏省约 65~70%。**仅新增产物文件，不影响页面逻辑，需部署端配合**。

- **路由懒加载合规** —— `router/index.js:9-25` 10 个路由**全部** `() => import()`，无静态 import 拖入首屏；echarts（574 kB）经 `utils/echarts.js` 按需注册且仅 Dashboard 加载，**不在首屏**。

- **首屏关键路径合规** —— `index.html` 无 CDN 字体 / 图标，含内联首屏占位样式（`:9-41`），无额外阻塞资源。

## 六、渲染效率

- **`Qc.vue:104/112` 可编辑列表用 index 作 key（唯一确凿风险）**
  ```vue
  v-for="(f, i) in customFormats" :key="i"     <!-- 含 el-input-number v-model + removeCustomFormat(i) -->
  v-for="(c, i) in form.consistency" :key="i"  <!-- 含 4 个 el-select v-model + splice(i,1) -->
  ```
  成因：可增删 / 可编辑的行却用 index key，删除中间行时 Vue 就地复用 DOM，组件内部状态（`el-select` 过滤态、`input-number` 临时值）会错位到相邻行。
  影响：**删除一致性规则后，用户已选的下拉值与扣分可能串行错位** —— 这是功能正确性风险，不是纯性能问题。
  方案：新增行时生成稳定 `uid`（自增或 `crypto.randomUUID()`），`:key="c.id"`，提交前剥离 `id`。
  收益：消除复用错位。**改动仅 `Qc.vue` 一个文件**。

- **`AiAssistant.vue:127` 拖动动画走 `left`/`top` 且无 rAF 节流** —— `:153-159` 每个 `pointermove` 直接改 `pos.value`，改 `left`/`top` 会触发 layout。方案：改 `transform: translate(x,y)` + rAF 节流。收益：拖动进入合成层，无 layout。（面板展开动画 `:443-446` 已正确用 `opacity + transform`，合规。）

- **其余 index key 均安全** —— `AiAssistant.vue:37`（消息仅追加）、`Dictionary.vue:157`、`Review.vue:112/121/178`、`Qc.vue:60/280`、`StructuredDataCard.vue:20` 均为只读 / 不重排渲染，无需改。

- **`AuditLog.vue:49` 表格未设 `max-height`** —— 而 `page-sizes=[10,20,50]`（`:77`），用户选 50/页时整表展开无内部滚动。方案：补 `max-height="520"`（与 Governance 一致）。低危。

- **清理与 DOM 读取合规** —— `Dashboard.vue:291/301` resize 成对增删、`:303` 卸载 `dispose()` 图表；`AiAssistant.vue:278/279 ↔ 282/283` 成对；`AiAssistant.vue:212` 读 `scrollHeight` 仅在 `nextTick` 后单次（非循环）；无循环内强制同步布局。

## 七、界面视觉设计评估

### 7.1 配色

- **约 20 处面板底直接写 `#fff`**（`PanelCard.vue:22`、`StatCard.vue:47`、`Governance.vue:453/479/605`、`Review.vue` 多处、`AiAssistant.vue:392/418/439`、`NlpExtract.vue:1073`）。五个令牌之外还有 **130+ 处颜色字面量**（`Review.vue` 24 处、`NlpExtract.vue` 12 处、`MainLayout.vue` 13 处），`StatCard.vue:89` 直接写 `#a04335` 而非 `var(--danger)`。方案：新增 `--surface` / `--surface-sub` 令牌并批量替换。
- **对比度不达标** —— `MainLayout.vue:231`、`Review.vue:786` 用 `#a09c90`，在 `#fbfaf6` 上约 **2.6:1**，低于 WCAG AA 的 4.5:1，侧栏分组名与字段提示明显发灰难读；`Qc.vue:742` 的 `#96714f` 在 `#fdf6e8` 上约 4.1:1，临界。方案：改用 `--text-sub`（4.64:1）。
- **骨架屏用了渐变** —— `AiInterpretCard.vue:173/186` 的 `linear-gradient(90deg,…)` 扫光，**违反项目「禁渐变」约定**。方案：纯色 + `opacity` 呼吸动画。

### 7.2 布局

- **`Dashboard.vue:310-315` 待办条 `repeat(3,1fr)` 只放 2 张卡**，右侧 1/3 恒空（注释已自认「第 3 列留空」）。这是整页最显眼的版面失衡。方案：改 `repeat(2,1fr)` 或 `auto-fit`，**零结构改动**。
- **间距无体系** —— `AuthShell.vue:115`（`margin:7px 0 24px`）、`NlpExtract.vue:938`（`padding:7px 11px`）、`Review.vue:792/910`（13px）、`StatCard.vue:50`（`14px 18px`）、`Governance.vue:459`（`gap:48px`）—— 7/9/11/13/18/22/26/48 混排，纵向密度忽松忽紧。方案：收为 4/8/12/16/24 五档（可只加 `--space-*` 令牌，不动布局）。
- **`Review.vue:714` 自写 `.panel-hd` 缺竖条装饰** —— 字号与 `PanelCard.vue:32` 一致，但没有 `::before` 的 3px 竖条，与全站其他面板标题不一致（已定缺陷修复项的残留）。

### 7.3 视觉层次

- **`Qc.vue:923-945` 评分瀑布的最终得分无突出** —— `.wf-num` 与 `.end .wf-num` 同为 12.5px，全页最关键的「最终得分」与每行扣分等权，扫读抓不到重点（对比 `Review.vue:849` 的 `.preview b` 有 17px）。方案：`.end .wf-num` 提至 16~17px bold，配色不变。

- 双栏在 ≤1200 收单列（`NlpExtract.vue:924` 的 1.25fr/1fr、`Review.vue:928`、`Governance.vue:694`），1366 下核心双栏仍成立（各约 565px），无塌陷风险。`RangeFilter.vue:8/29/34/38` 写死 140/240/150/110px 使筛选条总宽约 640px，1366 下与 4 个按钮同行必换行，但有 `flex-wrap` 兜底，**维持现状即可**。

### 7.6 总评

**整体观感：一般偏上。** 墨绿 / 赭石 / 宣纸的中式调性克制统一，无 emoji、无花哨动效，基调是好的。问题集中在**「不一致」而非「不好看」** —— 同一语义的色 / 圆角 / 标题装饰在 8 个页面里各写各的，导致系统看起来像「多人拼装」。

**最影响观感的 3 个问题**：

1. `Dashboard.vue:310-315` 待办条 2 卡占 3 列，右侧 1/3 永久空白（首屏第一眼即见）。
2. 错误 / 警示浅底 4 套并存，同页混用（`Qc.vue` 内 `#fdf6e8` 与 `#fdf3f1` 同屏）。
3. 约 20 处 `#fff` 面板底 + 圆角 7 种混排，卡片「厚薄不一」；叠加 `#a09c90`（2.6:1）发灰的次级文字。

**若只改 3 处，收益最大**：

1. 加 `--surface` 令牌替换全部 `#fff` 字面量、圆角收为 2/4/6 三档 —— 一次性拉齐所有卡片观感。
2. 错误 / 警示浅底各收敛为 `--danger-surface` / `--ochre-surface`，并把 `#a09c90` 换成 `--text-sub`。
3. `Dashboard.vue:310` 的 `.todo-bar` 改 `repeat(2,1fr)` —— 零结构改动，直接消掉首屏空白列。

> 以上均为**不改排版结构**的优化项。所有样式改动须在 **1600×900 与 1366×768** 两档视口实测后再合入。

## 八、商业功能完整性

> 无「前端绕过 API 层直连」的情况（前端无 `import request` 直接使用）。

### 8.2 业务闭环

导入 → 解析 → 归一 → 评分 → 复核 → 清洗导出，**主链路可完整从界面操作**：

- **导入**（`Records.vue`）：同步接口，返回失败清单；**不可回滚**。
- **结构化解析**（`NlpExtract.vue`）：单条 + 批量异步（线程池、进度 / 取消 / 失败清单落库），关页可回、失败可重跑，**闭环最好**。
- **术语归一**（Governance / Dictionary）：词典导入 / 转换 / 回滚 / 备份齐全；但强依赖 ES，索引不可用即整体失败。
- **质控评分**（`Qc.vue`）：单条 / 批量 / 规则读写重置 / 扣分统计齐全。
- **人工复核**（`Review.vue`）：任务列表 + 提交，含 7 工作日 deadline 与 reviewed_by。
- **清洗导出**（`Governance.vue`）：clean + export（csv/json，含打码）+ 预览。

**薄弱点**：失败恢复 —— 导入无回滚、删除为硬删（`deleteBatchIds`）无回收站。

### 8.3 商业上必要但缺失的能力

| 缺失项                   | 现状                                                                              | 商业后果                                                                   | 补齐难度 |
|--------------------------|-----------------------------------------------------------------------------------|----------------------------------------------------------------------------|----------|
| 用户管理                 | 仅注册（强制审核员）+ 登录；无列表 / 改角色 / 改密 / 停用；`users` 表无 status 列 | 离职无法停号、无法增管理员，账号管理失效                                   | 中       |
| 数据隔离                 | 仅按 grade 分级域（审核员=待复核、管理员=全库），无科室 / 医生行级权限            | 多科室共用时审核员可见全院待复核病历，不满足隐私隔离                       | 中高     |
| 审计合规                 | 有操作日志 + 检索 + CSV 导出（§七 L3：purge 已删）      | 无留存策略、无防篡改，等保 / 电子病历评级可能不过 | 低-中    |
| 数据生命周期             | 删除为硬删，无软删 / 回收站；无备份                                               | 误删 3.5 万条不可恢复                                                      | 中       |
| 导出与报表               | 仅 csv / json；看板无打印 / 导出 / 订阅；pom 有 poi / pdfbox 但未用               | 无法生成上报级固定报表、不能定时推送                                       | 中       |
| 集成能力                 | 无 HIS / EMR、无 FHIR / HL7、无 MQ，仅 xlsx 导入                                  | 不能从 HIS 实时取数，医院采购硬门槛                                        | 高       |
| 运维能力                 | 无 actuator / health（Java）、无 prometheus、无限流；仅 Python 有 `/health`       | 无法接监控告警、容器探活缺失                                               | 低       |
| 多语言 / 多院区 / 多租户 | 无 tenantId、无 i18n                                                              | 无法 SaaS 化，多院区只能独立部署                                           | 高       |

### 8.4 代码难度评估（以现有状态为准）

> **2026-09-28 注：§8.3 表前 3 项已有归属，不在本报告实施范围**
> - **用户管理** → 由《多课题组改造计划》R1/R5 解决（`users.status` + 课题组管理 / 成员管理 2 个新页面）
> - **数据隔离** → 由该计划 R3 解决（`grade` 分域改为课题组隔离；`grade` 退回纯业务字段）
> - **审计合规** → purge 已由§七 L3 删除；剩下的「日志读接口加 `operator` 强制条件」由该计划 R4/L7 解决
>
> 其余 5 项（数据生命周期 / 导出与报表 / 集成能力 / 运维能力 / 多租户）**本报告只记录，未排期**。

**规模**：Java 133 文件 / 12963 行、Vue 25 个 SFC / 8689 行、前端 JS 679 行、Python 2 文件 / 264 行（仅 RoBERTa NER 推理）。测试 15 个 Java 测试类，**无前端测试、无 CI**。

**技术含量最高的四处**：

1. Spring AI 2.0 集成 —— `LlmClient` 懒装配 + openai / ollama 双供应商 + 版本号热重建。
2. ES 术语归一 —— `EsTermNormalizer` + 索引重建与版本跳过。
3. NLP 异步批处理 —— 线程池 + 落库 + 进度 / 取消 / 失败清单。
4. 规则驱动质控 —— `QcRuleSet` / `QcScorer` / `LogicChecker`。

**常规 CRUD**：Auth / Record / Dictionary / Log 四个 Controller 与 Stats 聚合。

**结论**：这是一套**「演示级偏上、产品化不足」**的全栈系统。架构与工程意识（数据域、审计、注释规范、事务边界）明显高于普通课程项目，AI / ES / 异步三条链路有真实技术门槛；但商业必需能力（用户权限、数据隔离、HIS 集成、运维监控、多租户）几乎全缺 —— **当前状态可演示、不可直接交付医院使用**。

### 8.0 排序判据（报告 §二.1）

体验项优先级按三条判据评定：**人时消耗**（频次 × 单次耗时）· **错误代价**（后果 × 可逆性）· **阻塞性**（卡住则后面全走不通）。报告的**逐环判定**（6 个环节，全文照录）：

| 环节 | 频次 | 单次耗时 | 错误代价 | 阻塞性 | 判定 |
|---|---|---|---|---|---|
| 批量解析 + 质控 | 每批必跑 | 极高（500 条实测 89 秒） | 中（可重跑） | 强 | **关键** |
| 人工复核 | 每批都有待复核 | 极高（逐条读原文 + 对照 + 裁决） | 高（裁决影响定级与导出） | 强 | **关键** |
| 结果数字可信度 | 每次看板/报告 | 低 | 极高（口径分裂会让用户按错数字决策） | 中 | **关键** |
| 失败可识别 | 每次操作 | 低 | 高（静默失败会让用户把「没做」当成「没问题」） | 中 | **关键** |
| 术语词典维护 | 低频 | 中 | 中 | 中 | 重要 |
| 日志审计、组织管理 | 低频 | 低 | 低 | 弱 | 一般 |

结论：最需优先的是「批处理进度与结果反馈」「人工复核」两个人时黑洞 + 「数字可信度」「失败可识别」两个信任底座 —— **前者决定用户累不累，后者决定用户敢不敢信**。

### 10.2 诊断结论：`snapshot` 并未挂死，是**会话没对上**

**证据（后台作业最终 `exit=0`，返回结构化 JSON）**：

```json
{"success":true,"data":{"origin":"about:blank","refs":{},
 "snapshot":"(no interactive elements)",
 "lifecycle":{"launched":true,"reused":false,"relaunchedBrowser":false}}}
```

**判读**：`reused:false` + `origin:about:blank` ⇒ 执行 `snapshot` 时**连的不是刚 `open` 的那个页面**，而是另一个 session 里新启的空白浏览器 ✗。也就是说：命令本身可用（返回 JSON、退出码 0），失败在于**前后两条命令落在了不同 session**。

**下一步（可执行）**：
1. **每条命令显式带同一个 `--session <name>`**，不依赖环境变量跨进程传递（`open` / `snapshot` / `click` 全部带上）；
2. **快照后先断言 `origin` 等于目标 URL**，不符立即报错退出 —— 避免把「对空白页的成功快照」当成「页面没问题」（这与本计划反复强调的「状态不许撒谎」同源）；
3. 断言通过后再把「登录 → 主链路 → 内页」写成脚本，与报告第一版的无头实测互补。

### 10.3 一处操作纪律（本轮自省）

排查时我打印到了系统中多个 `node` 进程，但**没有杀任何一个** ✗ —— 其中可能包含本会话所在 Web GUI 自身的 node 进程，盲目清理会直接弄断会话。**结论：清理进程前必须先确认归属，宁可留着也不误杀。**

1. **JWT secret 必须轮换**（最高优先）：换新值后**所有已签发 token 立即失效**，用户需重新登录 ⇒ **时机由你定**（工作时段/停机窗口）

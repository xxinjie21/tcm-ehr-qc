# 25.4 EXPLAIN 对照：records 补 (org_id, visit_time) 复合索引

日期 2026-10-06 · 批次 25 工作项 25.4 · 环境 MySQL 9.7.2（本地 tcm_ehr 库）

## 为什么做

病历列表 / 导出 / 统计查询的通用形态是「org_id 等值（数据域，见 RecordFilter 的 operatorScope）
+ visit_time 范围或排序」。既有索引 `idx_records_org (org_id)` 与 `idx_records_visit_time (visit_time)` 都是单列，
MySQL 只能选其一，另一维只能回表后过滤。

## 怎么测（可复现，不动业务数据）

在 tcm_ehr 里建了一次性探针表 `records_explain_probe`（`CREATE TABLE ... LIKE records`），
用递归 CTE 灌入 50000 行合成数据（org_id 20 个取值、visit_time 均匀分布在 900 天），
`ANALYZE TABLE` 后对同一条查询做两次 EXPLAIN：一次在只有既有单列索引时，一次在补上复合索引后。
测完 `DROP TABLE`，业务表 records 与其它表未被写入。

查询：

```sql
SELECT id FROM records_explain_probe
 WHERE org_id='org-3' AND visit_time >= '2023-06-01' AND visit_time < '2023-07-01'
 ORDER BY visit_time DESC LIMIT 20;
```

## 结果

### 补索引前（原样输出）

```text
-> Limit: 20 row(s)  (cost=370 rows=20)
    -> Filter: (records_explain_probe.org_id = 'org-3')  (cost=370 rows=88.2)
        -> Index range scan on records_explain_probe using idx_records_visit_time over ('2023-06-01 00:00:00' <= visit_time < '2023-07-01 00:00:00') (reverse), with index condition: ((records_explain_probe.visit_time >= TIMESTAMP'2023-06-01 00:00:00') and (records_explain_probe.visit_time < TIMESTAMP'2023-07-01 00:00:00'))  (cost=370 rows=1680)
```

### 补索引后（原样输出）

```text
-> Limit: 20 row(s)  (cost=14.2 rows=20)
    -> Filter: ((records_explain_probe.org_id = 'org-3') and (records_explain_probe.visit_time >= TIMESTAMP'2023-06-01 00:00:00') and (records_explain_probe.visit_time < TIMESTAMP'2023-07-01 00:00:00'))  (cost=14.2 rows=56)
        -> Covering index range scan on records_explain_probe using idx_records_org_visit_time over (org_id = 'org-3' AND '2023-06-01 00:00:00' <= visit_time < '2023-07-01 00:00:00') (reverse)  (cost=14.2 rows=56)
```

## 结论

- 估计代价 370 → 14.2（约 26×）；预扫描行数 1680 → 56。
- 关键差别不只是「两维都进索引」，而是新索引是 **covering index**：查询只取 id（主键，在二级索引叶子内），
  于是彻底不回表；旧的 `idx_records_visit_time` 必须回表取 org_id 再过滤。
- `idx_records_org (org_id)` **保留不删**：复合索引的最左前缀虽已覆盖它，但 migration-03 的回滚脚本
  显式按该索引名做 DROP/ADD，删掉会让「03 → 06」往返验证对不上；单列索引的写放大代价在此规模可忽略。

## 迁移可用性验证（同一环境）

在一次性探针库上实跑 `data/migration-06-records-org-visit-time.sql` 与其回滚脚本：

| 动作 | 索引数（期望） | 实测 |
|---|---|---|
| apply 第 1 次 | 1 | 1 |
| apply 第 2 次（幂等） | 1 | 1 |
| rollback 第 1 次 | 0 | 0 |
| rollback 第 2 次（幂等） | 0 | 0 |
| 回滚后再 apply | 1 | 1 |

另在一次性探针库上整跑 `database-init.sql`（库名替换），records 索引为：

```text
idx_department_visit_time, idx_grade, idx_records_org, idx_records_org_visit_time,
idx_records_visit_time, idx_registration_no, idx_status, PRIMARY, uk_records_org_text_hash
```

即「全新装库」与「存量库迁移」两条路径的 records 终态一致。

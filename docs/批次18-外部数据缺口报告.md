# 批次 18 · 外部数据缺口报告（**不由代码解决，遇即停下报告**）

> 生成于 2026-10-06。计划文档对批次 18 的要求是「不由代码解决 · 遇即停下报告」——
> 本文就是那份报告。所有数字都是**实测**，命令与口径写在每节里，可复现。

## 一、缺口三项（实测）

### 18.1 症状标准词表偏小

| 项 | 值 | 来源 |
|---|---|---|
| 现有症状词条 | **72 条** | `SELECT COUNT(*) FROM dictionary_terms WHERE type='symptom'` |
| 未归一且属于「本该能归一」的症状 | 计划文档记载 **97 种 / 2736 次** | 报告接口的 `unmatched.dictionaryGap`（500 条真实数据） |

结论：不是程序缺陷。词表里没有「神疲乏力」「食少纳呆」「面色萎黄」这类标准词，
归一链路已经尽力（ES 召回 → 三级判定 → Dice 阈值），召回为空就是没有。

### 18.2 病因词典**根本不存在**

| 项 | 值 |
|---|---|
| `dictionary_terms` 里 type 的取值 | pattern / disease / symptom / herb / pulse / tongue / treatment / formula —— **没有 cause** |
| ES 索引 | `term_pattern` `term_disease` `term_symptom` `term_herb` `term_pulse` `term_tongue` `term_treatment` `term_formula` —— **没有 `term_cause`** |
| `causeList` 实体总数 | **300** |
| 其中已归一 | **0** |

⇒ 病因是「**这一类压根没有被当作可归一实体**」，不是「词表缺词」。
补词表也无效 —— 需要先有词表，再让 `EntityTypes` 的 cause 条目带上 `dict=true` 与文件名，
之后重建索引、重跑解析。这三步是**数据结构 + 数据**，不是算法。

### 18.3 国标编码（`code`）全空

| 项 | 值 |
|---|---|
| `dictionary_terms` 行数 | **3698** |
| 其中 `code` 非空 | **0** |
| 分类型 | pattern 2080 · disease 1364 · symptom 72 · herb 66 · pulse 43 · tongue 41 · treatment 27 · formula 5 —— 8 类**全部为 0** |

**一处需要更正的旧注释**：`database-init.sql:198` 写「（`code`）预留：国标代码（GB/T 15657 / 16751），
**当前无消费方**」—— 后半句**已经过时**：`EsTermIndexServiceImpl.toEntry` 会读 `code` 写进
`TermEntry`，`EsTermNormalizer.NormalizeResult` 也带 `code` 一路传到接口。
也就是说**读回链路是通的**，缺的只是数据本身（这正好也与计划文档「读回链路已就绪」一致）。

## 二、代码侧已经就绪的部分（所以交付时是「投数据」而不是「再开发」）

- `EntityTypes` 是实体类型的**单一来源**（key / 中文名 / structured_data 字段名 / 是否有词典 /
  词典文件名 / 原始列回退 / 展示顺序 / 是否计入未归一扣分）。
- 词典：`dictionary_terms` + `dictionary_versions`（内容哈希做版本）+ 导入接口 + 归档回滚。
- 归一：ES `term_{type}` 索引 + 三级判定（精确 / 包含 / Dice 模糊），未命中一律**不臆造**标准词。
- 编码读回：如上所述已通。
- 报告：`unmatched`（四类归责 + 词表缺口 TOP15）会直接告诉你**还缺哪些词、各缺多少次**。

## 三、需要提供什么（交付物清单）

| # | 需要的数据 | 形态 | 用在哪 |
|---|---|---|---|
| 1 | 症状标准术语集（含别名） | 词条 + 别名，可导出为现有导入格式 | 18.1 |
| 2 | 病因标准术语集（含别名） | 同上 | 18.2（**还需把 cause 在 EntityTypes 里改为 dict=true 并给 fileName**） |
| 3 | 国标编码映射表 | 标准词 → GB/T 编码，8 类各自一份 | 18.3（写进 `dictionary_terms.code`） |

## 四、交付后怎么跑（三步，都在现有能力内）

1. **导入**：用词典导入（有 dry-run 预览与归档回滚），按类型导入对应词表。
2. **重建索引**：`DictionaryController` 的 reindex（`term_{type}` 重建，含 mapping 兼容性校验）。
3. **重跑解析**：归一结果是在解析时写入 `structured_data` 的，**必须重跑解析**才会用上新词表 ——
   只补词表不重跑，报告里的未归一致字不会变（这一点曾有实际故障，见 `StructuredDataMeta` 的注释）。

## 五、我**没有**做的事（避免误解）

- 没有造任何假的标准术语集或编码表。18 的缺口是**数据**，造出来的假数据会让归一结果
  看起来正常但实际不可信，比缺数据更糟。
- 没有为了 18.1/18.2 去改归一算法（那会把「词表缺词」伪装成「算法问题」）。
- 18.2 里「让 cause 变 dict=true」这一步**没有做**：没有词表的情况下改它只会让归一链路
  多查一个不存在的索引（会抛 `TermIndexUnavailableException` → 503）。这一步应当与词表
  一起交付。

> **定位**：记录项目在性能与缓存设计上的技术决策、踩坑经验与可复用模式。

## 一、缓存架构思想

### 1.1 Cache-Aside 模式的正确姿势

**核心思想**：读时查缓存 → 未命中查库 → 回填缓存；写时先改库 → 后失效缓存。

**踩过的坑**：
- ❌ **错误**：事务内失效缓存 → 并发读在事务提交前 miss，按旧数据现算回填 → 提交后缓存持旧值最长 60s
- ✅ **正确**：`DistLock.afterCommit()` 在事务提交后才失效

**为什么这是个坑**：Cache-Aside 的铁律是"失效必须在事务提交后"，但很多人会忽略这一点。项目里清洗、删除病历两个地方都犯了这个错，导致统计数据脏读。

**可复用模式**：
```java
@Transactional
public void deleteRecords(...) {
    recordMapper.deleteByIds(...);
    DistLock.afterCommit(StatsCacheInvalidator::invalidateStats);  // 提交后失效
}
```

### 1.2 版本号前缀失效 vs KEYS 命令

**错误做法**：用 `redis.keys("prefix:*")` 通配删除 → O(N) 全库扫描，Redis 单线程阻塞，期间所有请求排队。

**正确做法**：版本号前缀失效
- Key 格式：`cache:stats:{scope}:v{n}:{md5(filters)}`
- 失效：`INCR` 版本号 → 旧 key 自然过期，不主动删除
- 优点：O(1) 失效，不阻塞 Redis，不需要 `KEYS` / `SCAN`

**思想**：不要"删缓存"，而是"让旧缓存自然过期"。版本号是时间戳的廉价替代品——不需要遍历所有 key，只要版本号变了，旧 key 就永远不会被读到。

### 1.3 并发三防

| 问题 | 解决方案 | 思想 |
|------|----------|------|
| 穿透（查不存在的数据） | 空值哨兵缓存 10s | 防止恶意请求打穿到 DB |
| 击穿（热点 key 过期瞬间） | 单飞锁 `SETNX` | 过期瞬间只一个请求回源，其他等待 |
| 雪崩（大量 key 同时过期） | TTL 随机抖动 ±10% | 错开过期时间，避免集中回源 |

**设计哲学**：缓存不是"加了就行"，要考虑异常流量下的行为。Redis 挂了怎么办？→ 自动降级直连 DB，绝不抛 500。

## 二、SQL 与查询优化

### 2.1 列投影：不要拉回不需要的列

**踩坑**：标准化报告 `selectList` 拉回 records 全部 21 列 → 4 万条 45MB 常驻堆。
**优化**：按实际消费投影 8 列 → 降到 12MB。

**思想**：ORM 的 `selectList` 是方便，但生产环境要清楚自己到底需要哪几列。TEXT 列比 INT 列贵一个数量级，不需要的列坚决不拉。

**对照范式**：项目里 `RecordServiceImpl.searchRecords` 和 `StatsServiceImpl.recordsFor` 都已经做了列投影，是正确的参照。

### 2.2 keyset 分页 vs offset 分页

**offset 分页的问题**：`LIMIT 39800, 200` 需要扫描前 39800 行，累计扫描量是实际行数的 20 倍。

**keyset 分页**：用 `(visit_time DESC, id ASC)` 锚点，下次从 `WHERE visit_time < ? OR (visit_time = ? AND id > ?)` 开始扫。

**效果**：扣分统计接口从 4.9s 降到 216ms，22 倍提升。

**思想**：深分页不要用 offset，用 keyset。这是数据库优化的经典题，但很多人不知道。

### 2.3 N+1 查询的识别

**案例**：清洗链路逐条调词典元数据 → 4 万条 16 万次 SQL。
**根因**：循环内每条记录都查一次基础层 + 本组织词典版本。
**解决**：`DictMeta` 记忆化，循环外取一次，循环内复用。

**思想**：N+1 不是 ORM 才有的问题——手写 SQL 循环里逐条查也是 N+1。识别信号："循环体内有 DB 调用"。

## 三、并发与队列设计

### 3.1 有界队列 + 拒绝策略

**踩坑**：`newFixedThreadPool(4)` 内部 `LinkedBlockingQueue` 无界 → LLM 卡住时并发提交 100 个任务，96 个堆在队列里跑，前端早放弃了后端还在跑。

**优化**：显式 `ThreadPoolExecutor` + 有界队列（容量 100）+ 拒绝策略（拒绝时回 503「AI 繁忙」）。

**思想**：线程池不要用 `Executors.newFixedThreadPool`，要显式构造——队列容量、拒绝策略都要自己定。无界队列是生产事故的温床。

### 3.2 多实例下的状态共享

**踩坑**：AI 异步任务状态存在进程内 `ConcurrentHashMap` → A 实例提交、B 实例轮询 → 404。

**优化**：任务状态迁 Redis Hash，TTL 600s，进程内表作一级缓存。

**思想**：只要是多实例部署，任何"进程内状态"都是定时炸弹。登录态、任务状态、计数器——只要需要跨实例可见，就必须放共享存储。

## 四、工程优化思想

### 4.1 一次解析，多处复用

**踩坑**：标准化报告同一条 JSON 解析 7 次（7 个统计器各自解析）→ 4 万条 ≈ 28 万次 Jackson 反序列化。

**优化**：入口一次遍历、一次解析，抽扁平中间结构向下传。

**思想**：不要让每个统计器各自解析同一份数据。入口处一次解析好，传下去——这是"数据管道"思想，不是"每个消费者自己拿数据"。

### 4.2 降级设计

**原则**：Redis 不可用 → 降级直连 DB，绝不抛 500。

**实现**：读 / 写 / 锁全部 `try-catch` 吞异常，走 `loader.get()` 现算。

**思想**：缓存是"加速器"不是"必需品"。加速器挂了，系统应该慢，但不应该挂。

## 五、设计决策与取舍

| 决策 | 选择 | 理由 |
|------|------|------|
| 缓存框架 | 自研 StatsCache，不用 Spring Cache | 需要版本号失效、单飞、fail-open 等语义，`@Cacheable` 不支持 |
| 进程内缓存 | VersionedCache 自研，不用 Caffeine | 需要"版本号前缀失效"语义，Caffeine 没有 |
| 限流实现 | 自研 ZSET 滑动窗口，待换 Redisson | 简单场景下自研够用，但要意识到这是技术债 |
| 异步任务 | Redis 共享状态，不用消息队列 | 单实例部署，Redis 足够；MQ 是过度设计 |

**核心取舍**：这个项目是单实例为主的内部系统，所以很多设计是"够用就好"，不追求分布式完美。但要清楚哪些是"刻意简化"，哪些是"技术债"。

## 六、索引与覆盖索引实战

### 6.1 先量后改：EXPLAIN 实测校正静态审查

**踩坑**：4 个并行审查 agent 静态推断"多个谓词缺索引"，上真实库 `EXPLAIN` 后发现多数被 MySQL 8 的 index skip scan、LIMIT 早停、覆盖索引缓解，据实降级。

**教训**：不要凭静态代码推断加索引。每条待改 SQL 先 `EXPLAIN ANALYZE` 存档作改后对比；索引治理用 `information_schema.STATISTICS` 在真实库核对，不要信 `database-init.sql` 的注释。

### 6.2 覆盖索引消除回表：行宽才是聚合慢的真根因

**案例**：看板趋势 / 科室两条 `GROUP BY` 聚合各 ~2.3s。初判"临时表"，`EXPLAIN ANALYZE` 后根因是 records 行极宽（`avg_row_length≈12KB`，`structured_data`/`qc_results` 两个 TEXT，整表 ≈290MB），聚合只需 3 列却被迫读整行回表。

**修复**：一条覆盖索引 `idx_records_org_agg(org_id, visit_time, department, grade)` 同列覆盖两条聚合 → Covering index scan（趋势 2306→50ms、科室 2287→16ms），无需 STORED 生成列、无需 admin 变体。配套删冗余索引抵消写放大。

**思想**：聚合慢先量"回表读了多少行宽"，再加覆盖索引把 `COUNT/GROUP BY` 钉在索引里，别先怀疑临时表。

### 6.3 schema 注释会误导索引治理

**踩坑**：`status` 谓词无索引全表扫，根因是 `database-init.sql` 注释谎称"被 org 前缀复合索引覆盖"——实际没有任何索引含 `status`，注释错误 + 误删索引。

**修复**：补 `idx_records_org_status_vt` / `idx_records_status_vt` 两个变体（V7）。

**教训**：索引有没有，以真实库 `information_schema` 为准，注释会骗人；改索引时注释要一起改。

### 6.4 字典 N+1 的批量收口

**踩坑**：报告页首屏 36 次 SQL，其中 32 次是词典往返（8 类 × `readEffective` 2+2）。

**修复**：`IDictionaryTermStore.readEffectiveAll(orgId)` 用一条 `org_id IN ('',?)` 取回全部类型、内存逐位合并 → 报告页 32→1、看板 10→1。

**思想**：N+1 的收口不是"加缓存"，是"把逐类查询合并成一次批量查询"，内存合并保持口径逐位一致。

## 七、缓存模式进阶

### 7.1 版本号粒度：全局 kind 版本 vs 按组织失效

**原方案**：失效时同时 bump「请求者 scope」与「被改数据所属 org」，要求改 ~10 个写路径在分批遍历时顺手收集 orgId。

**拍板放弃**：任一处写路径漏收集就 ≤TTL 脏读，10 个点太脆弱。

**最终选择**：任一写入 bump 一个**全局 kind 版本号**（与 org 无关），现有 10 处 `invalidateStats()` 调用点一行未改，自动获得"任一写入即失效全部 kind"。

**代价**：任一组写入作废其它组缓存。本项目单组织、写入低频，可接受。

**思想**：失效粒度的正确性 vs 改造成本要算账。按 org 失效"理论最优"但要动 10 个写路径、易漏；全局版本"粗但稳"，单实例/低频场景下粗是优点不是缺点。

### 7.2 SWR：冷算挡在用户前面时，让它后台重算

**问题**：报告 180s TTL 只给了一段不重算窗口，窗口一过用户仍要等 ~4.3s 冷算。实测那 3s 是磁盘 I/O（表体 290MB > buffer pool 128MB），SQL 侧列投影/去 ORDER BY 后已无空间。

**机制（`getOrLoadSwr` 双 key）**：
- `dataKey`（值，TTL=基准×10=30min）+ `dataKey:fresh`（标记，TTL=基准 180s）
- 读：data 在 + fresh 在 → 命中；data 在 + fresh 没了（时间到期）→ **立即秒回旧值** + 后台单飞重算；data 没了 → 阻塞现算
- 后台池：1~2 线程、有界队列 16、`DiscardPolicy`（满则丢弃，下次读再触发）
- 正确性：写入 bump 全局版本 → key 段变 → 两把 key 皆空 → 仍阻塞现算新值（只有时间到期才走秒回）

**效果**：冷算 4358ms，再读 14ms；fresh 过期后秒回 15ms（vs 冷算 4358ms），后台 ~2.8s 重算完成。

**思想**：对"计算重、磁盘 I/O 主导、SQL 侧无优化空间"的接口，不要追求更快，要用 SWR 让它别挡在用户前面。

### 7.3 后台重算线程脱离请求上下文：ReportContext 快照

**踩坑（真实风险）**：报告现算体读 `RequestUtils.currentOrgId()` ×3、`RecordFilter.domainOrgId()`/`viewAllOrgs()`；SWR 后台重算线程里这些一律退化成 `"unknown"` + fail-closed，会**回填错误甚至空的报告**。

**修复**：在请求线程捕获 `ReportContext(orgId, domainOrgId, viewAllOrgs)` 快照显式传入，现算体与线程无关（与批任务 `qc_task.role` 快照同一做法）。

**教训**：任何把计算丢到后台线程池的缓存模式（SWR、异步预热），都必须先盘点它读了哪些 ThreadLocal/请求上下文，在请求线程快照传下去。

### 7.4 不是所有统计都能缓存（语义漂移清单）

| 场景 | 为什么不能缓存 |
|---|---|
| `overview` 待复核数 | 含"待办"语义，缓存反而让待办数变旧；已毫秒级覆盖索引，收益小 |
| `review/tasks/count` 超期数 | 随墙钟变（`deadline_time < now`），无数据变更也变 → 缓存语义漂移 |
| report 类 Key | 换词表数字会变但不是数据变更 → Key 必须 salt=dictVersion |

**思想**：缓存的前提是"数据不变缓存就不变"。凡是随墙钟、待办状态、词典版本（非业务数据变更）漂移的统计，要么不缓存，要么 Key 把漂移维度一起编进去。

## 八、NLP 推理服务性能（CPU）

### 8.1 CPU 推理不要攒批

**设想**：攒批一次前向，吞吐从 ~10 条/s 提到 50+。

**实测否定**：32 核 CPU、torch 线程 4、信号量 8 下，攒批 batch=8/16/32 吞吐反降到基线的 **0.36~0.60x**。根因：① CPU 前向已吃满 4 线程，攒批把并发从 8 压到 1~2；② batch 与单条走不同 BLAS 路径，浮点 ~1e-7 差异，argmax 在边界抖动，**实体边界会变**。

**附带结论**：torch{2,4,8,16}×信号量{4,8,12,16} 全扫描，其余组合 ≤0.98x，现行 torch=4/并发=8 已是最优，无需调参。Tokenizer 缓存收益上限 0.6% 且真实命中率≈0（病历文本互不相同），不要做。

**教训**：攒批是 GPU 的优化手段。CPU 上并发已吃满算力时，攒批只会压低并发度；且 batch 化会改变数值路径，NER 这类边界敏感任务不能容忍 ~1e-7 抖动。

### 8.2 规则兜底加词的判据

**踩坑**：按文档提议给病因/治法加词，实测回归——`RULE_PULSE_POSITION` 加脉质白名单后脉象 144→120 条次（-16.7%）；`边有瘀斑` 一类被 `边有齿痕` 收窄规则整段丢掉。

**判据（已写进代码）**：加词前先 grep `dictionaries/`，**若该词已是某条目的 `standardTerm` 或 `aliases`，就说明它属于那个类，不要往本类加**——否则跨类重复计数。病因 6 词里 `肝郁`/`食积` 在证候/病名词典精确命中，该由那两路归一收走。

**教训**：规则兜底加词不是"越多越好"。词典里找不到落点就不要加；收窄型正则会隐蔽回归（演示数据恰好只覆盖正例，负例损失看不见），加完要跑全量逐行对比。

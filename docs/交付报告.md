## 八、归一化与治理页重构（第三轮）

通读全部设计文档（需求分析/功能设计/项目设计/openapi）后，按文档定义修正：

### 8.1 归一算法重构（修复"咽喉痛→腰部冷痛"误命中bug）
- **根因**：ES BM25对短中文词仅共享单字（"痛"）即超阈值误命中；且ES的minimum_should_match百分比在小token数下取整后失效
- **修正**：按项目设计文档9.4算法实现——①精确（标准词/别名全等）→②**双向包含**（输入包含别名 或 别名包含输入）→③**字符Dice相似度≥0.8**（"咽喉痛"vs"腰部冷痛"=0.29拒绝；vs"咽痛"=0.8命中；"膝关节疼"→"膝关节疼痛"=0.89命中）
- 实测：无关词正确返回原词+空source；双向包含"腰冷痛"→"腰部冷痛"生效

### 8.2 清洗算法对齐文档5步流水线（9.5节）
`执行数据清洗` = ①去重（**原始文本哈希**，替换原挂号号方案）→ ②字段修补（trim/空值）→ ③格式规整 → ④脏数据隔离 → ⑤**术语自动归一**（遍历合格病历structuredData全实体，content替换为国标标准词、sourceText保留原文溯源，`normalized`计数）——归一完成后`governed`标记置1

### 8.3 治理页UI对齐原型（项目设计文档第8节5）
- 移除错位的"术语标准化"手动查词面板（normalize接口保留供NLP链路/复核修正内部调用）
- 新增顶部状态行：质控合格/待治理/已治理（GET /api/governance/stats，records表新增`governed`列）

#### 12.7.2 顺带修复：双写时间戳差 1 秒

**现象**：同一操作在库中为 `14:35:08`、在文件中为 `14:35:07`，恒定差 1 秒。
**根因**：`LocalDateTime.now()` 带小数秒；`DATETIME`（0 位小数）对 `.5` 以上小数秒**四舍五入**，而文件格式化 `yyyy-MM-dd HH:mm:ss` 是**截断**。同一 `now` 因此呈现两个值。
**修复**：`OperationLogger.log()` 取 `LocalDateTime.now().withNano(0)`，两侧同源截断。修复后实测库/文件时间逐秒一致（见 12.7.1）。

### 12.11 ES 检索接入（归一算法真正走 ES）（2026-09-19）

#### 12.11.1 起因与裁决

§12.10.7 查明「ES 只写不读」——ES 索引建了却从不检索，归一实际由纯内存 `DictionaryStore` 完成。本轮用户裁决两项：

1. **ES 客户端**：本轮只接检索，Jackson 2/3 并存问题暂不动（保留 `RestHighLevelClient`）。
2. **归一判定**：**ES 召回 + Java 规则判定**，判定逻辑不下推 ES。

#### 12.11.2 为什么不把判定下推 ES

`Dice` 是**字符集合相似度**，ES 的 `fuzzy` 是**编辑距离（Levenshtein）**，两者在边界上不等价。下推会直接改变既有阈值语义——文档中「咽喉痛 vs 咽痛 = 0.8 命中、vs 腰部冷痛 ≈ 0.33 拒绝」这类判据是靠 Dice 算出来的，换成 ES fuzzy 后需要全部重新标定与验收。因此保留 Java 判定、ES 只做召回。

#### 12.11.3 改动

| 文件 | 改动 |
| --- | --- |
| `service/IEsTermIndexService.java` | 新增 `List<TermEntry> search(String type, String input, int maxCandidates)`；接口注释明确「检索与索引同处一个服务是为了让字段名/映射只有一处权威」 |
| `service/impl/EsTermIndexServiceImpl.java` | ① 新增 `search` 实现；② **mapping 变更**：`aliases` 由「空格拼接的 text」改为**数组** + `keyword` 子字段；③ 文档 JSON 改由 Jackson 生成（删掉手写 `escape`）；④ 新增 `toEntry` 反序列化（兼容旧格式单串别名） |
| `common/utils/EsTermNormalizer.java` | 三级判定逻辑**逐字保持**，改为「ES 召回 → 判定 → 未命中则内存全量兜底」 |
| `test/.../EsTermNormalizerTest.java` | 新增 9 例，锁「行为等价」契约 |

**mapping 为什么必须改**：`aliases` 原先是 `String.join(" ", aliases)` 拼成的单个字符串，其 `keyword` 子字段只能匹配**整串**，无法精确命中单个别名。改成数组后 ES 会为每个别名各建一个 `aliases.keyword` term，别名精确匹配才成立。

**召回查询**（`recallQuery`）——只求不漏、不求准，`minimum_should_match=1`：

```
bool.should:
  term  standard_term          = input     ← 标准词精确
  term  aliases.keyword        = input     ← 别名精确
  match standard_term.text     = input, fuzziness=AUTO  ← IK 分词近似
  match aliases                = input, fuzziness=AUTO  ← IK 分词近似
```

#### 12.11.4 行为等价性论证

改造后 `normalize` 的路径是：**ES 召回候选 → 三级判定 → 未命中则内存全量再判一次**。等价性依据两条：

1. **精确命中必然被召回**：`term` query 直接命中 keyword，不存在漏召回。故「精确 vs 模糊」的优先级不会因 ES 候选集而倒挂。
2. **未命中路径有内存全量兜底**：ES 召回是近似检索，存在理论漏召；因此候选未命中时会再跑一次内存全量判定。这使最终结果**收敛到与改造前完全一致**，ES 从「判定参与方」退回「加速通道」。

代价：命中路径 `O(候选数)`，未命中路径 `O(N) + O(候选数)`。词典规模小时差异可忽略；规模到 3 万条时命中路径才显现优势。

#### 12.11.6 Jackson 2/3 并存的结论（本轮未动，留档）

**明确结论：只要还在用 ES 官方客户端，Jackson 2 就必然在类路径上，无法移除。** 依据：`org.elasticsearch:elasticsearch-x-content:7.17.22` 的 pom 中 `com.fasterxml.jackson.core:jackson-core` 是**非 optional 的 compile 依赖**（另带 `jackson-dataformat-{smile,yaml,cbor}`）。经 `dependency:tree` 复核，Jackson 2 共两个来源：

1. `org.elasticsearch:elasticsearch:7.17.22` → `elasticsearch-x-content` → `jackson-core:2.21.5`
2. `io.jsonwebtoken:jjwt-jackson:0.11.5` → `jackson-databind:2.21.5` + `jackson-annotations:2.21`

要「只用一个（Jackson 3）」，可行路径是：**舍弃 ES 官方客户端，改用 `java.net.http.HttpClient` 手写 ES REST 调用**（`_bulk` / `_search` / 索引管理均为纯 JSON HTTP，约 150 行），这样来源 1 消失，顺带清掉「`RestHighLevelClient` 自 ES 7.15 起废弃、8.0 已移除」的技术债；来源 2 则由给 jjwt 写一对 Jackson 3 的 `Serializer`/`Deserializer` 适配器解决（`jjwt-api` 的 `io.jsonwebtoken.io.Serializer<T>` 仅要求 `byte[] serialize(T)`，`Deserializer<T>` 仅要求 `T deserialize(byte[])`，实现简单）。

两条路都改动较大且触及核心链路，**本轮按用户裁决均未执行**。

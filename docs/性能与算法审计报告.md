## 二、科研级算法方案

### S1 · 术语建议召回：全量线性扫描词典

**1. 问题位置**
- `AiServiceImpl.java:737-746`（`recallCandidates`）、`:748-757`（`overlap`）、`:758-772`（`commonChars`）；调用点 `:706`

**2. 原始逻辑 + 复杂度**

```
// :706 对每个待补词，全量扫描一遍该类型全部词条
// :740 逐条 overlap(content, e) >= RECALL_MIN_OVERLAP
// :744 排序比较器内再算 2 次 overlap
// commonChars 用 StringBuilder.indexOf + deleteCharAt，各 O(L)
```

- **复杂度**：O(T × D × A × L²)。T=待补词数，D=该类型词条数，A=平均别名数，L=词长。
- **注意**：排序重算 overlap 是既有报告 AI-7/A3 已登记的根因（相似度未预计算），此处不重复计入。

**3. 性能现象（4 万病历场景）**

质量报告产出「未命中词典的症状」清单即 `suggestTerms` 的输入。当前规模（证候 2080、症状 110 等）：单条待补词约 2000~3000 次 `commonChars`；T=500 时达百万级 → 秒级。导入国标全量后（D≈3 万）：单条约 4.5 万次 → T=500 时 2250 万次 → 十秒到分钟级。

**4. 优化方案（科研级）**

- **算法**：**倒排索引 + 字符 n-gram**。预建「字符 → 词条 ID」倒排表；因 `RECALL_MIN_OVERLAP=2`，「与 w 共享 ≥ 2 个不同字符」是入选的**充要条件** → 可在完全不改变结果集的情况下把扫描量从 D 降到候选数。
- **学术参考**：Manning, Raghavan & Schütze, *Introduction to Information Retrieval*, 2008（第 1–2 章）；CJK 场景 n-gram 索引是中文 IR 标准做法；若换 BM25 排序见 Robertson & Zaragoza, *The Probabilistic Relevance Framework*, 2009。
- **复杂度收益**：O(T×D×L²) → O(T × (Σpostings + C×L²))；D 从 2080→3 万时收益从约 30× 增到约 400×。
- **精度说明**：过滤阶段**零精度损失**（充要条件保证结果集相同）；若把 `overlap` 换成 BM25 排序则排序会变（精度风险项）→ 建议分两步，先只换过滤。
- **落地风险**：倒排表须随词典变更重建。`DictionaryTermStoreImpl` 已有 `VersionedCache`（按 `org|type|version`，`:56`）+ 写路径主动失效，可挂在同一版本号，不需新增失效通道。

**5. 优先级**：**P1**。**6. 落地评估**：开发中；不影响业务准确性；医疗风险低（候选集合不变，人工确认流程不变）。

### S2 · 词典页搜索：线性扫描 + 内存分页

**1. 问题位置**：`DictionaryServiceImpl.java:100`（循环 `contains`）、`:68`（`subList` 内存分页）

**2. 原始逻辑 + 复杂度**：先全量筛出 hit 再 `subList`；分页不减少筛选量——每次翻页都全筛一遍。O(D × A × L)。

**3. 性能现象**：当前 D=8169 → 每次翻页仍数 ms，可接受；国标全量 D≈3 万 → 数十到上百 ms，且与页码无关地恒定。

**4. 优化方案（科研级）**
- **算法**：倒排索引（与 S1 共用一份表）；若目标是「长文本中找词典命中的所有词」，则用 **Aho-Corasick**。本处模式是单个查询词，AC 收益有限——真正合适的是倒排/前缀树。
- **学术参考**：Aho & Corasick, *Efficient String Matching: An Aid to Bibliographic Search*, CACM 18(6), 1975。
- **复杂度收益**：O(D×A×L) → O(L + 命中数)；倒排与 AC 均为精确匹配 → **零精度损失**。
- **落地风险**：同 S1，需维护索引一致性。

**5. 优先级**：**P2**（当前不痛；国标全量后升 P1）。**6. 落地评估**：开发中（可与 S1 共表）；不影响准确性；医疗风险低。

### S3 · 术语归一的模糊判定：Dice 逐对计算 + 每次重建字符集

**1. 问题位置**：`EsTermNormalizer.java:243-268`（三级判定模糊级）、`:277-285`（`dice`）

**2. 原始逻辑 + 复杂度**：对每个候选（≤50）与每个别名调 `dice`；`dice` 每次 `new HashSet<>()` 两个（`:282`/`:284`）。O(C×A×L)，C 有界；`input` 侧字符集被重复重建 C×A 次，纯浪费。

**3. 性能现象（4 万病历）**：单实体约 75 次 `dice`、150 个临时 Set；4 万病历 × 每病历约 30 实体 ≈ 120 万实体 → **约 1.8 亿次 Set 分配**，「单点不痛、批量痛」。与 AI-22 同源（AI-22 只讲实现层，未给算法替代）。

**4. 优化方案（科研级）**
- **算法 A（推荐，零精度损失）**：**字符集位图（bitset）**。字符集用 `long[]`/`BitSet`，则 `Dice = 2×popcount(a&b) / (popcount(a)+popcount(b))`，`Long.bitCount` 单指令。`input` 位图建一次；候选位图随词条预计算并挂在词典版本上。
- **算法 B（更通用，有精度风险）**：**SymSpell** 或 **BK-tree**（编辑距离半径检索）。
- **学术参考**：集合相似度位图是标准做法（Broder, *On the Resemblance and Containment of Documents*, 1997）；SymSpell 见 Garbe (2012)；BK-tree 见 Burkhard & Keller, CACM 16(4), 1973。
- **复杂度收益**：单次 Dice 从「O(L) 建集 + O(L) 求交」降到 **O(1)**（预计算后），临时对象归零。
- **精度说明**：位图结果与现实现逐位相同（Dice 定义不变）→ **零精度损失，可直接替换**。SymSpell/BK-tree 会改变命中集合（编辑距离 ≠ 字符 Dice，项目注释已指出「咽喉痛」vs「咽痛」=0.8 命中 vs「腰部冷痛」=0.29 拒绝）→ 精度风险，必须先用 `tools/eval-dictionary-impact.py` 做前后对比。
- **落地风险**：位图方案的候选位图随词典版本失效即可，`VersionedCache` 有版本机制，风险低。

**5. 优先级**：**P1**（位图）/ **P3**（SymSpell，需评测）。

**6. 落地评估**

| 方案 | 开发成本 | 影响准确性 | 医疗风险 |
| --- | --- | --- | --- |
| 位图 Dice | 小 | **否** | 低 |
| SymSpell / BK-tree | 中 | **是**（需评测） | 中——会改变「哪些词算归一成功」，直接影响质控扣分 |

### S4 · 残词回补的真子串判定：嵌套遍历

**1. 问题位置**：`EntityNormalizer.java:536-546`（`isProperSubstringOfAny`）；调用点 `:294`（`removeIf`）

**2. 原始逻辑 + 复杂度**：对每个待判定实体遍历全部命中词做 `contains(s)`。O(E×H×L)。

**3. 性能现象**：单病历数十实体/命中 → 千次短串比较不痛；批量放大后绝对量百万级短串比较，约百 ms。

**4. 优化方案（科研级）**
- **算法**：**Trie / 后缀自动机**。「s ⊂ hit」与 AC 的「pattern ⊂ text」方向相反；把 hits 建 Trie 反向检查，或用后缀自动机 O(|s|) 判定。
- **学术参考**：Blumer et al., *The Smallest Automaton Recognizing the Subwords of a Text*, TCS 40, 1985。
- **复杂度收益**：O(E×H×L) → O(E×|s|)；子串判定是精确谓词 → **零精度损失**。
- **落地风险**：hits 每次调用不同，结构须按调用现建；建结构成本 O(H×L) 与省下的 O(H) 同量级——**仅当 |hits| 明显大时才划算**。

**5. 优先级**：**P3**。**6. 落地评估**：中成本；零准确性影响；**建议列为「有阈值触发的储备方案」**（单段命中词数 > ~200 时启用）。

### S5 · 质控规则匹配：朴素 contains

**1. 问题位置**：`LogicChecker.java:47-60`（`anyContains`）、`:40-56`（双向遍历）、`:66-86`（`listOf` 重建 List）

**2. 原始逻辑 + 复杂度**：O(r × (E_t×V_t + E_e×V_e) × L)。

**3. 性能现象**：规则集仅 14 条 → 每病历几百次短串 contains，4 万条重算约千万次 → 百 ms 级，非瓶颈。

**4. 优化方案（科研级）**
- **算法 A**：**Aho-Corasick**（触发/期望值建自动机，一次扫描）。**算法 B**：**Rete**（规则扩成大规模知识库时）。
- **学术参考**：Forgy, *Rete: A Fast Algorithm for the Many Pattern/Many Object Pattern Match Problem*, AI 19(1), 1982。
- **复杂度收益**：AC 把 O(r×V×L) 降到 O(总文本长 + 命中数)；Rete 在「规则数 ≫ 对象数」时避免重复匹配。
- **精度说明**：AC 与 contains 结果一致 → 零损失；Rete 需形式化规则语义，偏差会改质控判定 → 风险高。
- **落地风险**：当前 AC/Rete 均属过度设计。触发条件：一致性规则 > ~100 条 或 规则值集合 > ~1000 个。

**5. 优先级**：**P3（当前不建议做）**。**6. 落地评估**：AC 中 / Rete 高成本；Rete 与「质控必须可解释、可复现」约定冲突 → **不建议**。

### S6 · 指标统计：多次全表遍历

**1. 问题位置**：`StatsServiceImpl.java:195`、`:221`、`:240`（`byMonth`/`byDept`/`dist` 三趟遍历）；对照已优化 `:191`（`recordsFor` 列投影）

**2. 原始逻辑 + 复杂度**：O(3n)，同一集合独立遍历三遍。

**3. 性能现象**：4 万行 → 约 12 万次迭代，几十 ms；不是瓶颈但纯浪费，且列表被三趟期间持有。

**4. 优化方案**
- **工程级（首选）**：三趟合并为一趟，O(3n) → O(n)。
- **科研级（条件性）**：**增量统计 / 前缀和**——维护「按月累计」增量表，查询 O(月份数)；区间用前缀和 O(1)。
- **学术参考**：前缀和/差分是区间查询标准技术；增量视图维护见 Gupta & Mumick, *Maintenance of Materialized Views*, IEEE Data Eng. Bull. 18(2), 1995。
- **精度说明**：零精度损失（确定性聚合）；风险在并发一致性——增量表必须与病历表同事务更新。
- **落地风险**：引入物化状态与「口径单一来源」约定有张力；`StatsCache` 与失效机制可复用。

**5. 优先级**：**P2（先做单趟合并；增量统计列储备）**。

**6. 落地评估**

| 方案 | 开发成本 | 影响准确性 | 医疗风险 |
| --- | --- | --- | --- |
| 单趟合并 | 小 | 否 | 无 |
| 增量统计 | 中 | 否（需事务口径） | 中——计数漂移直接错报质控指标 |

## 三、工程级代码优化（T1–T20）

### T1 · 导出 CSV：循环内对整实体做 bean→Map 转换【P0】

**位置**：`GovernanceServiceImpl.java:630-641`（`:631` 循环体 `objectMapper.convertValue(r, Map.class)`）

**原始逻辑**：`convertValue` 在 `for (String col)`（`:630`）循环体内，每行做列数次整实体反射转换，常数极大。

**性能现象**：4 万行导出 → 数十万次整实体反射转换 + 等量临时 Map，比「每行转一次」慢 20 倍以上。

**优化方案**：`convertValue` 提到循环外每行一次；更彻底用 `RecordUtil.column(r, col)`（`QcScorer.rawValue:70` 就在用）绕开反射。

## 四、先工程后科研：必要性判定

| 科研项             | 低成本工程替代是否够用                                             | 结论                              |
| --------------- | ------------------------------------------------------- | ------------------------------- |
| **S1** 术语建议全量扫描 | ❌ 不够。预计算 overlap 只能省排序（既有 A3），扫描本身 O(T×D) 无法靠实现消除       | **需要科研级**（倒排索引），过滤等价、零精度损失      |
| **S2** 词典页线性扫描  | ⚠️ 部分。可用 `String.indexOf` 微优化，但 O(D) 本质不变               | **规模到 1 万条以上才需要**；当前 P2         |
| **S3** 模糊 Dice  | ⚠️ 部分。既有 AI-22 的「复用 HashSet」只省一半，input 侧重复建集与 O(L) 求交仍在 | **位图方案值得做**（零精度损失）；SymSpell 需评测 |

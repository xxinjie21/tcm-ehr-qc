一、总体评价

根因方向：后端 SQL 层，不是前端。

病历列表的排序键是 ORDER BY visit_time DESC, id ASC（RecordFilter.java:315），而 records 表上没有任何索引能匹配这个排序键——因此每一次列表查询都必须把该机构的全部 4 万行读出来做 filesort（EXPLAIN ANALYZE 实测：Sort: records.visit_time DESC, records.id + Index lookup ... rows=40000）。在这条主因之上，还有两处放大器：

  1. 后台批处理用偏移分页循环：QcServiceImpl.deductionStats 与 QcBatchServiceImpl.run 都是 while(true) { selectPage(new Page<>(pageNo, 1000), wrapper) }，4 万条 = 41 页，每页都重排一次全表，实测扫完 4 万行需 4.9 秒（缓存态）/ 26.9 秒（未缓存）。
  2. 统计接口把全表载入 JVM 堆并重复解析 JSON：StatsServiceImpl.recordsFor() 用 selectList 一次性拉 4 万行（≈320MB）进堆，/api/stats/all 对同一份列表连续调 4 次 statsFor → agg → objectMapper.readValue(structured_data)，每条记录解析 5 次 3.7KB JSON（合计 20 万次）。病历列表首屏并发的 5 个接口里，/api/stats/overview 与 /api/governance/stats 各需 0.57 秒（需 grade/governed 列，走不了覆盖索引）。

前端侧基本健康，但也没有为大数据量做任何准备：全仓库没有任何 >200 的 pageSize 调用，病历列表实际上限是 50（PAGE_SIZES_STANDARD = [10,20,50]），el-table 每次只渲染当前页。前端从未一次性接收 4 万条，也从未全量渲染 4 万 DOM 节点——「前端全量渲染导致卡顿」这一假设在本代码库不成立（详见附录 C）。但浏览器真机实测表明：el-table 的渲染成本是 ≈3ms/行、26.1 个 DOM 节点/行，50 行 170ms、1000 行 2.97s、4 万行外推 108 秒（20000 行已把浏览器拖到 90 秒超时）。所以「业务要能检索 4 万条」这条约束，在前端这一侧必须靠虚拟滚动兑现，而不是靠限制条数。前端另有两个真实问题：「无请求取消/防抖」导致并发重查询把后端放大，以及深分页无防护。

综合评分：⭐ 2 / 5

⭐⭐⭐⭐ 轻微优化即可
⭐⭐⭐ 有优化空间但可用

判分依据：功能正确、代码规范、索引与分页注释都写得很清楚（甚至已经预见到「3.5 万条量级需留意 deleteByFilter 与 clean」），但索引未与排序键对齐、批处理仍用偏移循环，导致 4 万条时列表页单次交互 0.2~1.0 秒、质控扣分统计 13~27 秒、统计看板约 10 秒。补齐索引 + 批处理改游标后，列表首页可降到 1.8ms（实测 98 倍提升），可回到 4~5 星。

P0-1 排序键 visit_time DESC, id ASC 无匹配索引，每次列表查询读全表 4 万行 + filesort

【优化方案】

方案 A（推荐，MySQL 8.0+，零代码改动）

-- 与排序键逐字对齐的降序复合索引
ALTER TABLE records
  ADD INDEX idx_records_org_vt_id (org_id, visit_time DESC, id ASC);

实测 EXPLAIN ANALYZE：Index lookup on records using idx_records_org_vt_id —— 无 Sort，首页 1.8ms。

方案 B（兼容 MySQL 5.7，需改一处代码） MySQL 5.7 不支持降序索引。把次级排序键方向反转（RecordFilter.java:315）：

// 原：wrapper.orderByDesc("visit_time").orderByAsc("id");
wrapper.orderByDesc("visit_time").orderByDesc("id");

配套索引（全升序）：

ALTER TABLE records ADD INDEX idx_records_org_vt_id (org_id, visit_time, id);

实测 EXPLAIN ANALYZE：Index lookup on records using idx_asc3 (reverse) —— 无 Sort，0.116ms。

注意事项（数据准确性，必须遵守） - ❌ 不要为了省排序而删掉次级键 id。RecordFilter.java:314 的注释是对的：同 visit_time 的病历必须靠 id 决定先后，去掉它会在页边界出现重复行 / 漏行。 - ✅ 方案 B 把 id ASC 改成 id DESC，只改变「同一接诊时间内的显示先后」，分页稳定性不受影响（仍是全序），但会改变 UI 上同秒记录的排列顺序——需产品确认可接受。 - ✅ 建议同步把 idx_records_org_visit_time (org_id, visit_time) 迁移脚本执行掉（它虽不解决排序，但对 COUNT(*) WHERE org_id=? 等仍有用），并补齐 DDL 里另一个缺失的 idx_department_visit_time（见 P1-3）。 - 该索引会新增约 10MB 索引空间（4 万行实测索引总量 10.1MB），可忽略。 - 建索引请用 ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE（MySQL 8 支持在线 DDL），避免锁表。

P0-2 后台批处理用偏移分页循环，扫完 4 万行需 4.9~26.9 秒

【问题描述】 QcServiceImpl.deductionStats（QcServiceImpl.java:378）与 QcBatchServiceImpl.run（QcBatchServiceImpl.java:485）都是同一形态：

int pageNo = 1;

后端改造（推荐） 1. 批处理改用主键/游标分页，彻底去掉 OFFSET： java // 首页 ... WHERE org_id = ? ORDER BY visit_time DESC, id ASC LIMIT 1000 // 后续页：以上一页末条的 (visit_time, id) 为锚点 ... WHERE org_id = ? AND (visit_time < :lastVt OR (visit_time = :lastVt AND id > :lastId)) ORDER BY visit_time DESC, id ASC LIMIT 1000 实测（配置②）扫完 4 万行仅 216.5ms，且页数无关——第 1 页与第 40 页耗时相同。 2. 关掉逐页 COUNT：批处理只需要「扫到没有为止」，不需要总数。用 Page<>(pageNo, size, false)（searchCount=false）或直接走 selectList + 游标。41 次 COUNT 累计约 669ms。 3. 若必须保留分页语义，至少把 wrapper 的 orderByDesc("visit_time").orderByAsc("id") 在批处理场景下换成只按 id 排序（FiltersDTO 重载的调用方是聚合/批处理，排序对它们无意义——RecordFilter.java:312 的注释已经点出这一点），配 (org_id, id) 索引即可。

注意事项（数据准确性） - 游标分页依赖 (visit_time, id) 是严格全序。id 是主键（varchar(36) UUID），本身唯一 → 组合键唯一，不会漏行也不会重复。 - 锚点必须用「上一页最后一条」而不是「第一条」，且必须包含 id（同 visit_time 有多条时只比较 visit_time 会漏）。 - 若处理过程中数据被并发删除/新增，游标分页可能出现边界抖动——批处理场景建议在同一事务/快照内完成，或接受「本轮可能漏掉刚插入的行」（与现状的偏移分页相比并无更差）。 - 不要通过「只处理前 N 条」来提速（MAX_SCAN_RECORDS = 40000 已是业务上限，不可再降）。

P0-3 /api/stats/all 一次性把 4 万行（≈320MB）载入 JVM 堆，且每条记录重复解析 5 次 JSON

【问题描述】 StatsServiceImpl.recordsFor()（StatsServiceImpl.java:246）：

QueryWrapper<Record> wrapper = RecordFilter.build(RequestUtils.currentOrgId(), filters);
return baseMapper.selectList(wrapper);   // 无分页、无投影

/api/stats/all（:125-133）拿到这份 list 后连续调用：

vo.setDisease(statsFor(records, "disease"));       // agg(records, "diseases")     → 解析 1 次/条
vo.setSymptom(statsFor(records, "symptom"));       // agg(records, "symptoms")     → 解析 1 次/条
vo.setPattern(statsFor(records, "pattern"));       // agg(records, "patternList")  → 解析 1 次/条
vo.setPrescription(statsFor(records, "prescription")); // agg("formulaList") + agg("herbs") → 解析 2 次/条

而 agg → extractFromStructured（:340）每次都执行 objectMapper.readValue(r.getStructuredData(), ...)。

合计：4 万条 × 5 次 = 20 万次 3.7KB JSON 解析，外加 4 万行 × ~8KB ≈ 320MB 一次性进堆。

实测参照：库内仅 500 行时，/api/stats/all 已需 120ms，而同页的 /api/stats/overview 只需 9ms、/api/stats/extra 40ms —— 线性外推到 4 万行约 9~10 秒，并有 OOM 风险（selectList 把全表实体一次性物化）。

【优化方案】

后端改造（按优先级） 1. 解析一次、多处复用：把 List<Record> 先映射成 List<Map<String,Object>>（或只抽出 diseases/symptoms/patternList/formulaList/herbs 五个数组），每条只 readValue 一次。仅此一项即可把 20 万次解析降到 4 万次（约 5 倍）。 2. 只取需要的列：selectList 前加 .select("id", "structured_data")，避免把 21 个文本列 + qc_results 一起拉进堆。 3. 改到 SQL 侧聚合：用 JSON_TABLE 把 structured_data 展开成行后在 SQL 里 GROUP BY 计数，只把 Top10 结果带回 JVM（records 表数据 314MB，全表在 DB 侧聚合仍可接受）。 4. 加缓存：统计结果是「准实时」语义（页面已有 FreshnessTag 提示读取时刻），可加 60s 缓存。系统已有 Redis（spring.data.redis 已配置），直接复用。 5. 流式/分批：若短期不动 SQL，至少把 selectList 改成游标分批（1000/批）并在每批内解析一次，避免 320MB 堆峰值。

注意事项（数据准确性） - 缓存 TTL 需与业务确认。医疗数据要求实时性的口径下，建议 60s 短 TTL + 写入病历/跑完质控后主动失效，而不是长 TTL。 - 「解析一次复用」不改变任何统计口径，属于纯性能优化，风险最低、收益明确，建议先做这一步。 - 用 JSON_TABLE 时注意 structured_data 可能为 NULL / 非合法 JSON（未结构化的旧病历），SQL 侧要能容忍，不能因此丢记录——现有 extractFromStructured 的 fallback（证候回退到 pattern 原始列）语义要在新实现里保留。

P1（严重影响使用）

P1-1 偏移分页在深页衰减（前端 jumper 可直接跳到第 4000 页）

【问题描述】 实测（4 万行，缓存态）：

首页 LIMIT 0,10 176.7 ms 1.8 ms 2.1 ms

第 2000 页 LIMIT 19990,10 626.2 ms 69.3 ms ~2.2 ms

P1-5 前端无请求取消 / 无防抖 → 并发重查询把后端放大

【问题描述】 usePagedList 只有响应侧取号（seq，latest-wins，慢的旧响应被丢弃），没有 AbortController；request.js 里也没有 signal。实测代码走查确认全仓库无请求取消。

后果：用户快速切换筛选 / 连点翻页时，N 个请求同时在飞，每一个都在后端跑一次 4 万行 filesort（未命中缓存时每次 0.7~1.05s）。前端虽然只采用最后一个响应，但后端已经白干 N 次，且占用 Hikari 连接池（maximum-pool-size: 20）。

Review.vue 一进页就并发 4 个 searchRecords（3 个 pageSize=1 拿 total + 1 个列表）→ 4 次全表排序。

【优化方案】 - 前端： 1. request.js 支持传入 signal；usePagedList.load() 在发起新请求前 abort() 上一个（取号逻辑保留，作为双保险）。 2. 筛选输入（TermInput 的关键词、el-select 的科室）加 300ms debounce，el-date-picker 的 change 事件再触发查询（现在是每次变更即查）。 3. 翻页按钮加「请求进行中禁用」（searching 已存在，接到 :disabled 即可），避免连点。 - 后端： 4. 新增轻量 POST /api/records/count（只执行 COUNT，不做 SELECT），供 pageSize=1 那类「只要总数」的调用替换。实测 COUNT(*) WHERE org_id=? 仅 5.5ms，比「COUNT + SELECT 全表排序」便宜一个数量级。 5. 现有 pageSize=1 的调用点（Records.vue:446、Review.vue:252-254、NlpBatchPanel.vue:241）改用它。 - 注意：AbortController 取消的是客户端等待，Spring MVC 侧不一定能中断已在执行的 SQL。所以根治仍要靠 P0-1 的索引（把单次查询从 700ms 降到 2ms），取消只是减少排队与连接占用。

【问题描述】 onSelectionChange = rows => selectedIds.value = rows.map(r => r.id)；无 row-key / reserve-selection，翻页即清空勾选。表格表头的「全选」复选框只选中当前页（≤50 条）。

【影响评估】 不影响功能正确性： - handleBatchDelete 提交的是当页勾选的 id，后端 filterAccessibleIds 会再按数据域过滤（安全）； - 批量质控提交的是 filters（Qc.vue:478 → recomputeQc({ filters: {...} })），不是 id 列表，后端按 filter 重新取数 —— 这是正确且高效的设计，不需要把 4 万个 id 传到前端再传回。

【优化方案】 - 前端：在「共 {{ total }} 条」旁边补一句说明，把「勾选 = 选中本页 N 条」与「按筛选范围操作 = 作用于全部 {{ total }} 条」明确区分（现在 danger-zone 的 danger-note 已部分做到，可再强化）。 - 若产品确实需要「跨页全选 4 万条再批量删除」，正确做法是提交 filters（复用 delete-by-filter），而不是把 4 万个 id 传到前端——既省流量又避免 id 列表被篡改。

P2-3 统计结果无缓存

【问题描述】 /api/stats/all、/api/stats/extra、/api/qc/deduction-stats 每次进入页面都重算，即使筛选条件完全没变。

【优化方案】 - 后端：对「同一 orgId + 同一筛选条件」的统计结果加 Redis 缓存，TTL 60s；病历写入 / 质控重算 / 批量任务完成后主动失效。 - 前端：Qc.vue 的 getDeductionStats 在筛选条件未变化时不重复请求（现在 onMounted 与「查询」按钮都会触发）。 - 注意：医疗数据实时性优先，TTL 不宜过长；页面已有 FreshnessTag 提示「数据为本次页面读取时刻」，可复用它向用户说明缓存新鲜度。

（现状核实） 全仓库没有任何查询缓存：无 @Cacheable / @EnableCaching / CacheManager；Redis（StringRedisTemplate / Redisson）目前只用于 JWT token（JwtUtil）与分布式锁。所以这一项不是「调优现有缓存」，而是从零引入——收益明确（/api/stats/*、/api/qc/deduction-stats 都是纯读聚合），但需要先把 P0/P1 的索引问题解决，否则缓存只是把慢查询的结果存起来，冷启动仍然慢。

P2-4 排序功能实际未实现（业务要求 vs 代码现状的差距）

【问题描述】 本次硬性约束写着「病历列表需要支持检索、筛选、排序、分页、勾选、批量质控」。但代码走查结果：

检查项 结果
前端 el-table 是否可排序 ❌ 全仓库无 sortable / sort-change / default-sort
后端是否接受排序参数 ❌ SearchDTO 无 sort / orderBy 字段
排序键 硬编码 ORDER BY visit_time DESC, id ASC（RecordFilter.java:97 与 :315）

即：当前是「固定排序」，不是「用户可排序」。这不是性能缺陷，而是功能覆盖差异——但它直接影响性能方案的走向：如果后续要补「按评分排序 / 按接诊时间正序 / 按分级排序」，那么：

  • 每新增一个可排序列，都需要一条与该排序键对齐的复合索引（(org_id, score DESC, id ASC) 等），否则每个新排序都退化成 4 万行 filesort（回到 P0-1 的问题）；

【优化方案】 - 后端：SearchDTO 增加受白名单约束的 sortBy / sortOrder（不要把用户输入直接拼进 orderBy——SQL 注入风险）；RecordFilter 按白名单映射到固定列名。 - 后端：为白名单里每个可排序列准备对应的 (org_id, <sortCol> <dir>, id ASC) 索引；或者先只开放 visit_time（已有索引），其余列在明确需求后再加。 - 注意：次级键方向必须与索引定义一致（见 P0-1 的坑）。

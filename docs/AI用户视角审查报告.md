## 一、问题清单

### 高

#### H1 同一份病历的「核心字段缺失」，质控说缺、AI 说齐全

| 项        | 内容                                                                                           |
| --------- | ---------------------------------------------------------------------------------------------- |
| 页面·角色 | 质控校验（扣分明细）· 人工复核（预检建议）· 病历详情 AI 解读 · AI 助手 —— 管理员与审核员都可见 |

**复现步骤**

1. 质控校验 → 范围查询「分级＝待复核」→ 点任一行「扣分明细」，记下结论。
2. 同一份病历调 `POST /api/qc/score`（页面弹窗的数据源）与 `POST /api/ai/interpret`（病历详情的 AI 解读、AI 助手的数据源）。
3. 对比两者的「核心字段缺失」结论。

**期望**：AI 解读要回答「这份病历为什么是 87 分、为什么待复核」，且与质控页同一口径。

**实际**（同一份病历 `723551fb-b3df-4b7e-b2cb-1786b66d0de0`，同一次会话内）

| 来源                      | 原文                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------- |
| `POST /api/qc/score`      | 评分 87、待复核；核心字段缺失-疾病 -6、核心字段缺失-证候 -6、术语未标准化-未命中词典 -1  |
| `POST /api/ai/interpret`  | 「规则预检：21 字段中完整 21 项。**核心字段齐全**。术语归一命中 12 处（精确 12）」       |
| AI 助手答「为什么待复核」 | 「…评分：87（待复核）。核心字段缺失：无。」                                              |

质控的 -6 是「结构化结果里没有、但原始病历有记录，可能未被抽取」，AI 的「齐全」只统计原始 21 列是否为空，两处用的是**同一个词、两套口径**。

**影响**：质控科用户问系统「这份为什么待复核」，得到的是「核心字段齐全」——他会直接推翻质控结论，或认为系统算错了分。这是本次审查中唯一会让用户做出错误业务判断的问题。

#### H2 一致性规则的类型写错了：「14 条（证候 → 中药 / 舌象 / 脉象）」

| 项        | 内容                               |
| --------- | ---------------------------------- |
| 页面·角色 | 质控校验 →「质控评分标准」· 管理员 |

**复现步骤**：打开质控校验页，看「质控评分标准」面板的「一致性」行；再点「规则配置」或展开「查看完整规则说明」对照。

**期望**：与规则实际内容一致，并随规则配置变化。

**实际**：页面写「14 条（证候 → 中药 / 舌象 / 脉象）」；`GET /api/qc/rules` 的 14 条里期望类型只有**中药 9 条 + 方剂 5 条**，没有任何舌象/脉象规则；「规则配置」弹窗与「查看完整规则说明」里也都显示「则 中药/方剂 应为…」。

**影响**：用户按这句话去找「舌象/脉象」相关规则，永远找不到；这句话是写死的，改过规则后依然这么显示，越改越误导。

#### H3 「查看完整规则说明」把正则表达式和英文字段名直接摊给业务用户

| 项        | 内容                                   |
| --------- | -------------------------------------- |
| 页面·角色 | 质控校验 →「查看完整规则说明」· 管理员 |

**复现步骤**：质控校验 →「质控评分标准」→ 点开「查看完整规则说明」。

**期望**：与同一系统的「规则配置」弹窗一致的业务语言（那里写的是「年龄 不合规扣 5 分」）。

**实际**（展开后逐字）

- 「格式检查：【年龄】须符合格式 `^\d+(\.\d+)?(岁|个月|月|天)?$`（- 5 分）；【性别】须为 男/女（- 5 分）。」
- 「术语（disease/pattern/symptom/herb/formula）未命中标准词典的，每个扣 1 分，最多扣 5 分。」

**影响**：这正是需求里明确要求避免的「技术术语泄漏」。同一套规则在同一页有两个入口，一个说人话、一个说机器话，用户会怀疑哪个才算数。

#### H4 批量解析的「重跑」无二次确认，且按当前表单范围提交

| 项        | 内容                                        |
| --------- | ------------------------------------------- |
| 页面·角色 | 结构化解析 →「批量解析」→ 最近任务 · 管理员 |

**复现步骤**

1. 结构化解析 →「批量解析」→ 最近任务列表（有一条已完成任务）。
2. 点该行「重跑」（不填任何筛选）。

**期望**：重跑这条任务，或至少二次确认并告知将处理多少条。

**实际**：**没有任何确认框**，直接发出 `POST /api/nlp/extract/batch`，请求体为 `{"filters":{"department":"","dateRange":null,"pattern":"","grade":""},"limit":0}`——即**当前表单的空范围＝全库**，与那条任务原本的范围无关。「开始批量解析」同样没有二次确认。

**影响**：业务用户以为「重跑」是重跑那条失败任务，实际会启动全库 500 条、约 90 秒的后台任务并覆盖结构化数据。同一屏上「开始批量解析」与「重跑」是两个后果相同、措辞不同、都没有确认的按钮。

## 三、做得好的地方

1. **零控制台噪声**：8 个页面 × 2 个角色 × 2 档视口，**没有一个 console error/warning、没有一条 4xx/5xx**。这在有异步任务轮询、图表、多弹窗的系统里很少见。
2. **权限三层都拦得住**：审核员侧栏只剩「首页看板 / 人工复核」；直输 `/records`、`/dictionary` 被退回看板；用审核员 token 调管理员接口返回 `403 {"code":403,"msg":"权限不足，需要角色：管理员"}`；不带 token 返回 `401 {"code":401,"msg":"未登录或token失效"}`。前端置灰、路由拦截、后端注解三道都实打实生效。
3. **评分可解释性做得很好**：扣分明细弹窗用「100 分起、逐项扣」的瀑布图给出「总分 100 → 术语未标准化 -5 → 最终得分 95 → 合格线 90 分」，明细里每条都带原因（「有 6 个实体未命中标准词典」）；人工复核页的预检建议更进一步，写「结构化结果中无证候（原始病历有记录，可能未被抽取）」——**直接告诉用户是漏抽而不是真缺**。
4. **删除入口的防呆是完整的**：单条删除、勾选批量删除（按钮实时显示「批量删除（10）」）、按范围删除，三者都有 `ElMessageBox` 二次确认，文案里带条数、写「不可恢复（会留痕）」；无勾选/无筛选时按钮直接置灰，从 UI 上就堵住了「误删全库」。
5. **长任务的交互闭环**：批量解析是后端异步任务，状态文案精确到数字（「进行中 244/500 · 成功 244 失败 0」「已取消（已处理 N，剩余未处理）」「已中断（服务重启），可重跑」），并明确告知「提交后可关闭本页，任务在服务端继续」。实测任务 500 条 89 秒完成、失败 0，与审计日志一致。
6. **弹窗与布局守住了尺寸**：4 个弹窗在 1366×768 下全部不溢视口、底栏都在首屏内（规则配置弹窗自适应到 673px）；人工复核页底栏 `sticky` 吸底在两种视口下都可见。
7. **术语归一是可信的**：解析页给出「有词典的实体 19 个：命中 12（精确 11 / 包含 1 / 模糊 0），未命中 7；另有 2 个实体所在字段无独立词典、不参与归一」——19＝12+7 自洽；试算工具当场给出「脾肾阳虚 → 脾肾阳虚（精确匹配，来源：中医病证分类与代码 GB/T 15657-2021）」和「嗓子疼 → 未命中词典，返回原词」，未命中不伪装成命中。
8. **LLM 配置弹窗写得很克制**：「API Key 不落盘，每次需重新填写」「点左下「测试连接」可就地看到结果，不必先保存」，没有把密钥、yml 键名暴露给用户。

## 四、系统性问题与改进建议

**① 同一事实存在两个权威（优先级最高）**

H1（核心字段缺失两套口径）、H2（规则类型写死）、M5（次数口径）、M3（治理口径）本质是同一件事：**同一个业务名词在系统里有多份定义，且没有任何一处说明它们的差别**。建议确立一条规则：**凡是会在界面上出现的判定结论，口径只有一份，且由后端下发**（H2 的那句「（证候 → 中药 / 舌象 / 脉象）」应该像规则配置那样由规则数据拼出来；H1 的「核心字段缺失」要么统一为「漏抽+真缺失」两档，要么在助手侧改用不同措辞，如「原始病历字段完整」）。这一条不修，后面每加一个功能都会多一处对不上。

**② 按钮名与实际行为不符（H4、L3、L5）**

「重跑」实际是「按当前范围重新提交」，「删除范围内病历」的实际前置条件是「必须先设筛选」却不说，「重置为全部」和别处的「重置」不是一回事。建议：**入口名只描述动作，前置条件与作用范围写在按钮旁边**（例如「重跑」→「按当前范围重新提交」，范围为空时按钮旁直接标「当前范围：全部 500 条」）。批量解析这类分钟级、会覆盖数据的操作，二次确认是底线。

**③ 给业务用户看的文字要过一遍「脱敏」（H3、L7、M6）**

正则表达式、`disease/pattern/symptom/herb/formula`、`logs/` 目录、「不再单独设分级」这类文字，说明书写者视角还停留在实现层。建议把「查看完整规则说明」直接复用规则配置弹窗已经写好的中文句子（那套句子是达标的），并加一条检查：**面向用户的文案里不出现正则、英文字段名、目录路径、版本变更口吻**。M6 的脱敏承诺属于「说了但没做」的反面——承诺了不存在的字段，比不说更危险。

**④ 助手与弹窗的层级关系需要定一个策略（M2）**

现在助手的定位是「全局可用」，但它被模态弹窗挡住。两种可接受的做法：把助手球的层级提到遮罩之上（并允许在弹窗内使用），或在弹窗打开时把助手入口收进弹窗内部（例如病历详情里给一个「问助手」按钮）。现状是「声明能查当前病历」但「打开病历就点不到助手」，属于设计冲突而非实现缺陷。

**⑤ 空态与空列要交代清楚（M4、M7、L8）**

「操作对象」恒空、「版本回滚」只有「暂无数据」、别名列整列为「无」——三者都不是 bug，但都会让用户怀疑系统坏了。建议：**留着的列必须有值，留着的空态必须解释为什么空、以及怎么才会有内容**（演示词典规模的问题建议直接在词典页标注「当前为演示词典，共 131 条」）。
